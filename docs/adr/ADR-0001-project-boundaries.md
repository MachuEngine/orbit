# ADR-0001 — 프로젝트 경계

- 상태: 제안 (개발자 검토 전)
- 작성일: 2026-11-10
- 관련 문서: `docs/architecture.md`, 세부 설계 초안 v0.1·하네스 설계 v0.1 (비공개, `private-docs/`)

## 배경

Orbit은 메일·캘린더·문서를 다루는 대화형 개인 AI 비서다. 1인 개발이고, 웹을 먼저 만든 뒤 데스크톱과 다른 제공자로 확장한다. 구현을 시작하기 전에 어떤 경계를 바꾸기 어렵게 고정할지 정해야 한다.

## 결정

1. **웹 우선, 공통 백엔드.** 첫 클라이언트는 웹이다. 데스크톱 클라이언트는 같은 HTTP API와 SSE를 쓰도록 하고, 클라이언트 전용 로직을 백엔드에 넣지 않는다.
2. **제공자 중립 Connector 계약.** 메일·캘린더 접근은 `MailConnector`·`CalendarConnector` 계약을 거친다. 첫 구현체는 Sim Provider이고, Google Adapter는 같은 계약 테스트를 통과해야 한다.
3. **실행은 워커, API는 중계.** Agent 실행은 백그라운드 워커에서 하고 API 서버는 Run 등록과 이벤트 중계만 맡는다.
4. **제품 상태의 원본은 Orbit DB.** LangGraph 등 라이브러리의 내부 상태를 API·UI가 직접 읽지 않는다.
5. **개발 하네스와 런타임 분리.** 코딩 에이전트 하네스와 서비스 런타임 Agent·가드레일은 파일·테스트·평가를 따로 둔다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 데스크톱 우선 (로컬 인덱스) | 서버에 메일 본문을 두지 않음 | 배포·평가 환경이 복잡해지고 웹 우선 목표와 맞지 않음. 데스크톱 확장 시 재검토 |
| Google API를 Orchestrator에서 직접 호출 | 계층이 하나 줄어듦 | Sim 환경에서 재현 가능한 실험을 할 수 없고, 다른 제공자로 확장할 때 수정 범위가 큼 |
| HTTP 요청 안에서 Agent 실행 | 구조가 가장 단순 | 연결이 끊기면 실행도 끊기고, 수 분 이상 걸리는 승인 대기를 처리할 수 없음 |

## 결과

- 장점: Sim Provider로 실제 사용자 데이터 없이 전체 흐름을 개발·평가할 수 있다. 클라이언트를 추가해도 백엔드를 다시 만들지 않는다.
- 비용: Connector 계약과 계약 테스트를 먼저 만들어야 한다. 워커와 큐 때문에 초기 구성 요소가 늘어난다.

## 미결정 사항

- 백엔드 언어와 프레임워크의 확정 (현재 Python 전제, 별도 ADR 필요)
- 프론트엔드 스택
- 설계 v0.2의 ADR(ADR-000, ADR-002 등)과 이 ADR의 번호 체계 통합 방법

## 재검토 트리거

- Sim과 Google Adapter의 동작 차이 때문에 실험 결론이 바뀌는 사례가 나올 때
- 데스크톱 클라이언트에 서버 API로 처리할 수 없는 요구(오프라인, 로컬 데이터)가 생길 때
