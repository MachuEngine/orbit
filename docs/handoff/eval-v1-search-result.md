# 평가 스위트 v1 검색 세트와 질의 문구 보완

## 범위

초기 검색 세트는 PR #24에서 main에 머지됐다. 이번 문구 보완은 그 main `634d94a`에서
`eval/search-query-diversity` 브랜치를 만들어 진행했다.
주제 문구의 글자 그대로 일치하는 질의만으로 RAG를 비교하는 편향을 줄이기 위해 두 형태를 바꿨다.
검색·색인·임베딩 실행기와 기존 검색 지표 정의는 변경하지 않는다.

실제 LLM 호출과 추가 LLM 비용은 **0**이다. `secrets/`·`private-docs/`는 읽지 않았다.
기존 세계·뼈대·종단 과제와 제품·채점 규칙·하네스는 유지했다.

## 생성 결과

검색 주제 60개에서 주제당 3개, 총 **180개**를 생성한다.

| --- | ---: | ---: | ---: |

- 기존 d2 과제와 공유하는 근거 body: 0개.

관련도 표는 주제 60개를 한 번씩 센 값이다. 같은 주제의 질의 세 개는 같은 관련도 맵을 공유한다.

| 메일함 크기 | 등급 0 | 등급 1 | 등급 2 |

| 200 | 36 | 60 | 60 |
| 1,000 | 96 | 60 | 60 |

작은 메일함이 큰 메일함의 부분집합인지 공통 `body_id`로 검증한다.

## 문구 보완 결과

- `keyword`: main의 60개 문구를 그대로 보존한 어휘 일치 기준 형태다.
- `paraphrase_question`: 프로젝트 이름은 보존하고 주제 명사를 동의어·설명 표현으로 바꾼다.
  표는 **20개 명사 × 서로 다른 표현 2개 = 40개**이며, 각 표현에 원래 명사의 토큰을 넣지 않는다.
- `person_time`: 주제 명사 없이 프로젝트·사람·실제 자료의 시점·사실 종류로 찾는다.
  다른 주제와 월 단서가 겹치거나, 같은 주제의 등급 1 문서가 같은 사람·같은 기간(Asia/Seoul 등 계정 시간대 기준)이라
  등급 2와 구별되지 않는 주제는 실제 자료의 현지 날짜로 구체화했다.
  **19개는 월, 41개는 날짜** 단서를 사용하고, "가장 최근에/마지막으로" 최신 조건을 붙인 질의는 0개이며 최종 버림은 0개다.
  날짜로도 같은 주제의 등급 1과 구별되지 않으면 등급 2가 더 나중일 때만 최신 조건을 쓰고, 아니면 버린다(주제당 1개 초과 시 생성 실패).
  조사는 받침으로 고른다(예전 "…28일야" 오류 20건 수정). 등급 1 겹침 검사는 같은 사람·프로젝트·기간만 보고 메일/문서 구분은 보지 않는다.
- 같은 조건을 말투만 바꾸는 것으로 구별됐다고 판정하지 않는다. 실제 다른 주제의 조건을 대조하고,
  더 세밀한 시점이나 다른 동의어를 시도한다. 끝까지 구별되지 않으면 사유를 기록하되 주제당 1개를 넘게 버리면 실패한다.
- 문구 시드와 분할 시드를 분리했다. `split_seed=20261116`을 고정하고 필터링 전 원래 슬롯으로
  분할을 정해, 문구 시드를 바꾸거나 질의가 배제돼도 남은 주제의 분할을 재배정하지 않는다.

### 형태별 어휘 겹침

| 형태 | 질의 수 | 평균 | 최댓값 |
| --- | ---: | ---: | ---: |
| keyword | 60 | 46.8333% | 60.0000% |
| paraphrase_question | 60 | 9.1464% | 11.1111% |
| person_time | 60 | 9.5969% | 11.1111% |

각 질의에서 `원래 topic_phrase의 토큰 집합에 속하는 질의 토큰 수 / 전체 질의 토큰 수`를 계산한 뒤
형태별 평균과 최댓값을 기록한다. NFC·소문자로 정규화하고, 공백·문장부호로 나뉜 연속 문자/숫자를
토큰으로 쓴다. 형태소 분석은 하지 않으며 프로젝트 이름도 겹침에 포함한다.
두 새 형태에서 원래 주제 명사의 토큰은 나타나지 않지만 프로젝트 이름을 유지하므로 비율은 0이 아니다.
이는 어휘 통계이며 키워드·벡터·혼합 검색의 성능 개선을 측정한 값은 아니다.

## 검증 정책과 한계

- 등급은 truth에서 그대로 가져온다. 각 계정의 매핑이 뼈대의 ID·body 대응 및 실제 세계의 ID와 맞는지 검사한다.
- 등급 1·2는 200통 메일함에도 있어야 하며, 모든 계정의 등급 2 본문에서 fact 표기를 확인한다.
- 등급 0은 해당 메일함에 실제로 존재하는 것만 기록한다. 작은 메일함에 없는 등급 0 후보는 생략한다.
- 정규화는 NFC·대소문자·공백 차이를 제거한다. 정답 표기 포함, 전체 주제 문구의 겹침, 중복 질의를 탐지한다.
  프로젝트 이름 같은 개별 단어의 공유만으로 주제가 충돌한다고 보지는 않는다.
  새 두 형태는 원래 주제 문구와 명사 토큰을 금지하며, 프로젝트 이름만 허용한다.
- 사람·시점 질의는 실제 발신자 또는 문서 소유자, 계정 현지 시각의 발송·수정 시점을 사용한다.
  문서 소유자가 작성·수정했다는 근거 없는 주장은 하지 않는다.
- 기존 main의 연결 요소와 분할을 유지한다. 문구 변경이나 배제로 남은 주제의 분할을 재배정하지 않으며, 관련도 값도 보존한다.
- 검색 결과의 중복 ID는 첫 등장만 남긴 뒤 k와 순위를 적용한다. 관련 항목이 없는 경우 지표는 0이다.
  recall은 등급 2와 등급 1 이상을 별도로 계산하고, MRR은 첫 등급 2의 역순위다.
  nDCG는 등급 자체를 gain으로 쓰며 지수 gain은 사용하지 않는다.
- test 질의는 105개여도 독립 묶음은 35개다. 변형 세 개를 독립 표본으로 보면 정밀도를 과대평가한다.
  독립 묶음 35개에 최악 분산을 가정한 정규 근사의 95% 비율 반폭은 약 ±16.6%p다.
  이는 실제 측정 신뢰구간이 아니라 규모의 한계를 설명하는 예시이며, 실제 비교는 묶음 단위 통계가 필요하다.

## 명세와 다른 부분·사람 검수

범위를 바꾸지 않았다. 명세가 정하지 않은 중복 순위 처리·빈 관련도 점수·분할 허용 오차는 코드와 문서에 명시했다.
등급 1이 없는 입력은 단언 위반으로 생성에 실패하고 누락 주제 수를 오류에 표시한다. 유효 출력의 매니페스트에도 그 수를 기록한다.

사람 검수에서는 다음을 우선 확인한다.

- 세 문구가 같은 주제를 찾으며, 최신 금액·마감 의도와 관련도 정답표가 맞는가? 표현의 매끈함보다 이 일치 여부를 우선한다.
- 동의어가 원래 주제와 같은 뜻인가? 사람·시점·프로젝트·사실 종류만으로 대상 주제가 하나로 읽히는가?
- 이전 값의 등급 1과 최종 근거의 등급 2가 질의 의도에 맞는가?
- 사람·월 또는 날짜 단서가 실제 근거에 맞고 정답 날짜나 금액을 노출하지 않는가?
- 등급 0 후보가 정말 답과 무관한 어려운 오답인가?
- 메일함 세 크기에서 질의와 관련도 의미가 같고, 부가 메일만 늘어나는가?
- 반복 변형의 상관과 test 35묶음의 정밀도 한계를 비교 실험에서 반영하는가?

사람 검수·test 봉인은 다음 단계이며 이번에는 수행하지 않았다. 공개 저장소의 정답은 읽을 수 있으므로
향후 검색 실행기도 test 실행 시 명시적 확인을 요구해야 한다. 색인 저장·재사용 방식은 RAG 실험 전에 따로 정한다.

## 질의 문구 보완 단계의 검증

- 동의어 표·금지 토큰·정답 미노출·조건 충돌의 대체/배제·필수 단서·분할/관련도 보존·결정성을 포함한 집중 테스트 **44 passed**.
- 실제 출력은 생성기 커밋 `10146dd`에서 만들었다. 다른 프로세스와 `PYTHONHASHSEED=19`로 재생성한 두 출력 파일이 바이트 단위로 같다.
- main 원본 스냅샷과 180행의 보존 필드, 키워드 60개의 문구를 직접 비교했다. 세계·뼈대·종단 과제·종단 매니페스트·검색 지표 모듈의 SHA-256이 작업 시작과 같다.
- 별도 Luna 읽기 전용 리뷰 후 필수 단서 누락을 거부하도록 보완했고, 재검토에서 주요 지적은 없었다.
- 모호성 검사는 합성 세계의 60개 주제에 대한 구조화된 조건을 비교한다. 표현의 의미와 사람이 읽었을 때의 구별 가능성은 후속 사람 검수가 필요하다.
- 백엔드 전체 테스트는 PostgreSQL 통합 테스트를 포함해 **2,590 passed / 35 skipped**. 건너뜀은 실제 Google 계약 34개와 실제 모델 호출 1개다.
- 요청한 환경 로드 후 `scripts/check.sh` 전체 **exit 0**. 프론트엔드 **479 passed**, 데스크톱 **201 passed**, ruff·mypy·ESLint·Prettier·TypeScript·하네스 검사를 통과했다. Electron GUI 스모크는 실행하지 않았다.
