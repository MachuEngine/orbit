# ADR-0027 — 종일 일정의 날짜 경계는 캘린더 시간대 기준

- 상태: 채택 (2026-11-16 개발자 결정)
- 작성일: 2026-11-16
- 근거: ADR-0026 §3(종일 일정 한계), Connector 계약(`backend/src/orbit/connectors/contracts.py`), Sim·Google 캘린더 커넥터의 계약 해석 규칙

## 문제
지금 계약 해석은 종일 일정의 `start`·`end`를 UTC 00:00으로 둔다(Sim·Google 어댑터 모두). 한국 시간(+09:00) 사용자에게 11월 20일 종일 일정은 11월 20일 09:00부터 11월 21일 09:00까지로 보인다.
- "11월 21일 일정"을 그날 00:00~24:00(현지)로 조회하면 전날 종일 일정이 같이 나온다(겹침 기준 조회).
- Google Calendar는 종일 일정을 날짜(`date`)로 저장하고 캘린더 시간대의 날짜로 해석한다. 지금 해석은 실제 동작과 다르다.
- 평가 세계 v1에는 종일 일정이 24개 있고, 종일 일정이 정답에 들어가는 문항을 만들 수 없었다(ADR-0026 §3).

## 결정
1. 종일 일정(`all_day=True`)의 `start`·`end`는 **그 일정이 속한 캘린더의 `time_zone`에서 00:00인 순간**이다. `end`는 배타적이다(하루짜리면 다음 날 00:00). 오프셋은 그 날짜의 오프셋이다(일광 절약 시간 전환일도 그날 현지 00:00).
2. 검증: 종일 일정의 `start`·`end`가 캘린더 시간대에서 00:00이 아니면 `ValueError`. 생성·수정 모두 같다. 캘린더 `time_zone`이 없으면 UTC로 본다(지금 기본값과 같다).
3. 조회(`list_events`)는 지금처럼 순간(instant) 겹침 기준이다. 1번 덕분에 현지 하루 범위 조회에 전날·다음날 종일 일정이 섞이지 않는다.
4. Google 어댑터: 읽을 때 `{"date": "YYYY-MM-DD"}`를 캘린더 시간대의 그날 00:00으로 바꾼다(캘린더 시간대는 `events.list` 응답의 `timeZone` 또는 캘린더 목록 값). 쓸 때는 `start`·`end`를 캘린더 시간대 날짜로 바꿔 `date`로 보낸다.
5. 커넥터는 종일 일정의 `start`·`end`를 캘린더 시간대 오프셋으로 표현해 돌려준다(순간은 1번과 같고 표기만 현지 오프셋). 그래서 모델에 보여 주는 도구 결과는 추가 조회 없이 캘린더 시간대 날짜를 표시한다. 날짜 표시를 위해 모델이 부르지 않은 커넥터 호출을 하지 않는다(평가 궤적·채점에 섞이지 않게).
6. Sim과 Google 어댑터는 같은 계약 테스트를 통과해야 한다(D1-1).

## 영향
- 평가 세계 v1의 종일 일정 24개는 생성기를 고쳐 현지 00:00으로 다시 만든다. 본문 명세가 바뀌지 않으면 이미 생성한 본문을 그대로 써서 `world.json`을 다시 조립한다(본문 재생성 비용 없음).
- 평가 데이터 v0에는 종일 일정이 없어 영향이 없다.
- 실사용 DB에 저장된 일정 스냅샷이 있으면 다음 동기화 때 새 해석으로 바뀐다. 종일 일정은 알림 대상이 아니다(ADR-0021).

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
| --- | --- |
| UTC 경계 유지, 종일 일정 문항 제외 | 실제 Google 동작과 달라 실사용 품질 문제가 남는다(개발자 결정) |
| 사용자 시간대 기준 | 같은 계정에 시간대가 다른 캘린더가 있을 수 있다. Google은 캘린더 시간대로 해석한다 |
| 계약에 `date` 필드 추가 | 계약 변경 범위가 커진다. 순간 표현을 유지하면 조회 로직을 바꾸지 않아도 된다 |
