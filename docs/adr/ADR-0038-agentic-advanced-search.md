# ADR-0038 — Agentic RAG 검색 도구에 Advanced RAG 검색 단계 넣기 (R03c)

- 상태: 채택 (2026-11-23). dev·test 실행을 마쳤다. 결과는 [rag-architecture-v1](../eval/rag-architecture-v1.md#r03c-agentic-rag-검색-도구에-advanced-rag-검색-단계-넣기)의 R03c 절에 있다. test 성공률 A2X 0.663(A2 대비 +0.181 [0.108, 0.253]), A2R 0.500(+0.017 [−0.049, 0.087]). 평가 경로 전용 구성이며 제품 기준 설정은 바꾸지 않는다.
- 작성일: 2026-11-22
- 근거: ADR-0036(RAG 아키텍처 비교, R03), ADR-0037(GraphRAG + reranker, R03b), ADR-0010(짝 비교·봉인), ADR-0006(RLS 밖 저장소), ADR-0019(메일 색인)

## 문제

R03·R03b test 결과에서 Advanced RAG(`A1`)와 Agentic RAG(기준, `A2`)는 약점이 서로 반대였다.

| 유형 (test) | Advanced RAG | Agentic RAG |
| --- | --- | --- |
| 단일 조회 | 0.708 | 0.431 |
| 다중 홉 | 0.167 | 0.417 |
| 전체 집계 | 0.639 | 0.306 |
| 전체 | 0.601 | 0.483 |

- Advanced RAG는 검색을 한 번만 한다. 첫 메일에서 얻은 값(예: 담당자 이름)으로 다시 검색할 수 없어서 다중 홉에 약하다.
- Agentic RAG는 다시 검색할 수 있지만, 검색 도구가 Hybrid 검색 순위를 그대로 돌려준다. 단일 조회·집계가 낮고 pass³(0.302)가 가장 낮다.
- 유형별 값은 탐색 결과다. Agentic RAG의 단일 조회가 낮은 원인이 검색 품질인지 에이전트 행동인지는 분리해서 재지 않았다.

질문: Agentic RAG의 검색 도구에 Advanced RAG의 검색 단계를 넣으면 다중 홉을 유지하면서 단일 조회·집계가 오르는가. 어느 단계가 효과를 내는가.

## 결정

### 1. 새 구성 두 개를 추가한다. R03·R03b 구성과 결과는 바꾸지 않는다

| 설정 ID | 사용자용 이름 | `search_indexed_mail`이 하는 일 |
| --- | --- | --- |
| `A2R` | Agentic RAG + reranker | Hybrid 상위 20통 → reranker → 상위 `max_results`통. 결과 형식(머리글 + 일치 청크 발췌)은 `A2`와 같다 |
| `A2X` | Agentic RAG + Advanced 검색 | 질의 재작성 → Hybrid 상위 20통 → reranker 상위 5통 → 문맥 압축. 결과에 발췌 대신 압축 본문을 넣는다 |

- 두 구성 모두 `A2`와 같은 ReAct 흐름, 같은 도구 집합(`search_indexed_mail`, `read_mail`, `submit_answer`), 같은 시스템 프롬프트를 쓴다.
- `A2R − A2`는 reranker 순위의 효과, `A2X − A2R`은 질의 재작성·압축을 더한 효과로 읽는다.
- reranker, 재작성·압축 프롬프트, Hybrid 후보 수 20은 `A1`과 같은 값·같은 버전을 쓴다. 새로 조정하지 않는다.

### 2. 세부 규칙

- **reranker 질의(두 구성)**: `A1`은 사용자 질문을 넣지만, 두 구성은 에이전트가 도구에 넘긴 `query`를 넣는다. 검색 호출마다 찾는 대상이 다르기 때문이다. `A2X`의 재작성 질의는 Hybrid 검색에만 쓴다.
- **재작성·압축의 입력(`A2X`)**: 사용자 질문 원문이 아니라 에이전트가 도구에 넘긴 `query`를 쓴다. 다중 홉의 두 번째 검색은 첫 메일에서 얻은 값을 찾는 것이므로 그 검색 의도에 맞춰 압축해야 한다.
- **`max_results`(`A2X`)**: 상위 5통으로 고정한다(`A1`과 같음). 에이전트가 넘긴 값은 무시하고 무시한 횟수를 기록한다.
- **`read_mail`**: 두 구성 모두 허용한다. `A2X`는 압축 본문이 부족하면 원문을 읽을 수 있다.
- **도구 설명**: `A2R`은 `A2`와 같다. `A2X`는 결과에 압축 본문이 들어간다는 한 문장을 더한다. 이 문장은 프롬프트 버전 문자열에 반영한다.
- **외부 콘텐츠**: 압축 본문도 메일 내용이므로 `A2`의 발췌와 같은 데이터 봉투·필드 상한을 적용한다(ADR-0018, D6-1).
- **검색 범위**: 후보를 읽는 SQL과 Connector 호출은 `A1`과 같은 경로를 쓰고 `workspace_id`로 거른다(D4-1, D4-4).
- **핸들 등록**(코드 검토 후 추가): reranker 입력용 후보 20통은 메일 ID로 읽고 작업 집합에 등록하지 않는다. 에이전트에게 반환한 메일만 등록한다. 에이전트가 보지 못한 메일 핸들을 짐작해 읽으면 `A2`와 정보 범위가 달라지기 때문이다.
- **빈 압축**(코드 검토 후 추가): 압축 결과가 비면 `A1`과 같이 머리글만 넣고 context recall에도 센다(R03의 도달 정의: 머리글이 들어간 메일은 센다). 횟수를 `empty_compressed_mails`(검색 호출 단위로 센 횟수, 같은 메일이 여러 호출에 나오면 중복으로 센다)로 기록해 결과에서 따로 보고한다.
- **에이전트 `query`의 봉투**: 재작성·압축 프롬프트에 에이전트 `query`를 봉투 없이 넣는다. `A1`과 같은 프롬프트를 유지해야 비교 조건이 같기 때문이다. `query`는 모델이 만든 값이라 앞서 읽은 메일 문장이 섞일 수 있다. 다만 재작성 출력은 검색어로만 쓰이고, 압축 출력은 원문 문장으로 검증되므로 이 경로로 쓰기 도구가 실행되지는 않는다. 평가 경로 전용 구성이며 제품 경로에는 넣지 않는다.

### 3. step·시간 상한

- `A1`처럼 reranker 입력을 만들려고 후보 20통을 Connector로 읽는다. `step_definition`(`llm_calls+connector_calls/v1`)에 따라 검색 1회에 step이 20 이상 늘어난다. `A2X`는 재작성·압축 LLM 호출 2회도 더해진다.
- R03 상한 `max_steps = 50`이면 검색 2회에서 걸릴 수 있으므로 두 구성은 `--max-steps 150`으로 실행한다. 이 상한은 실패 여부만 바꾸고 모델에게 보이지 않는다. 값은 설정 지문 `budget.max_steps`에 들어간다.
- 시간 상한(120초)과 토큰 상한은 R03과 같다. reranker가 CPU에서 검색마다 돌아 시간 상한에 걸리는 episode가 생길 수 있다. 상한을 결과를 보고 바꾸지 않고, 걸린 비율을 그대로 보고한다.

### 4. 설정 지문

- `A2`와 같은 항목에 더해 `search_variant`(`rerank` / `advanced`), reranker의 `model_id`·`revision`·`max_length`·`device`, 후보 수 20, 상위 수 5, 재작성·압축 프롬프트 버전.
- `A2`의 지문 골든 테스트는 바뀌면 안 된다.

### 5. 실행 기록

`rag_diag`에는 episode마다 ID와 숫자만 남긴다(ADR-0006). 질의문·압축 본문은 `rag_diag`에 저장하지 않는다. 결과 행의 실행 기록(`trace`, ADR-0029)에는 R03의 다른 구성과 같이 도구 인자와 결과 본문이 남는다. 이 기록은 합성 데이터 평가에만 쓰고 결과 파일은 git에 올리지 않는다.

- 검색 호출 수, 호출마다 후보 메일 ID와 반환 메일 ID, reranker 처리 시간(ms).
- `A2X`: 재작성 fallback 여부, 압축이 원문과 맞지 않아 원문으로 되돌린 메일 수, 무시한 `max_results` 횟수.

## 실행 순서

1. 구현과 단위·통합 테스트(implementer). `scripts/check.sh` 통과.
2. dev 실행: 두 구성 × 64문항 × 3회(구성당 192 episodes). 실행 전 비용을 다시 추정해 승인받는다.
3. dev 결과 보고. dev는 구현 결함 확인용이다. dev 결과를 보고 고친 것이 있으면 이 ADR에 기록하고 dev를 다시 실행한다.
4. test 실행: 두 구성 모두 한 번만 실행한다(ADR-0010). 실행 직전 `verify-seal`로 봉인을 확인하고, 실행 전 비용을 다시 추정해 승인받는다. dev 결과로 후보를 빼지 않는다.

## 지표와 통계

R03·R03b와 같은 지표, 같은 계산을 쓴다.

- **주 지표**: task success. 짝 차이를 cluster bootstrap 95% CI(10,000회, seed 0)로 낸다.
  - `A2R − A2`, `A2X − A2`(기준 대비)
  - `A2X − A2R`(재작성·압축의 추가 효과)
  - `A2R − A1`, `A2X − A1`(Advanced RAG 대비)
- 유형별 성공률과 짝 차이(탐색 결과로 표시). 다중 홉은 `A2`·`A1` 대비 값을 함께 낸다. pass³.
- **진단 지표**: context recall(episode 동안 받은 도구 결과 전체), 검색 호출별 recall@5(호출마다 반환 상위 5통 기준, 신규), 근거 인용 정밀도·재현율, groundedness Judge(repeat 0), 효율(검색·LLM 호출 수, 토큰, 비용, 지연 p50·p95, reranker 처리 시간), step·시간 상한 도달 비율.
- **정답 비교 Judge**: R03과 같은 Judge·프롬프트(`correctness-v2`)로 구성마다 표본 100건을 채점해 코드 채점 일치율을 낸다.
- dev 결과는 문항이 64개라 CI가 넓다. dev 값으로 우열을 결론 내지 않는다. CI가 0을 포함하면 차이를 확인하지 못했다고 쓴다.

## 예상 비용

R03 실측 단가로 추정했다(생성 `openai/gpt-6-luna`, Judge `google/gemini-3.6-flash`). `A2`의 episode당 비용은 $0.00077, `A1`의 재작성·압축 2회는 검색 1회당 약 $0.00026이다. `A2`의 평균 검색 호출 1.19회보다 늘어날 수 있어 여유를 두었다.

| 항목 | `A2R` | `A2X` | 합계 |
| --- | --- | --- | --- |
| dev 실행(192 episodes) | 약 0.15~0.25 | 약 0.25~0.40 | 약 0.4~0.65 |
| dev groundedness Judge(repeat 0) | 약 0.37 | 약 0.37 | 약 0.74 |
| dev 정답 비교 Judge(표본 100건) | 약 0.12 | 약 0.12 | 약 0.24 |
| **dev 소계** | | | **약 1.4~1.6** |
| test 실행(288 episodes) | 약 0.25~0.35 | 약 0.35~0.6 | 약 0.6~0.95 |
| test groundedness Judge(repeat 0) | 약 0.56 | 약 0.56 | 약 1.12 |
| test 정답 비교 Judge | 약 0.12 | 약 0.12 | 약 0.24 |
| **test 소계** | | | **약 2.0~2.3** |
| reranker | API 비용 없음(CPU 시간만) | | |
| **합계** | | | **약 3.4~3.9** |

- **비용 상한 4.5달러(제안)**. 현재 누적 약 11.04달러와 합치면 약 15.5달러 이하이고, 프로젝트 총예산(약 35달러) 안이다.
- dev·test 실행 전에 각각 다시 추정해 보고하고 승인받는다. 누적 비용이 상한을 넘으면 멈춘다. 후보와 지표는 줄이지 않는다.

## 대안

- **반복 검색(Advanced RAG 2회 고정)**: Advanced RAG 흐름을 두 번 돌리고, 두 번째 검색어를 LLM이 1차 문맥에서 만든다. 흐름이 고정돼 결과가 덜 흔들릴 수 있다. 이번 범위에 넣지 않았다. 이번 결과에서 `A2X`가 다중 홉을 유지하지 못하면 다음 후보로 둔다.
- **Adaptive RAG 라우터 개선**: R03 라우터는 다중 홉을 모두 `A1`로 보냈다(정확도 0.000). 라우터 프롬프트를 test 결과를 보고 고치면 누설이 되므로 이번 범위에서 다루지 않는다.
- **질의 분해(query decomposition)**: 두 번째 질문이 첫 답에 달려 있는 이번 다중 홉 질문에는 맞지 않는다.

## 결과와 위험

- 결과 문서에는 R03c로 따로 적고 R03·R03b 표의 값은 바꾸지 않는다.
- 효과는 이 합성 코퍼스(160문항)와 이 생성 모델에서 잰 값이다. 제품 기준 설정 변경은 이 결과만으로 결정하지 않는다.
- 검색마다 reranker가 돌아 지연이 늘어난다(R03 `A1` p50 11.3초). 실측해서 보고한다.
- `A2X`의 압축 본문은 에이전트가 원문을 읽지 않고 답하게 만들 수 있다. 근거 인용 정밀도와 groundedness로 확인한다.
