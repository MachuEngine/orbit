# ADR-0029 — 평가 지표 확장과 실행 기록 (v1 기준선 전)

- 상태: 채택 (2026-11-16 개발자 지시: "지금 측정 안되는 지표 모두 측정되도록 수정해서 진행")
- 작성일: 2026-11-16
- 근거: 평가 계획 §1(`docs/evaluation-plan-draft.md`), ADR-0009·0010(채점), ADR-0023(runflow 평가), ADR-0026(평가 스위트 v1)

## 문제
평가 계획 §1에 정의한 지표 중 러너가 재지 않는 것이 많다. 결과 행에는 도구 이름·인자·구조화된 답만 있고, 도구 결과 본문·답 문장·인용 핸들·결함 주입 시점이 없다. 이대로 기준선을 측정하면 지표를 추가할 때마다 비용을 들여 다시 실행해야 한다.

## 결정

### 1. 실행 기록을 먼저 넓힌다 (다시 실행하지 않고 지표를 더할 수 있게)
에피소드 결과 행에 다음을 남긴다. 평가 데이터는 합성이고 결과 파일(`runs/`)은 git에서 제외한다(ADR-0026 §7.3과 같은 근거). 실사용 DB·그래프 상태 규칙(ADR-0006)과는 무관하다.
- 턴별 사용자 발화와 최종 답 문장, 구조화된 답 원본
- 도구 호출마다: 이름, 인자, 결과 본문(모델에 보여 준 그대로, 호출당 상한 8,000자), 오류 종류, 결함 주입 여부와 규칙 이름, 지연
- 답이 가리킨 핸들과 그 핸들이 가리키는 아티팩트 ID(작업 집합 대응표)
- 턴별 구조화된 답(다중 턴)

### 3. Judge가 필요한 지표는 사후로 채점한다
- 서술형 주장의 근거성(§1-2)은 Judge가 필요하다. 계획대로 사람 라벨 표본과의 일치도(kappa ≥ 0.6)를 먼저 검증해야 한다.
- Judge 구성(`evalrunner/judge.py`, 프롬프트 `judge-v2`): 평가 대상(OpenAI)이 아닌 anthropic·google 두 계열이 각각 에피소드마다 답의 주장을 최대 8개로 나눠 supported·unsupported·not_checkable로 판정하고 에피소드 grounded 여부를 낸다. 응답 원문은 저장하지 않는다.
- 신뢰도는 에피소드 단위 grounded 이진 판정의 Cohen's kappa로 잰다(Judge 간, 각 Judge와 사람 표본 60건). 기준은 kappa ≥ 0.6이며, 못 미치면 Judge 지표를 보조 참고로만 쓴다. 주장 단위는 정렬이 어려워 분포만 보고한다.
- Judge 입력(답 문장·도구 결과 본문)은 에피소드 실행 때 기록한다. Judge 채점은 기록된 결과에 사후로 적용하므로 기준선을 다시 실행하지 않는다. 아래 보정 실험은 개발자가 지시한 범위와 비용 상한 안에서 수행한다.

#### judge-v2 보정 실험 (채택: Flash 3.6)
- 판정 기준에 계산값·빈 조회 결과·비서의 제안/작성 문구·성공한 쓰기 결과의 보고를 명시한다. 도구와 다른 값, 없는 사실, 미실행·실패한 행동의 완료 보고는 근거 없음이다. 응답 형식과 실사용 경로는 바꾸지 않는다.
- 기존 사람 라벨 60건 중 1건은 금액 단위 정규화 오류의 오경보를 정정해 근거 있음으로 바꾼다. 정정 후 모두 양성이므로 이 표본만으로 음성 탐지와 사람 kappa를 검증할 수 없다.
- 합성 기록에서 도구로 확인되는 사실이 있는 답을 대상으로 시드를 고정해 30건의 사실 하나(날짜·시각·금액·이름·장소)를 바꾼다. 대체 값은 도구 결과에 없음을 정규화해 확인한다. 나머지 원본 30건과 섞되 원본·변조본이 같은 에피소드로 중복되지 않게 한다. 이 선택은 부정·제안만 있는 답의 변조를 피하기 위한 것으로 표본 편향의 한계가 있다.
- 생성 도구는 별도 정답 키와 익명 Judge 입력, 단일 파일 라벨링 HTML을 만든다. 라벨링 자료에는 변조 여부·원래 ID·정답·Judge 판정을 넣지 않는다. 금액은 만 원 단위와 쉼표 숫자 같은 표기를 동등하게 대조한다. 원문·키·개별 판정은 git 제외 경로에만 둔다.
- 정답 키로 근거 없음 재현율(변조 음성 판정/30), 오경보율(원본 음성 판정/30), 전체 정확도(키 일치/60)를 고정 분모로 잰다. 판정 누락은 별도 보고하고 성공으로 세지 않는다. 새 사람 라벨을 받은 뒤 Cohen's kappa를 계산한다. 채택 기준은 사람 kappa ≥ 0.6 **및** 근거 없음 재현율 ≥ 0.8이다. 자동 정답과의 일치는 사람 검증을 대신하지 않는다. 프롬프트 보정에 사용한 원본을 재사용하므로 독립 검증 세트가 아니며, 통과해도 일반적인 환각 탐지 성능으로 확대 해석하지 않는다.
- 비교 모델은 claude-haiku-5.5, gemini-3.6-flash, gemini-2.5-flash-lite다. dry-run 후 누적 $1 안에서 순차 실행하며, 같은 계열 모델은 출력 폴더를 분리한다. 세부 실측과 과거 결과는 `docs/eval/results-v1.md`에 기록한다.
- 이전 `judge-v1` 사람 일치율은 Haiku/Lite 0.70/0.85, Sonnet 5.5/Flash 3.6은 0.82/0.92였고 뒤의 두 Judge 간 kappa는 0.53이었다. 이는 라벨 정정 전의 기록이다. Lite는 판정 누락 1건을 제외한 59건이다.
- 2026-11-17 균형 60건의 정답 키 기준으로 Flash 3.6/Haiku 5.5/Lite 2.5의 근거 없음 재현율은 1.000/1.000/0.867, 오경보율은 0.133/0.233/0.167, 정확도는 0.933/0.883/0.850이었다. 판정 누락은 각 0건이다. dry-run 합계 $0.2947 뒤 순차 180회에 $0.23542533을 썼다. 새 사람 kappa를 받기 전까지 세 모델 모두 실험 중으로 둔다. 추후 kappa 신뢰구간은 키로 원본의 38개 근거 묶음을 복원해 계산한다.

#### v3 표본: 코드 문자열 대조와의 비교 (실험 중)
- v2의 변조는 모두 도구 결과에 없는 값으로 바꾼 표면 치환이어서 Judge 고유 가치를 측정하지 못했다. v2 입력·키·결과를 보존하고 새 시드와 별도 v3 출력으로 다시 비교한다. 판정 프롬프트는 같은 `judge-v2`를 사용한다.
- 변조 30건의 목표는 surface 6, stale_value 5, role_swap 5, unsupported_addition 4, false_action 4, false_absence 3, meaning_flip 3건이다. 해당 원본이 부족한 유형은 이유와 실제 구성을 기록하고 다른 의미 변형으로 보충한다. surface는 최대 6건이다. 수동 검토한 합성 문장만 사용하고 LLM으로 생성·교정하지 않는다.
- stale_value와 role_swap에 새로 들어가는 날짜·시각·금액·이름·장소는 모두 실제 도구 결과에 있는 값을 쓰고 생성 때 검증한다. 원본·변조 에피소드의 중복을 금지하며, 정규화한 답 텍스트의 해시도 전체 60건에서 중복되지 않아야 한다. 별도 키에 유형·변경 설명을 보관하고 라벨링 HTML에는 투영하지 않는다.
- 기존 사실 추출기를 재사용한 문자열 대조 기준선과 세 Judge의 전체·유형별 탐지율, 원본 오탐률, 정확도와 비용을 같은 키로 계산한다. 핵심 비교는 surface를 제외한 유형에서의 탐지율 차이다. 사람 kappa는 새 라벨 전까지 pending이다. 코드 추출기의 놓침과 표본 선정 한계를 별도로 기록한다.
- 새 실행은 dry-run 합계가 $0.5 이하일 때만 진행하고 작업 누적 $1 상한을 유지한다. v2에서 이미 쓴 $0.23542533을 포함해 예산을 추적한다. 실측 전에는 개선 효과를 단정하지 않는다.
- 실제 구성은 surface 6, stale_value 3, role_swap 6, unsupported_addition 5, false_action 4, false_absence 3, meaning_flip 3건이다. 원래 답의 사실과 정정 전 값이 동시에 확인되는 stale_value가 3건뿐이어서 부족한 2건을 역할 교환과 사실 추가로 한 건씩 보충했다. 전체 60건은 source와 정규화 답 해시가 모두 유일하다.
- v3의 surface 외 24건에서 코드/Flash 3.6/Haiku 5.5/Lite 2.5의 탐지 수는 1/24/24/18건이었다. 각 원본 오탐은 7/2/6/4건, 정확도는 50.0%/96.7%/90.0%/83.3%다. 코드 대비 탐지율 차이는 Flash·Haiku +95.8%p, Lite +70.8%p다. 코드의 1건은 변형 전에도 계산값 때문에 음성으로 보던 항목이라 의미 오류 탐지로 해석하지 않는다.
- Lite의 false_action 판정 누락 1건을 분모에 포함했다. v3는 dry-run $0.294646 뒤 183회 요청(180개 쌍과 재시도)에 $0.23054425, v2 포함 $0.46596958을 썼다. 표본이 작고 보정 원본을 재사용하므로 일반화 근거로 확정하지 않는다. 유형별 표와 추출 한계는 `docs/eval/results-v1.md`에 남긴다.
- 사람 라벨(개발자 1명, 60건) 대조 결과 사람 kappa는 Flash 3.6 0.636 [0.446, 0.805], Haiku 0.575, Lite 0.454다(38묶음 bootstrap). 사람은 변형 30건 중 8건을 놓쳤고, Flash·Haiku는 그 8건을 모두 근거 없음으로 판정했다.
- **결정(채택): 근거성 Judge는 `google/gemini-3.6-flash` 단일 모델로 한다.** 점추정 kappa ≥ 0.6과 재현율 ≥ 0.8을 함께 충족한 유일한 모델이다. CI 하한이 0.6 미만이므로 Judge 근거성은 보조 지표로 보고하고, 성공률 비교의 결론을 바꾸는 근거로 쓰지 않는다.
- 판정 규칙 추가(다음 프롬프트 버전에서 반영): 도구 결과 없이 기능 부재를 단정하면 근거 없음, 미실행을 사실대로 보고하면 근거 있음이다. v3 결과는 이 규칙이 없는 `judge-v2`로 판정한 값이다.
- 후속 준비(2026-11-19): 두 규칙을 `judge-v3`에 반영하고 test 가용 10설정 1,300건 중 1,267건의 입력을 준비했다(답 없음 33건 제외). 전체 dry-run $6.121430이 실행 조건 $5.50을 넘어 실제 채점은 하지 않았다(지출 $0). 근거성·엄격 성공률은 미측정이며 기존 결정은 유지한다. [상세](../eval/results-v1.md#test-judge-v3).

### 4. 범위 밖
- 안전(§1-5)은 안전 세트가 없어 가드레일 실험 단계에서 한다.
- 검색 종단 지표(§1-4 종단)는 RAG 비교 실험에서 색인을 켠 실행으로 잰다.
- 음성(§1-8)은 별도.

## 영향
- 결과 파일이 커진다(도구 결과 본문). `runs/`는 git 제외라 저장소에는 영향이 없다.
- v0 결과 파일은 새 필드가 없으므로 새 지표는 "기록 없음"으로 표시하고 비교에 섞지 않는다.
- 이 변경 뒤 assistant_v0·runflow_v0의 luna 기준선을 dev에서 한 번 측정한다(중단한 이전 실행은 버린다).
