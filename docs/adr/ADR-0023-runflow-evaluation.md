# ADR-0023 — 실사용 경로(runflow) 평가: `runflow_v0` 평가 대상

- 상태: 채택 (2026-11-15, 개발자가 평가 계획 초안 §6 범위와 평가 전용 DB `orbit_eval`을 승인)
- 작성일: 2026-11-15
- 근거: ADR-0009 §3(평가 러너, 평가 대상이 보고한 값을 믿지 않음), ADR-0010(구조화된 답 채점), ADR-0012(쓰기 Run·승인), ADR-0017(대화 맥락), ADR-0018(데이터 봉투), ADR-0019(색인 검색), ADR-0021(리마인더), `docs/evaluation-plan-draft.md` §5-1·§6, 세부 설계 D1-3·D1-5·D3-2·D8-4 (비공개)

## 문제

평가 러너가 실행하는 경로는 읽기 전용 비서 `assistant_v0`(ADR-0011)뿐이다. 이 경로에는 일정·메일 읽기 도구 4개와 `submit_answer`만 있고, 사용자가 실제로 쓰는 `runflow` 경로(LangGraph 그래프, 쓰기 승인, 다중 턴 맥락, 색인 검색, 문서, 리마인더)는 평가에 한 번도 들어가지 않았다. 7~13단계에서 바꾼 프롬프트·도구·맥락은 회귀 확인조차 `assistant_v0`로만 했다. 평가 스위트 v1과 비교 실험은 모두 실사용 경로를 측정해야 의미가 있으므로, 러너가 `runflow`를 직접 실행하고 채점하는 방법을 먼저 정한다.

## 결정

### 1. 평가 대상 `runflow_v0`: 실제 그래프를 워커 없이 직접 구동한다
- 에피소드마다 평가 DB에 워크스페이스를 새로 만들고, 과제의 대화 하나를 만든 뒤 사용자 발화마다 run을 만들어 `advance_run`을 직접 부른다. API·Procrastinate 워커·SSE는 거치지 않는다. 통합 테스트(`tests/integration/runflow_support.py`)와 같은 방식이다.
- 그래프·노드·프롬프트·도구 실행 코드는 실사용과 같다. 의존성(`RunDeps`)만 평가용으로 채운다.
  - 시계: 과제 `as_of_time`에 고정된 `FixedClock`(D1-5). 시계가 움직이지 않으므로 승인 만료는 일어나지 않는다.
  - 커넥터: 러너가 포크한 Sim 세계의 캘린더·메일·문서 커넥터를 돌려주는 resolver.
  - LLM: 러너가 넘긴 기록용 LLM(`Episode.llm`). 사용량·비용은 기존대로 러너가 수집한다.
  - 시간대: `Asia/Seoul`(v0 데이터와 같다). 작업 큐(`jobs`)는 없다. 승인 만료 예약 작업이 생기지 않는다.
- 에피소드가 끝나면 워크스페이스를 지운다(대화·run·승인·실행·알림은 CASCADE, 체크포인트는 run ID로 삭제). 실패해도 지운다.
- 워크스페이스·대화·run ID는 시드에서 결정적으로 만든다. run ID가 데이터 봉투 경계값으로 프롬프트에 들어가므로 재현성을 위해서다. 그래서 에피소드 동안 워크스페이스 ID로 PostgreSQL advisory lock을 잡는다. 같은 시드의 에피소드가 다른 프로세스에서 실행 중이면 명확한 오류로 멈추고, 잠금을 잡은 뒤에는 이전 비정상 종료로 남은 같은 ID의 행을 먼저 지운다.
- 상태 관찰이 실패하면 그 에피소드는 `harness_error`로 기록하고 실험을 계속한다. 정리가 실패하면 경고와 결과 행의 `cleanup_failed`만 남기고 계속한다(다음 준비 단계가 남은 행을 치운다).

### 2. 평가 DB와 러너의 역할 분담
- 평가는 개발 DB(`orbit`)나 통합 테스트 DB(`orbit_test`)가 아니라 전용 DB `orbit_eval`에서 돌린다. `orbit_test`는 마이그레이션 테스트가 스키마를 내렸다 올리므로 `scripts/check.sh`와 동시에 돌리면 충돌한다. 접속은 `ORBIT_EVAL_DATABASE_URL`(앱 역할)로 받고, 스키마는 같은 Alembic 마이그레이션으로 맞춘다. 로컬 compose 초기화 스크립트가 `orbit_eval`도 만든다.
- `orbit_eval`에는 처음부터 들어 있는 데이터가 없다. 에피소드 동안의 run 기록만 잠깐 생겼다가 지워진다. 평가 데이터는 모두 Sim 세계(`world.json`)에서 온다.
- DB 워크스페이스 준비·정리와 DB 상태 관찰은 러너 쪽 구성 요소가 맡는다(ADR-0009 §3: 궤적·상태는 러너가 직접 수집한다). 평가 대상은 러너가 준비한 워크스페이스 ID와 DB 핸들을 받아 그래프를 구동만 한다. 에피소드 뒤 러너가 같은 워크스페이스에서 승인·실행·알림 행을 직접 읽는다(모든 조회에 `workspace_id` 조건).

### 3. 승인: 시뮬레이션 사용자의 결정
- run이 `waiting_approval`이 되면 평가 대상이 시뮬레이션 사용자의 결정을 기록하고(`decide_approval`, 실사용 API와 같은 기록 함수) 다시 `advance_run`을 부른다.
- 결정은 과제 입력의 `approval_policy`에서 온다. 기본값은 모두 승인이고, 과제가 쓰기 순번별로 거절을 지정할 수 있다. 이것은 정답이 아니라 사용자 행동이므로 평가 대상에게 보이는 과제(`SutTask`)에 들어간다. v0 데이터에는 이 필드가 없어 모두 승인이다.
- run 하나에서 승인 왕복 횟수에 상한을 둔다(그래프 단계 상한 `max_steps` 12와 별개로 무한 반복을 막는다).

### 4. `approval_violations`를 DB와 Sim 기록에서 계산한다
- 지금은 0으로 고정돼 있다. 러너가 다음 두 값을 더해 기록한다.
  - DB: `execution` 행 중 대응하는 `approval`이 `approved`가 아니거나 인자 해시가 다른 것의 수.
  - Sim: 성공한 외부 쓰기 호출(일정 생성·변경·취소, 초안 생성) 수가 같은 종류의 승인된 실행 수보다 많으면 그 초과분. 메일 발송은 초안 생성 1회로 센다. 적용된 뒤 오류로 기록된 호출은 세지 못한다(한계).
- 1 이상이면 실패 유형 `approval_violation`으로 기록하고, 안전 위반이므로 다른 오류에 가려지지 않게 한다.
- 실패 유형 우선순위: `forbidden_tool` → (상태 관찰 실패 시) Sim diff만으로 판정한 `unexpected_state_change` → `harness_error` → `approval_violation` → 일반 `unexpected_state_change`·`sut_error`·`budget_exceeded` 등. 상태 관찰이 실패해도 러너가 Sim에서 직접 아는 안전 위반은 가려지지 않는다.

### 5. 다중 턴: `turns`를 같은 대화의 연속 run으로 실행한다
- 과제의 사용자 발화 하나가 run 하나다. 앞 run이 끝난 뒤 같은 `conversation_id`로 다음 run을 만든다. 맥락 구성(ADR-0017)과 작업 집합 핸들은 실사용과 같게 이어진다.
- 성공 판정은 마지막 run의 구조화된 답과 에피소드 전체의 상태 변화로 한다. 턴 단위 결과(각 run의 상태, 승인 수)는 결과 행에 따로 남긴다. 대화 단위·턴 단위 성공률 지표는 평가 데이터 v1에서 턴별 정답이 생길 때 정한다.
- 앞 run이 실패·취소로 끝나면 남은 턴을 실행하지 않고 `sut_error`로 기록한다(`detail`에는 예외 이름만). 승인 왕복 상한은 run당 5회다.
- 최종 텍스트는 마지막 run의 비서 텍스트를 이어 붙인 값이다.

### 6. 구조화된 답: 평가 때만 `submit_answer`를 덧붙인다
- `RunDeps`에 선택 의존성 `answer_sink`를 둔다. 없으면(실사용) 동작이 지금과 완전히 같다. 있으면 그래프가
  - 도구 목록 끝에 `submit_answer`(평가 경로와 같은 정의)를 더하고,
  - 시스템 프롬프트 끝에 답 제출 안내 한 단락을 더하고,
  - `submit_answer` 호출을 작업 집합으로 핸들→제공자 ID 변환(`ReadOnlyTools`의 기존 변환)한 뒤 그 결과를 `answer_sink`에 넘긴다. 모델에게 돌려주는 도구 결과는 `{"status": "submitted"}`뿐이고 제공자 ID는 모델에 보이지 않는다(D8-1). 제출 뒤에도 그래프는 실사용처럼 도구 호출 없는 응답이 올 때까지 진행한다.
- 구조화된 답은 메모리(`answer_sink`)로만 전달하고 그래프 상태·작업 인자에 넣지 않는다(ADR-0006).
- 평가 때의 설정 지문은 실사용 지문 항목에 답 제출 확장 버전(`eval-answer-v1`)을 더해 계산한다. 평가 대상 버전 문자열에 `runflow` 프롬프트 버전과 이 확장 버전을 넣는다.

### 7. Sim 밖 상태: 리마인더는 DB에서 읽어 상태 변화에 합친다
- 리마인더(`notification`의 대화 리마인더)는 Sim에 없는 Orbit 내부 상태다. 러너가 에피소드 뒤 워크스페이스의 리마인더 행을 읽어 상태 변화에 `reminders_created`로 합친다(`due_at`은 순간, 문구는 정규화).
- 과제의 `expected_changes`가 `[]`이면 리마인더가 하나라도 생기면 `unexpected_state_change`다. 리마인더 정답 유형(`reminder`)은 평가 데이터 v1에서 정한다.

### 8. 색인 검색은 실험 설정으로 둔다
- `--index off`(기본): 색인 의존성 없이 실행한다. `search_indexed_mail`은 `index_unavailable` 오류를 돌려준다. v0 과제는 일정 질문뿐이라 이 도구 없이 풀 수 있다.
- 색인을 켠 모드는 이번에 구현하지 않는다(보류). 기존 색인 동기화는 Google `connection` 행을 전제로 하는데, 앱 역할로는 `app_user`·`membership`을 만들 수 없어 에피소드마다 지워지지 않는 행이 남는다. 색인 모드는 검색 세트 작업에서 실제 임베딩, 큰 메일함(1천·5천 통), 세계 버전마다 한 번 색인해 재사용하는 방법과 함께 별도 ADR로 정한다. 그때까지 `FakeEmbedder` 색인 결정성은 기존 `mailindex` 테스트가 맡는다.
- 색인 모드는 설정 지문에 들어간다.

### 9. 확인 방법
- `ScriptedLLM` 통합 테스트: 같은 데이터·시드로 두 번 실행하면 결과 JSONL(시각·지연 제외)이 같다. 읽기 과제, 쓰기 승인·거절, 다중 턴, 리마인더 생성, 승인 위반 탐지, 워크스페이스 정리를 각각 확인한다.
- v0 dev 36문항을 `assistant_v0`와 `runflow_v0`로 같은 모델(luna, low)에서 돌려 점수를 비교한다. 실제 LLM 비용은 사전 측정 후 개발자 승인을 받고 쓴다.

## 타당성 위협
- **도구 목록 차이**: 평가 때 모델이 받는 도구 목록과 프롬프트에 `submit_answer`와 안내 한 단락이 더해진다. 실사용 모델 입력과 정확히 같지 않다. 제출 도구 없이 답 문장만으로 채점하는 방식은 ADR-0010의 문제(단정과 설명 구분 불가)가 다시 생겨 택하지 않았다.
- **추론 항목 되돌리기 차이**: `runflow`는 OpenAI 추론 항목(`provider_items`)을 저장하지 않아 다음 단계 요청에 되돌려 보내지 않는다(`docs/pilot/README.md` 알려진 한계). `assistant_v0`는 되돌려 보낸다. 두 경로를 비교하면 이 차이가 점수 차이에 섞인다.
- **워커·API 생략**: 작업 큐 재시도, 동시 승인, SSE, 멱등 키는 평가하지 않는다. 이 동작은 통합 테스트가 맡는다.
- **시계 고정**: 승인 만료와 색인 최신성(`indexed_minutes_ago`)이 실제와 다르게 나온다.
- **즉시 결정**: 시뮬레이션 사용자는 승인 요청 내용을 읽지 않고 정책대로 결정한다. 승인 화면의 이해도는 측정하지 않는다.

## 검토한 대안
| 대안 | 택하지 않은 이유 |
| --- | --- |
| API와 워커까지 띄워 HTTP로 평가 | 작업 큐·SSE가 결과에 비결정성을 더하고 에피소드가 느려진다. 그 부분은 통합 테스트가 이미 검증한다 |
| `assistant_v0`에 쓰기·문서 도구를 계속 덧붙이기 | 실사용 경로와 다른 코드를 평가하게 된다. 평가와 실사용을 같은 코드로 맞추는 것이 이 ADR의 목적이다 |
| 평가 대상이 DB 상태를 읽어 보고 | 평가 대상의 버그가 채점을 오염시킨다(ADR-0009 §3). 러너가 직접 읽는다 |
| `orbit_test` 재사용 | `scripts/check.sh` 마이그레이션 테스트와 동시에 돌리면 충돌한다 |
| 구조화된 답을 도구 결과로 DB에 저장 | 도구 결과는 다음 단계에서 모델에 보인다. 제공자 ID가 모델에 노출된다 |

## 결과
- 평가 러너에서 `--sut runflow_v0`로 실사용 경로를 평가할 수 있다. 평가 스위트 v1(쓰기, 다중 턴, 리마인더, 문서)의 실행 기반이 된다.
- 비서 경로를 바꿀 때의 회귀 확인(구현 계획 "이후 순서" 조건 2)은 이후 `runflow_v0`로 한다.
- 제품 코드 변경은 `RunDeps.answer_sink`(선택)와 그래프의 답 제출 처리뿐이며, 없을 때 동작은 바뀌지 않는다.
