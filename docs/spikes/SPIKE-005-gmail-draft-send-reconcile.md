# SPIKE-005 — Gmail 초안 발송으로 메일 발송 결과 대조

- 상태: 완료 (2026-11-10) — **가정 성립**: 초안 발송은 초안 ID로 결과를 추적할 수 있고, 같은 초안은 두 번 발송되지 않는다
- 관련 결정: 세부 설계 D5-4, ADR-0003, SPIKE-004(가정 불성립)
- 기간: 1일
- 코드: `spikes/005-gmail-draft-send/` (스파이크용 코드이며 제품 코드로 쓰지 않는다)

## 배경

SPIKE-004에서 "앱이 넣은 고유 값으로 보낸편지함을 검색해 발송 여부를 확인한다"는 방법이 불성립했다. Gmail이 `Message-ID`를 덮어쓰고, 사용자 정의 헤더는 검색되지 않기 때문이다. 대안으로 **초안을 먼저 만들고 그 초안을 발송**하는 방식을 확인한다. 초안 ID는 발송 전에 알 수 있으므로, 발송 응답이 유실돼도 초안 ID로 결과를 추적할 수 있을 것이라는 가설이다.

## 확인할 질문

1. `drafts.send`로 발송하면 그 초안은 사라지는가. `drafts.get(draft_id)`가 발송 직후 바로 "없음"(404)을 돌려주는가.
2. 발송되지 않은 초안은 `drafts.get`으로 계속 조회되는가. 즉 "초안이 있으면 미발송, 없으면 발송됨"으로 판단할 수 있는가.
3. 이미 발송된 초안 ID로 `drafts.send`를 다시 호출하면 실패하는가. 실패한다면 같은 메일이 두 번 발송되지 않는다(자연스러운 멱등성).
4. 초안을 만들 때 받은 메시지 ID·스레드 ID가 발송 후 실제 보낸 메일의 ID와 같은가. 같다면 발송 결과를 메시지 ID로 바로 조회할 수 있다.
5. `X-Orbit-Execution-Id` 헤더가 초안 발송을 거쳐도 보존되는가.

## 실행 조건

- SPIKE-004와 같은 OAuth 클라이언트(`secrets/gmail-oauth-client.json`)를 쓴다.
- 권한은 `gmail.compose`(초안 생성·발송·삭제), `gmail.readonly`(발송된 메일 조회) 두 개다. SPIKE-004와 권한이 다르므로 토큰 파일을 따로 쓰고(`secrets/gmail-token-compose.json`), 처음 실행할 때 다시 로그인·동의한다.
- 수신자는 인증된 본인 주소로 고정한다. 한 실행에서 실제로 발송되는 메일은 `--count N`(1~5) 회차의 N통과 D6 시뮬레이션 1통을 합친 N+1통이다. 기본 `--count 3`이면 4통, 최대 6통이다.
- 스파이크가 직접 만든 초안만 삭제한다(D5의 발송하지 않은 초안 정리). 다른 메일이나 초안은 건드리지 않는다.

## 시나리오와 판정 기준

| ID | 구분 | 절차 | 기대 결과 |
| --- | --- | --- | --- |
| D1 | 검증 | 초안 생성 → `drafts.send` → 응답 수신 직후 `drafts.get(draft_id)` | 404(없음). 발송 후 없어지기까지 걸린 시간 기록 |
| D2 | 검증 | 초안 생성 후 발송하지 않고 `drafts.get(draft_id)` 반복 조회 → 끝나면 그 초안 삭제 | 매번 조회된다 |
| D3 | 검증 | D1에서 발송한 같은 `draft_id`로 `drafts.send` 다시 호출 | 실패(오류 코드 기록). 보낸편지함에 그 실행 ID의 메일이 1통뿐 |
| D4 | 관찰 | 초안 생성 응답의 `message.id`·`threadId`와 발송 응답·실제 보낸 메일의 ID 비교 | 같은지 다른지 기록 |
| D5 | 검증 | 발송된 메일을 조회해 `X-Orbit-Execution-Id` 비교, `SENT` 라벨 확인 | 보존됨, `SENT` 있음 |
| D6 | 관찰 | "응답 유실" 흉내: `drafts.send`를 호출하되 응답을 버리고, 초안 ID만으로 대조 절차(`drafts.get` → 없으면 D4에서 확인한 방법으로 보낸 메일 조회)를 실행 | 대조 절차가 "발송됨"과 실제 보낸 메일을 찾아내는지 기록 |

**가정이 성립했다고 보는 조건:** D1, D2, D3, D5가 기대대로 동작한다. D4·D6에서 발송 응답 없이도 실제 보낸 메일을 특정할 수 있으면 대조 방법으로 채택을 제안한다.

## 결과

| --- | --- | --- | --- |

### 판정 근거와 전제
- D3·D6은 보낸편지함 검색 결과에서 실행 ID(`X-Orbit-Execution-Id`)가 일치하는 메일 수로 확인했다. 제목 검색은 SPIKE-004에서 즉시 색인됨을 확인했고, 이번에도 0.7~0.8초에 찾았다.
- 계정 1개, 본인 발송, 4통이라 표본이 작다. 다른 수신자에게 보낼 때, Google Workspace 계정, 발송이 서버에서 지연되는 경우는 확인하지 않았다.
- `drafts.get`이 404인 이유는 "발송됨" 말고도 "사용자가 초안을 지움"일 수 있다. 그래서 404만으로 발송됐다고 판단하지 않고, 스레드에서 실행 ID가 일치하는 SENT 메일을 찾아야 확정한다(D6 방식).

## 결론과 Orbit 설계에 주는 영향

**가정은 성립한다.** 메일 발송을 "초안 생성 → 초안 발송" 두 단계로 나누면, 발송 응답이 유실돼도 초안 ID와 스레드 ID로 결과를 대조할 수 있다. 같은 초안을 다시 발송하면 Gmail이 404로 거절하므로, 재시도가 중복 발송으로 이어지지 않는다. SPIKE-004에서 무효가 된 D5-4의 메일 대조 방법을 이 방식으로 바꿀 것을 제안한다.

### 제안하는 메일 발송 절차 (ADR-0003 조건 1과 결합)
1. `execution` 행을 먼저 기록한다(ADR-0003 조건 1).
2. `drafts.create`로 초안을 만들고 `draft_id`, 초안 `threadId`, `X-Orbit-Execution-Id`를 `execution` 행에 저장한 뒤 커밋한다.
3. `drafts.send(draft_id)`를 호출한다. 응답을 받으면 발송된 메일 ID를 기록하고 끝낸다.
4. 응답이 유실되거나 결과가 불명확하면 대조한다.
   - `drafts.get(draft_id)`가 존재 → 미발송. 같은 `draft_id`로 다시 발송해도 중복되지 않는다(D3).
   - 404 → `threads.get(threadId)`에서 실행 ID가 일치하는 SENT 메일을 찾는다. 있으면 발송 완료로 기록한다.
   - 404인데 일치하는 메일이 없으면 → 사용자가 초안을 지웠을 가능성이 있다. 자동으로 다시 만들어 보내지 않고 "확인 필요"로 사용자에게 넘긴다(D5-4의 기존 원칙).

### 비용과 남은 확인
- 권한이 `gmail.send` 대신 `gmail.compose`(초안 관리)가 필요하다. Google OAuth 검토에서 이 스코프의 등급과 요구 사항을 출시 전에 확인해야 한다.
- 발송 절차의 API 호출이 1회 늘어난다(초안 생성).
- 사용자의 Gmail 초안함에 Orbit이 만든 초안이 잠깐 보일 수 있다. 사용자 경험 측면의 영향은 화면 설계 때 검토한다.
