# ADR-0026 — 평가 스위트 v1과 Sim 세계 v1

- 상태: 채택 (2026-11-16 개발자 승인. 첫 구현 범위와 본문 생성 방식은 개발자가 정했다)
- 작성일: 2026-11-15
- 근거: `docs/evaluation-plan-draft.md` §1·§4·§6(실행 계획 ②), ADR-0009(평가 러너), ADR-0010(구조화된 답 채점, 분할·봉인), ADR-0023(실사용 경로 평가), `docs/pilot/results-2026-11-15-runflow-v0.md`, `docs/pilot/results-2026-11-15-runflow-ablation.md`

## 문제

평가 데이터 v0로는 평가 계획의 비교 실험을 할 수 없다.
- **규모**: 60문항, 독립 묶음 15개(test 9개)다. 반복 3회 dev 결과에서도 성공률 신뢰구간 폭이 30~40%p라, 설정 간 10%p 차이를 구분하지 못한다.
- **범위**: 모든 문항이 단일 턴 일정 조회다. 쓰기, 다중 턴, 메일 내용 질의(RAG), 문서, 리마인더, 답할 수 없는 질문이 없다.
- **세계**: 가상 사용자 2명, 메일 215통(본문 중앙값 84자, 템플릿 문장), 일정 84개(사용자당 캘린더 1개, 평일 09~18시만, 종일·반복 없음), 문서 0개. 메일이 짧아 청크가 메일당 하나라 검색 방식 비교의 의미가 약하다.
- **천장·바닥**: terra는 dev 100%, luna는 60~76%다. 강한 모델 위에서는 개선을 측정할 수 없다.

실사용 경로 평가(ADR-0023)를 돌리면서 측정 도구 자체의 문제도 드러났다.
- **답 종류 오류**: runflow 실패의 3분의 2가 형식 실패다. 일정 변경 문항은 맞는 일정을 골랐는데 종류만 `event`로 냈다(`event_time`이 정답). 형식 실패는 모델에 따라 달라서(terra 0건, luna 다수) 모델 비교에 섞인다.
- **답 제출 안내 불일치**: `assistant_v0`는 [답하는 방법] 구역에 항목별로, `runflow_v0`는 `eval-answer-v1` 한 단락에 압축해 안내한다. 같은 과제를 두 경로가 다른 안내로 받는다.
- **원인 분석 불가**: 결과 행에 도구 이름만 남고 인자가 없다. 인물 다음 미팅 문항에서 빈 목록을 낸 원인(조회 범위, 이름 대조)을 확인할 수 없었다.
- **문항 문구 모호성**: "다음 미팅 일정을 알려줘"는 목록 질문으로도 읽힌다.

## 결정

### 1. 범위와 순서
- 이 ADR은 스위트 v1 전체(평가 계획 §4의 세트 7개)의 공통 규칙과 첫 구현 범위를 정한다.
- **첫 구현(실행 계획 ②)**: Sim 세계 v1, 종단 과제 세트, 스모크 세트, 검색 세트. 비교 실험 순서상 첫 번째인 RAG와 그다음 Agent 패턴·모델 비교를 바로 시작할 수 있는 범위다.
- **나중 구현**: 안전 세트, 음성 세트, Judge 검증 세트는 해당 실험 직전에 이 ADR의 공통 규칙대로 만든다. 운영 로그 세트는 운영 단계 일이다.
- 구현 순서: (a) 측정 도구 정리와 스키마 확장 → (b) 세계 v1 구조 생성기 → (c) 본문 실현(LLM) → (d) 종단 과제·스모크 생성기 → (e) 검색 세트 생성기 → ③ 사람 검수·test 봉인. 단계마다 implementer 위임, 검토, `scripts/check.sh`를 거친다.

### 2. 생성 방식: 구조는 코드, 문장은 LLM 한 번
v0의 원칙(정답은 코드가 계산하고 사람은 자연스러움과 타당성만 검수)을 유지하고, 문장만 LLM으로 만든다.
1. **구조 생성(결정적, 시드 고정)**: 사용자, 연락처, 캘린더, 일정, 메일 스레드, 문서와 그 사이의 사실 관계를 코드가 만든다. 각 메일·문서에는 "이 본문에 반드시 들어갈 사실"(날짜, 시각, 사람, 장소, 금액, 결정 사항)과 "들어가면 안 되는 사실"을 함께 정한다. 정답과 근거 태그는 이 구조에서 계산한다.
2. **본문 실현(LLM, 한 번만)**: 메일 본문과 문서 본문을 LLM이 구조를 받아 한국어 문장으로 쓴다. 결과는 `world.json`에 저장해 저장소에 커밋하고, 평가 때는 다시 생성하지 않는다. 그래서 평가 재현성은 v0와 같다.
3. **코드 검증**: 생성된 본문이 필수 사실을 모두 포함하는지(정규화한 문자열 대조), 금지 사실이 없는지, 실제처럼 보이는 개인정보(실존 도메인, 전화번호 형식, 실명 목록 대조)가 없는지 검사한다. 실패하면 같은 입력으로 다시 생성하고, 상한(3회)을 넘으면 그 아티팩트를 템플릿 본문으로 대체하고 매니페스트에 수를 적는다.
4. **기록**: 매니페스트에 생성 모델 ID, 추론 강도, 생성 프롬프트 버전, 시드, 아티팩트별 재생성 횟수, 생성 비용을 남긴다. LLM 응답 원문 로그는 남기지 않고 검증을 통과한 본문만 저장한다.
5. **이종 모델 교차 생성(2026-11-16 개발자 결정)**: 본문은 한 모델이 아니라 OpenAI를 포함한 서로 다른 계열 모델 3개(예: OpenAI, Anthropic, Google)가 나눠 쓴다. 어느 아티팩트를 어느 계열이 쓸지는 구조 생성 단계에서 시드로 정하고, 시나리오 유형·문항 유형마다 계열이 고르게 나뉘게 한다. 평가 결과를 본문 생성 계열별로 나눠 보면, 평가 대상이 자기 계열이 쓴 본문에서 더 잘하는지(자기 계열 편향)를 잴 수 있다.
6. **비용**: 생성 전에 아티팩트 수와 평균 길이로 비용을 추정해 개발자 승인을 받는다. 계열별 구체적인 모델은 그때 단가를 확인해 정한다. 본문 생성·자동 검수·모델 비교에 쓰는 모델은 단가 상한을 입력 2달러, 출력 10달러(1M 토큰당)로 둔다(2026-11-16 개발자 결정. 예: `claude-sonnet-5.5`, `gemini-4-argon`, `gpt-6.1-sol`까지). 같은 날 추가 결정: 상위 등급(입력 1달러 이상)은 쓰지 않고 저가 등급(`gpt-6-luna`, `claude-haiku-5.5`, `gemini-3.x-flash` 계열)만 쓴다. 실제 운영에서도 고가 모델을 제공하기 어렵다고 보기 때문이다. 프로젝트 마무리까지 총비용은 5만원 이내이고, OpenAI 모델은 OpenAI 직접 크레딧(잔액 약 9달러)으로 쓰고 크레딧이 바닥나면 OpenRouter로 바꾼다. Anthropic·Google 모델은 OpenRouter로 쓴다. 호출 경로를 바꾸면 설정 지문이 달라지므로 기준선을 다시 재고 이전 결과와 한 비교에 섞지 않는다. 실험 기본 모델은 모델 비교 결과로 정한다(그때까지 ADR-0015의 luna 유지).

### 3. Sim 세계 v1
| 항목 | v0 | v1 |
| --- | --- | --- |
| 가상 사용자 | 2명, 모두 `Asia/Seoul` | 종단 과제용 6명(5명 `Asia/Seoul`, 1명 다른 시간대) + 검색용 크기 단계 3명 |
| 메일 | 215통, 4주, 짧은 템플릿 | 종단 사용자당 약 300통(8주), 스레드(답장 2~6통), 서술형 본문, 첨부 이름. 메일·캘린더 불일치 사례 포함. 본문 길이는 짧음 40%·보통 40%·긺 20%로 섞는다(개발자 결정, 너무 짧으면 실사용과 달라진다) |
| 검색용 메일함 | 없음 | 200·1,000·5,000통 세 단계(사용자 한 명씩). 작은 메일함은 큰 메일함의 부분집합이고, 검색 질의의 관련 메일은 200통 메일함에 모두 들어 있다. 같은 질의 집합을 세 크기에서 돌린다. 본문은 5,000통 분량만 생성한다 |
| 일정 | 84개, 캘린더 1개, 평일 09~18시 | 사용자당 캘린더 2~3개, 종일·반복 일정, 하루 경계·시간대 경계 일정, 취소·변경 이력 |
| 문서 | 0개 | 종단 사용자당 20~40개(회의록, 견적, 계획서 등 텍스트 문서). Sim Drive 커넥터로 제공 |
| 데이터 규칙 | 합성, `example.*` 도메인 | 같음. 실존 회사·인물 이름을 쓰지 않는다 |

- 종일 일정: 계약 해석을 캘린더 시간대 날짜 경계로 바꿨다(ADR-0027, 2026-11-16). 세계 v1의 종일 일정 24개는 현지 00:00으로 다시 만들었고 본문은 그대로다. 생성기의 빈 날 배치 규칙은 본문 명세를 바꾸지 않으려고 옛 UTC 경계를 유지해, 종일 일정 앞뒤 하루가 비어 있는 경우가 있다.
- 다른 시간대 사용자 1명은 일광 절약 시간 전환일이 기간 안에 들어가는 시간대로 둔다.
- 세계는 버전마다 하나이고, 모든 세트가 같은 세계 버전을 매니페스트에 적어 참조한다(평가 계획 §4-1).
- 5,000통 메일함은 에피소드마다 색인하지 않는다. 세계 버전과 색인 설정 지문마다 한 번 색인한 결과를 재사용한다. 저장 위치와 재사용 방법은 검색 세트 구현 때 정한다(RAG 비교 실험 전 결정).

### 4. 종단 과제 세트
- **규모(2026-11-16 개발자 결정)**: 약 240문항(test 140, dev 100). 처음 계획한 약 400문항에서 줄였다. 설정 간 비교의 정밀도는 문항 수가 아니라 test 독립 묶음 수로 정해지고, 240문항으로도 독립 묶음 100개 이상(성공률 80%에서 95% CI 반폭 약 ±8%p)을 채운다. 줄어드는 것은 유형별 정밀도(test 유형당 약 25 → 약 14문항)인데, 유형별 수치는 어느 쪽이든 경향 확인용이다. 대신 비교 실험 1회 비용이 약 60%로 준다.
- 유형별 문항 수(dev+test, 유형 11개 모두 유지): 일정 조회 32, 메일 내용 질의 40, 쓰기 20, 다중 턴 20대화, 문서 질의 16, 리마인더 16, 메일·캘린더 불일치 16, 답할 수 없는 질문 16, 모호한 질문 16, 커넥터 오류 파생 24, 표현 변형 파생 24. 정확한 배분은 (d) 생성기에서 묶음 수를 보며 맞추고 매니페스트에 기록한다.
- **정답 유형 확장**: 기존 `event_set`·`event`·`event_time`·`time_slot`에 `message_set`(메일), `document`(문서), `abstain`(답할 수 없음을 알림), `clarify`(되묻기, 아래 모호한 질문 문항)를 더한다. 쓰기와 리마인더는 구조화된 답이 아니라 최종 상태(`expected_changes`, 리마인더는 ADR-0023 §7 방식)로 채점한다.
- **문항 문구 규칙**: 질문 문장만 보고 답 종류가 하나로 정해져야 한다. 예: "다음 미팅이 언제야?"(`event`)와 "이번 주 미팅을 모두 알려줘"(`event_set`)처럼 구분한다. 생성기 템플릿에 이 규칙을 적용하고, 사람 검수 항목에도 넣는다. 이 규칙은 사용자 질문에만 적용하고, 메일·문서 본문에는 실제처럼 모호한 표현이 있어도 된다. 아래 모호한 질문 문항은 이 규칙의 예외다.
- **모호한 질문 문항(2026-11-16 추가)**: 사용자가 모호하게 묻는 경우를 따로 잰다. 약 16문항(위 규모 참고).
  - 생성: 코드가 해석 두 개를 가진 질문 템플릿을 고르고(예: "민수와의 다음 미팅 일정 알려줘" → 바로 다음 미팅 하나 / 잡힌 미팅 전체), 두 해석의 정답을 각각 계산한다. 두 정답이 같으면 모호성이 결과에 영향을 주지 않으므로 그 문항은 버린다.
  - 정답 유형 `clarify`: 답하지 않고 사용자에게 되묻는다. 이 문항의 성공은 `clarify`다.
  - 실패 유형: 한 해석으로만 답하면 `ambiguity_ignored`로 기록하고, 그 답이 어느 해석의 정답과 맞는지도 남긴다. 해석을 밝히고 답했는지는 코드로 채점할 수 없어 이 버전에서는 성공으로 치지 않는다(Judge 도입 때 재검토).
  - 과잉 되묻기: 한 가지 뜻으로 읽히는 일반 문항에서 `clarify`를 내면 실패(`unneeded_clarify`)이고, 보고서에 일반 문항의 `clarify` 비율을 따로 적는다. 되묻기만 늘려 점수를 올리는 설정을 잡기 위해서다.
  - 되묻는 동작은 제품 동작이므로 평가 전용 안내가 아니라 실사용 시스템 프롬프트에 지시로 넣는다. 지금 `runflow` 프롬프트에는 "그거"처럼 앞선 대상을 가리킬 때 후보가 둘 이상이면 되묻는 규칙만 있다. 두 평가 대상(`runflow_v0`, `assistant_v0`)에 같은 내용의 지시를 넣고 프롬프트 버전을 올린다(§7과 같은 단계에서 한다). 답 제출 안내(`eval-answer-v2`)에는 되물을 때 `clarify`를 제출하는 방법만 둔다.
- **분할**: 근거 아티팩트를 공유하는 문항을 한 묶음으로 묶고 묶음 단위로 dev/test를 나눈다. test에 독립 묶음 100개 이상을 둔다. 파생 문항은 원래 문항과 같은 묶음이다. test 봉인은 ADR-0010 §2를 따른다.
- **난이도**: 강한 모델(terra)도 실패할 수 있는 유형(불일치, 다중 턴 참조, 답할 수 없는 질문, 큰 메일함 검색)을 포함해 천장 효과를 줄인다. 실제 난이도는 생성 후 기준 측정으로 확인하고, 이 ADR에는 목표 수치를 두지 않는다.

### 5. 스모크 세트
- 종단 과제 세트 dev에서 유형별로 고른 25문항. 선택은 시드 고정이고 목록을 매니페스트에 적는다.
- CI 회귀 확인용이다(실행 계획 ④). 비교 실험의 판단 근거로 쓰지 않는다.

### 6. 검색 세트
- 질의 150~200개. 각 질의에 관련 메일·문서 ID와 관련도 등급(0: 무관, 1: 부분 관련, 2: 답의 근거)을 둔다.
- 관련도는 구조 생성 단계의 사실 관계에서 코드가 정한다. 같은 사실을 다루지만 답이 아닌 메일(이전 버전 견적, 취소된 계획)을 일부러 넣어 등급 1과 혼동 사례를 만든다.
- 같은 질의 집합을 200·1,000·5,000통 메일함에서 돌려 크기별 recall을 본다. 지표는 평가 계획 §1-4(recall@k, MRR, nDCG@10)다.

### 7. 측정 도구 정리 (비교 실험 전 필수)
1. **답 제출 안내 통일**: 두 평가 대상이 같은 답 제출 안내를 쓴다. 정답 유형마다 "어떤 질문에 쓰는가"와 예시 질문 한 줄을 항목으로 둔다. 새 버전(`eval-answer-v2`)으로 기록하고, `assistant_v0` 프롬프트와 `runflow_v0` 확장의 버전을 함께 올린다.
2. **실패 유형 세분화**: `answer_format`을 둘로 나눈다.
   - `answer_kind`: 답 종류만 틀리고 가리킨 대상(일정·메일·문서 ID 집합)은 정답과 같다
   - 답 종류가 틀리고 가리킨 대상도 다르면 `wrong_answer`다(예: 인물 다음 미팅에 빈 목록). 내용이 틀린 것이기 때문이다
   - `answer_format`: 답이 없거나 필드·값 형식이 틀렸다
   - 성공 판정은 바꾸지 않는다(종류가 틀리면 실패). 보고서에 `answer_kind` 비율을 따로 적어, 모델·패턴 비교에서 이 비율이 크게 다르면 해석에 반영한다.
3. **도구 인자 기록**: 결과 행의 궤적에 도구 이름과 함께 인자를 남긴다. 평가 데이터는 합성이고 결과 파일(`runs/`)은 git에서 제외한다. 실사용 DB·그래프 상태 규칙(ADR-0006)과는 무관하다.
4. **v0 결과와의 연결**: v1에서 처음 측정한 값은 v0 결과와 한 비교에 섞지 않는다(ADR-0015 원칙과 같음).

### 8. 검수 (실행 계획 ③)
- v0 검수 도구(`orbit.evaldata.review`)를 확장한다. 문항마다 자연스러움, 정답 타당성, 답 종류 유일성(§4 문구 규칙)을 본다.
- 검수자 간 일치도를 재려면 두 번째 검수자가 필요하다. 개발자 1인이면 일부 문항(약 10%)을 시간 간격을 두고 다시 검수해 자기 일치도로 대신하고, 그 한계를 매니페스트에 적는다.

## 타당성 위협
- **생성 모델과 평가 대상의 계열이 같으면 유리할 수 있다**: 같은 계열 모델이 쓴 문장을 같은 계열 모델이 더 잘 읽을 수 있다. §2의 교차 생성으로 계열을 섞고, 아티팩트별 생성 계열을 기록해 결과를 계열별로 나눠 본다. 차이가 크면 해석에 반영한다.
- **LLM 문체의 단조로움**: 본문이 비슷한 문체로 몰릴 수 있다. 구조 단계에서 발신자 유형(동료, 고객, 자동 발송, 뉴스레터)과 길이를 다양하게 지정하고, 검수에서 표본을 확인한다.
- **정답이 구조에서만 나온다**: 본문에 필수 사실이 들어갔는지는 검사하지만, 본문이 의도와 다른 사실을 함축할 수 있다. 사람 검수로 보완한다.
- **모호성 판단의 주관성**: 어떤 질문이 모호한지는 사람마다 다르게 볼 수 있다. 모호한 질문 문항은 두 해석의 정답이 실제로 다른 경우만 쓰고, 사람 검수에서 "두 해석 모두 자연스러운가"를 본다.
- **공개 저장소**: 정답을 누구나 읽을 수 있다. 오염(학습 데이터 유입) 가능성은 v0와 같고 매니페스트에 적는다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 템플릿만 사용(v0 방식) | 비용 0, 완전 결정적. 하지만 본문이 짧고 단조로워 RAG 방식 비교의 의미가 약하다(개발자 결정) |
| LLM이 문항과 정답까지 생성 | 정답 오류를 찾기 어렵고 검수 부담이 커진다. 정답은 코드가 계산한다 |
| 평가할 때마다 본문 생성 | 재현성이 깨진다 |
| 공개 벤치마크(AgentDojo, τ-bench 등) 사용 | 한국어가 아니고 Orbit 커넥터·도구와 맞지 않는다. 설계 참고로만 쓴다 |
| 7개 세트를 한 번에 구현 | 비교 실험 시작이 늦어지고 검수가 한꺼번에 몰린다(개발자 결정) |

## 결과
- 새 데이터 버전 `orbit-eval@v1`과 세계 v1이 생긴다. v0는 회귀 확인용으로 남긴다.
- `assistant_v0`와 `runflow_v0`의 답 제출 안내가 바뀌므로 두 평가 대상의 버전이 올라가고, v1 기준선을 다시 잰다.
- 본문 생성에 일회성 LLM 비용이 든다(생성 전 추정·승인).
- 재검토 트리거: 기준 측정에서 천장·바닥 효과가 남을 때, test 독립 묶음 100개를 채우지 못할 때, 생성 본문 검증 실패율이 높을 때.
