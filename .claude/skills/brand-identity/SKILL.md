# 브랜드 정체성

> **프로젝트 보충 규칙**: `.claude/project-skills/brand-identity.md`가 있으면 이 문서보다 먼저 읽는다. 두 문서가 충돌하면 보충 규칙이 우선한다. 사용자, 제품 성격, 꼭 표현해야 하는 상태, 산출물 위치, 프론트엔드 스택은 보충 규칙에서 정한다.
>
> 이 파일은 하네스 템플릿(스킬 팩 `ui-design`)이 관리한다. 프로젝트에서 직접 고치지 말고, 다른 프로젝트에도 필요한 변경이면 템플릿 저장소에 반영한다.

> 이 스킬은 후보를 만들고 검증하는 데까지 한다. **최종 선택은 개발자가 한다.** 개발자가 고르기 전까지 모든 안은 `후보` 상태다.
> 산출물은 특정 프레임워크에 묶지 않고 CSS 사용자 정의 속성(custom properties)으로 낸다.

## 언제 쓰나
- 브랜드가 아직 없어서 처음 정할 때 (첫 화면을 만들기 전)
- 팔레트, 글꼴, 로고, 토큰 중 하나를 바꿀 때
- UI 코드에 토큰에 없는 색·글꼴 값이 필요해졌을 때 (토큰을 먼저 추가한다)

브랜드 문서 폴더(기본 `docs/brand/`)가 이미 있으면 `brand-guide.md`의 결정 기록부터 읽는다. 기존 결정을 바꾸는 경우에도 아래 절차를 따르고, 바꾼 이유를 결정 기록에 추가한다.

## 산출물
보충 규칙이 위치를 따로 정하지 않았으면 아래 경로를 쓴다.

| 파일 | 내용 |
| --- | --- |
| `docs/brand/brand-guide.md` | 브리프, 채택안과 기각안, 대비표, 글꼴 라이선스, 사용 규칙, 결정 기록 |
| `docs/brand/tokens.json` | 토큰 원본. 색·글꼴·크기·간격·모서리·모션 |
| `docs/brand/tokens.css` | `tokens.json`과 같은 값을 CSS 사용자 정의 속성으로 옮긴 파일 |
| `docs/brand/logo/*.svg` | 로고마크, 워드마크, 조합형. 밝은·어두운 배경용 |
| `docs/brand/logo/preview.html` | 사람이 눈으로 확인하는 미리보기 페이지 |

저장소가 공개 저장소이면 비공개 문서(예: `private-docs/`) 내용을 브랜드 문서에 옮기지 않는다.

## 절차

### 1. 브리프 정리
아래 항목을 짧게 정리해서 개발자에게 확인받는다. 확인받기 전에 2단계로 넘어가지 않는다. 보충 규칙에 브리프가 있으면 그것에서 시작한다.
- **사용자**: 누가, 어떤 상황에서, 하루에 얼마나 자주 이 제품을 쓰는지.
- **제품이 사용자에게 주어야 하는 느낌**: 성격 키워드 3~5개를 후보로 제안한다. 제품의 핵심 화면에서 키워드를 끌어낸다. 예를 들어 사용자가 위험한 동작을 승인하는 화면이 핵심인 제품이면 "통제할 수 있다", "무엇이 일어날지 미리 보인다"가 후보가 된다. 키워드는 개발자가 정한다.
- **피할 기본값**: 생성형 도구가 흔히 내놓는 조합을 명시하고 피한다.
  - 보라·파랑 그라데이션, AI를 뜻하는 반짝이 아이콘
  - Inter 단독 사용, 한글 쪽은 아무 검토 없이 Pretendard를 고르는 것 (Pretendard를 쓰지 말라는 뜻이 아니라, 고른 이유를 남기라는 뜻이다)
  - 크림색 배경 + 테라코타 강조색
  - 같은 모양의 둥근 카드를 격자로 늘어놓는 SaaS 대시보드 구성
  - 거의 검은 배경 + 형광 강조색 하나
- **꼭 표현해야 하는 상태**: 제품이 구분해서 보여 줘야 하는 상태를 정한다. 예: 일반 정보, 주의(외부·미확인 출처 등), 되돌릴 수 없는 행동, 성공, 오류. 정한 상태는 팔레트에 의미 색(semantic color)으로 들어가야 한다.

### 2. 팔레트 후보 2~3개
각 후보마다 다음을 쓴다.
- 이름과 한 줄 의도 (브리프의 어떤 키워드를 어떻게 표현하는지)
- 기본 색 5~7개 (hex)
- 의미 색 매핑: 밝은 모드와 어두운 모드 값을 각각 둔다. 아래 목록은 예시이며, 1단계에서 정한 상태에 맞게 더하거나 뺀다.
  - 공통: `bg`, `surface`, `text`, `text-muted`, `border`, `accent`, `on-accent`, `focus`
  - 상태 예시: `warning`(주의), `danger`(되돌릴 수 없음), `success`, `error`
- 대비표 (아래 기준과 계산 방법)
- 1단계의 "피할 기본값"과 어떻게 다른지 한 문장

**대비 기준 (WCAG 2.x)**
| 조합 | 기준 |
| --- | --- |
| 본문 글자 (`text`, `text-muted`, `on-accent`, 상태 색 글자) / 배경 | 4.5:1 이상 |
| 큰 글자 (24px 이상, 또는 굵게 18.66px 이상) / 배경 | 3:1 이상 |
| 입력창 테두리, 포커스 표시, 아이콘 버튼 같은 UI 요소 / 인접 배경 | 3:1 이상 |

밝은 모드와 어두운 모드 각각에서, `bg`와 `surface` 두 배경 모두에 대해 계산한다. 반올림해서 통과시키지 않는다(4.49는 실패다).

**계산 방법**: 값을 눈으로 어림하지 말고 계산한 결과를 표에 적는다. 임시 스크립트는 스크래치패드나 임시 폴더에 두고 저장소에 넣지 않는다.

```python
def lum(hex_):
    h = hex_.lstrip('#')
    def ch(c):
        c = int(c, 16) / 255
        return c / 12.92 if c <= 0.04045 else ((c + 0.055) / 1.055) ** 2.4
    r, g, b = (ch(h[i:i + 2]) for i in (0, 2, 4))
    return 0.2126 * r + 0.7152 * g + 0.0722 * b

def ratio(fg, bg):
    hi, lo = sorted((lum(fg), lum(bg)), reverse=True)
    return (hi + 0.05) / (lo + 0.05)
```

브랜드 가이드의 대비표 형식:

| 모드 | 전경 | 배경 | 비율 | 기준 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 밝은 | `text` #xxxxxx | `bg` #xxxxxx | 0.00:1 | 4.5 | 통과/실패 |

색만으로 상태를 구분하지 않는다. 상태 색은 아이콘·문구와 함께 쓴다는 전제로 설계하고, 색각 이상 사용자에게 두 색이 비슷하게 보여도 문구로 구분되게 한다.

### 3. 한글·영문 글꼴 조합
후보를 2개 정도 제안하고 아래 기준으로 비교표를 만든다.
- **한글 글리프 품질**: 본문 크기(14~16px)에서 받침이 뭉개지지 않는지, 영문·숫자와 섞였을 때 기준선과 굵기가 어울리는지. 제품에 자주 섞이는 문자열(주소, 날짜, 시각, 금액, 코드 등)의 숫자·기호 모양도 본다.
- **굵기**: 본문, 강조, 제목에 필요한 굵기(예: 400·500·700)가 실제 글꼴 파일로 있는지. 없는 굵기를 브라우저가 흉내 내게(faux bold) 두지 않는다.
- **라이선스**: 웹 임베딩과 재배포를 허용하는지 배포처의 라이선스 파일에서 직접 확인한다. SIL OFL 1.1 같은 라이선스가 예다. 확인한 라이선스 이름, 버전, 출처 URL을 브랜드 가이드에 적는다. 확인하지 못했으면 후보에서 뺀다.
- **용량**: 한글 글꼴은 글자 수가 많아 파일이 크다. woff2와 `unicode-range` 분할 파일(서브셋)을 제공하는지 적는다.
- **대체 글꼴 순서(fallback stack)**: 웹 글꼴이 늦게 오거나 실패할 때 쓸 시스템 글꼴을 정한다. 예: `"<선택 글꼴>", -apple-system, BlinkMacSystemFont, "Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR", sans-serif`

한글 조판 기본값도 토큰과 가이드에 함께 정한다.
- `word-break: keep-all`로 단어 중간에서 줄이 바뀌지 않게 한다. 대신 주소나 URL처럼 긴 문자열이 화면을 넘치지 않도록 `overflow-wrap: anywhere`를 같이 쓴다.
- 본문 줄 간격은 1.6~1.8 사이에서 고른다. 한글은 글자 높이가 고르게 커서 영문보다 줄 간격을 넉넉히 둔다.
- 본문 한 줄은 한글 40~50자 안팎이 되게 한다. 한글 한 글자가 대략 1em이므로 `max-width`를 `em` 단위로 잡는다.
- 자간은 글꼴 기본값에서 시작한다. 제목에만 조정하고, 바꾼 값은 토큰으로 둔다.

### 4. 로고
- 로고마크(기호) 2~3안, 워드마크 1~2안, 조합형 1안을 SVG로 직접 작성한다. 외부 이미지 생성 API는 쓰지 않는다.
- SVG 규칙: `viewBox`만 두고 `width`·`height`는 고정하지 않는다. 외부 글꼴·이미지 참조 없이 파일 하나로 완결한다. 색은 단색 채우기를 기본으로 하고, 16px에서 사라질 가는 선과 작은 장식은 넣지 않는다. 기호와 글자는 `<g id="mark">`, `<g id="wordmark">`로 묶는다.
- 워드마크 글자를 `<text>`로 두면 보는 환경마다 글꼴이 달라진다. 초안은 `<text>`로 두되, 채택한 뒤에는 라이선스를 확인한 글꼴로 윤곽선(path)을 만들어 넣는다. 이 변환을 하지 못했으면 브랜드 가이드에 미완료로 적는다.
- 제품 이름에서 바로 떠오르는 모양(이름 뜻을 그대로 그린 기호)은 다른 서비스 로고와 겹치기 쉽다. 이 방향을 고르면 기존 로고와 비슷하지 않은지 특히 확인한다.
- `preview.html`을 만든다. 각 로고를 64px, 32px, 16px로 그리고, 밝은 배경과 어두운 배경에 각각 놓는다. 조합형은 정사각 칸에 억지로 줄여 넣지 말고 기호만 따로 넣는다. 페이지는 외부 리소스 없이 같은 폴더의 SVG만 불러온다.
- 미리보기는 사람이 보고 판단한다. 브라우저 도구가 있으면 열어서 스크린샷을 함께 보여 주고, 없으면 파일 경로를 알려 준다.
- PNG가 필요하면 `command -v rsvg-convert`로 도구가 있을 때만 `rsvg-convert -w 512 -h 512 mark.svg -o mark-512.png`처럼 만든다. 도구가 없으면 설치하지 말고 생략했다고 보고한다.

### 5. 토큰 작성
- `tokens.json`이 원본이다. 디자인 토큰 커뮤니티 그룹(DTCG) 형식처럼 값마다 `$value`와 `$type`을 두는 구조를 권한다. 다른 구조를 쓰면 이유를 가이드에 적는다.
- 두 층으로 나눈다. 기본 색(예: `blue-600`)은 원본 값만 가지고, UI 코드는 의미 토큰(예: `color.text`, `color.warning`)만 쓴다.
- 포함할 묶음: 색(밝은·어두운), 글꼴 묶음, 글자 크기 단계(`rem`), 줄 간격, 굵기, 간격, 모서리, 그림자, 모션 길이와 가속 곡선(easing).
- `tokens.css` 구조:

```css
:root {
  --color-bg: #......;
  --color-text: #......;
  --font-body: "...", -apple-system, ..., sans-serif;
  --text-md: 1rem;
  --leading-body: 1.7;
  --motion-fast: 120ms;
}
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { --color-bg: #......; }
}
:root[data-theme="dark"] { --color-bg: #......; }
@media (prefers-reduced-motion: reduce) {
  :root { --motion-fast: 0ms; }
}
```

- 토큰 생성 도구가 빌드에 들어오기 전까지는 두 파일을 손으로 맞춘다. 값을 바꿀 때 두 파일을 같은 커밋에서 바꾸고, 대비표도 다시 계산한다.

### 6. 결정 기록
`brand-guide.md` 끝에 아래 형식으로 남긴다. 개발자가 고르기 전에는 모든 안을 `후보`로 둔다.

```markdown
## 결정 기록
### YYYY-MM-DD 팔레트
- 상태: 채택 / 후보 / 기각
- 채택안: <이름> — 고른 이유 (브리프 키워드와 연결)
- 기각안: <이름> — 기각 이유 (예: 어두운 모드 `text-muted` 대비 4.1:1로 기준 미달)
- 선택한 사람: 개발자
- 남은 일: 워드마크 윤곽선 변환 등
```

후보를 제시할 때는 각 안을 같은 형식(대비표, 미리보기, 장단점)으로 나란히 보여 주고, 추천안이 있으면 이유와 함께 하나만 밝힌다. 개발자의 선택을 받은 뒤에만 `채택`으로 바꾸고 토큰 파일을 확정한다.

## 지킬 규칙
- 글꼴은 웹 임베딩과 재배포를 허용하는 라이선스만 쓰고, 라이선스 이름·버전·출처를 가이드에 남긴다.
- 기존 상표나 잘 알려진 서비스 로고와 비슷한 모양·색 조합을 만들지 않는다. 이 스킬은 상표 검색을 대신하지 못하므로, 출시 전 상표 확인이 필요하다고 가이드의 남은 일에 적는다.
- UI 코드의 색과 글꼴 값은 토큰에서만 가져온다. 토큰에 없는 값이 필요하면 UI 코드에 직접 쓰지 말고 토큰을 먼저 추가한다.
- 측정하지 않은 효과를 쓰지 않는다. "가독성이 좋아진다" 대신 계산한 대비 값이나 확인한 조건을 쓴다.
- 브랜드 결정은 보통 코드 구조에 영향을 주지 않으므로 ADR이 필요 없다. 토큰 생성 도구를 빌드에 넣는 결정은 프론트엔드 스택 ADR에서 다룬다.

- [ ] 결정 기록에 채택안과 기각안, 기각 이유가 있다
