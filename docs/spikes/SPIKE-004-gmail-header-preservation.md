# SPIKE-004 — Gmail 발송 시 앱이 넣은 헤더 보존

- 상태: 완료 (2026-11-10) — **가정 불성립**: Message-ID는 바뀌고, 사용자 정의 헤더는 보존되지만 검색되지 않는다
- 관련 결정: 세부 설계 D5-4(멱등성과 결과 불명 처리, 메일 발송 대조 방법)
- 기간: 1일
- 코드: `spikes/004-gmail-headers/` (스파이크용 코드이며 제품 코드로 쓰지 않는다)

## 확인할 질문

D5-4는 메일 발송 결과가 불명확할 때(응답 유실) 다시 보내지 않고 "보낸 메일함에서 앱이 넣은 고유 토큰을 찾아" 발송 여부를 확인하기로 했다. 이 방법이 되려면 다음이 성립해야 한다.

1. Gmail API(`users.messages.send`)로 보낼 때 앱이 지정한 `Message-ID`가 그대로 보존되는가.
2. 앱이 넣은 사용자 정의 헤더(`X-Orbit-Execution-Id`)가 보존되는가.
3. 보낸 메일함에서 그 값으로 메일을 **검색해서** 찾을 수 있는가. 찾을 수 있다면 발송 후 얼마 뒤부터인가.

## 실행 조건

- **실제 Gmail 계정과 OAuth 동의가 필요하다.** 개발자가 Google Cloud에서 OAuth 클라이언트(데스크톱 앱)를 만들고, 브라우저에서 직접 로그인·동의한다. Claude는 계정 생성, 로그인, 인증 정보 입력을 하지 않는다.
- **실제 메일을 발송한다.** 수신자는 개발자 본인의 테스트 주소로 한정한다. 발송은 개발자가 직접 실행한다.
- 인증 파일은 `secrets/` 아래에 둔다. 이 경로는 git에서 제외되고 Claude의 읽기 권한도 막혀 있다.
- 스코프: `gmail.send`, `gmail.readonly`. 둘 다 Google의 민감·제한 스코프이므로 OAuth 앱은 "테스트" 상태로 두고 본인을 테스트 사용자로 등록한다.

## 시나리오와 판정 기준

| ID | 구분 | 절차 | 기대 결과 |
| --- | --- | --- | --- |
| G1 | 검증 | 앱이 만든 `Message-ID`(`<uuid@orbit.invalid>` 형식)와 `X-Orbit-Execution-Id`를 넣어 본인에게 발송 → 응답의 Gmail 메시지 ID로 보낸 메일을 조회(`format=metadata`) | 두 헤더 값이 보낸 값과 같은지 기록 |
| G2 | 검증 | `rfc822msgid:<Message-ID>` 검색어로 보낸 메일함 검색 | 1건이 검색된다 |
| G3 | 관찰 | G2 검색을 발송 직후부터 일정 간격으로 반복 | 검색되기까지 걸린 시간 기록 (여러 번 발송해 분포 확인) |
| G4 | 관찰 | `Message-ID`를 지정하지 않고 발송 | Gmail이 만든 `Message-ID` 형식 기록 (대조용 키로 쓸 수 없는 경우 대비) |
| G5 | 관찰 | 사용자 정의 헤더 값으로 Gmail 검색이 되는지 | 검색 연산자로 찾을 수 있는지 기록 (일반적으로 임의 헤더는 검색 대상이 아니라고 알려져 있으나 확인) |

**가정이 성립했다고 보는 조건:** G1에서 `Message-ID`가 보존되고 G2에서 검색된다. 보존되지 않으면 `X-Orbit-Execution-Id`로 대조하는 대안(G1의 두 번째 값, 최근 보낸 메일 목록 조회 후 헤더 비교)을 검토한다.

## 결과

실행: 개발자가 본인 Gmail 계정으로 `uv run python gmail_spike.py run --count 3` 실행 (2026-11-10). 첫 실행 4회차(Message-ID 지정 3회 + 미지정 1회)를 모두 마쳤고, 이어진 두 번째 실행의 1회차까지 같은 결과였다. 수신자는 본인 주소다.

| ID | 구분 | 결과 | 관측 |
| --- | --- | --- | --- |
| G1 (`Message-ID`) | 검증 | **불성립 0/4** | 보낸 `<uuid@orbit.invalid>` 대신 Gmail이 만든 `<CAARZbk…@mail.gmail.com>`이 저장됐다 |
| G1 (`X-Orbit-Execution-Id`) | 검증 | 성립 5/5 | 보낸 값과 조회한 값이 같다 |
| G2 (`rfc822msgid:` 검색) | 검증 | **불성립 0/4** | 보낸 `Message-ID`로는 120초 동안 검색되지 않았다. G1에서 값이 바뀌었으므로 당연한 결과다 |
| G3 (검색 지연) | 관찰 | 측정 불가 | G2가 검색되지 않아 지연을 잴 수 없었다 |
| G4 (`Message-ID` 미지정) | 관찰 | — | Gmail이 `<CAARZbk…@mail.gmail.com>` 형식으로 생성한다. 앱이 지정했을 때와 같은 형식이다 |
| G5 (사용자 정의 헤더 값 검색) | 관찰 | **검색 안 됨 0/5** | 값 그대로, 따옴표, `X-Orbit-Execution-Id:<값>` 등 4가지 질의 모두 0건이었고, 30초 뒤 재확인도 0건이었다. `Message-ID`의 uuid를 일반 검색어로 넣어도 0건 |
| G5 대조군 (제목 검색) | — | 5/5 | 같은 메일을 제목(실행별 태그 포함)으로 검색하면 0.3~0.5초 만에 정확히 1건(방금 보낸 메일)이 나왔다 |

### 판정 근거와 전제
- 대조군과 G2·G5는 검색 결과에 **방금 보낸 메일 ID가 들어 있는지**로 판정했다. 이전 실행의 메일이 섞여도 잘못 판정하지 않는다.
- 제목 대조군이 즉시 검색됐으므로, G5가 0건인 것은 색인 지연 때문이 아니라 사용자 정의 헤더가 검색 대상이 아니기 때문이다.
- 계정 1개, 본인에게 발송한 경우만 측정했다. Google Workspace 계정이나 다른 수신자에게 보낸 경우는 확인하지 않았다.

## 결론과 Orbit 설계에 주는 영향

**가정은 성립하지 않는다.** D5-4의 메일 발송 대조 방법("앱이 넣은 고유 값으로 보낸편지함을 검색")은 그대로 쓸 수 없다.

- 앱이 지정한 `Message-ID`는 Gmail이 덮어쓴다. 발송 응답이 유실되면 Gmail이 만든 `Message-ID`를 알 방법이 없으므로 `rfc822msgid:` 검색도 쓸 수 없다.
- 사용자 정의 헤더(`X-Orbit-Execution-Id`)는 보존되지만 검색되지 않는다.
- 제목에 고유 값을 넣으면 검색되지만 수신자에게 보이므로 제품에서는 쓸 수 없다.

### 대안 (다음 단계에서 결정)

| 대안 | 방법 | 확인된 점 | 남은 위험 |
| --- | --- | --- | --- |
| A. 최근 보낸 메일 헤더 비교 | 발송 시각 전후의 보낸편지함 메일을 기간 조건(`after:`/`before:`)으로 조회하고, 각 메일의 `X-Orbit-Execution-Id`를 비교 | 헤더 보존 (G1 5/5) | 메일마다 조회 호출이 필요하다. 발송 직후에는 목록 조회에 나타나기까지 시간이 걸릴 수 있다(지연 미측정) |
| B. 초안 생성 후 초안 발송 | `drafts.create`로 초안 ID를 먼저 기록하고 `drafts.send`로 발송. 결과가 불명확하면 초안이 남아 있는지로 판단 | 없음 (미검증) | 발송된 초안이 즉시 삭제되는지, 초안 조회가 발송 결과와 일관된지 확인이 필요하다 |

ADR-0003의 조건 1(실행 기록 선기록)은 그대로 유효하다. 바뀌는 것은 메일 발송의 "결과 불명 시 대조 방법"뿐이다. 대안 B를 확인하는 짧은 후속 스파이크를 거쳐 정한다.
