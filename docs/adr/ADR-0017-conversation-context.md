# ADR-0017 — 대화 맥락 이어가기

- 상태: 채택(구조). 맥락 크기 값(N·K 등)은 `실험 중` 기본값이다. 다중 턴 평가(D8-4) 전까지 바꿀 수 있다.
- 작성일: 2026-11-12
- 근거: 세부 설계 D8-1(작업 집합)·D8-2(맥락 구성)·D8-4(다중 턴 평가, 비공개 `private-docs/`), ADR-0006(RLS 밖 저장소), ADR-0011(읽기 비서·핸들), ADR-0012(쓰기 경로)

## 문제
지금은 run마다 그 run의 메시지만 모델에 넘긴다. 같은 대화에서 "그거 3시로 바꿔줘"처럼 앞선 결과를 가리키면 모델이 대상을 모르고, 핸들(E1, M3)도 run이 바뀌면 사라진다.

## 결정

### 1. 맥락 구성 (D8-2)
run을 실행할 때 같은 `conversation_id`의 앞선 run(종료 상태만, 지금 run보다 먼저 만든 것)을 읽어 다음 순서로 모델 입력을 만든다.
1. 시스템 프롬프트
2. `[이전 대화]` 블록: 최근 N턴보다 오래된 턴의 사용자 요청을 최근 것부터 최대 10개, 각 80자까지. LLM 요약은 쓰지 않는다(아래 "보류").
3. `[참조 가능한 대상]` 블록: 대화 작업 집합에서 최근에 나온 순서로 상위 K개 핸들과 짧은 설명(일정: 제목·시작·끝, 메일: 제목·보낸 사람·날짜). 제목·이름은 외부 콘텐츠이므로 `<external_content>` 표지로 감싼다.
4. 최근 N턴: 턴마다 사용자 원문과 그 run의 비서 응답 텍스트(단계 순서로 이어 붙임, 턴당 2,000자 상한). 앞선 run의 도구 호출·도구 결과 원문은 넣지 않는다(비용, 호출 ID 짝 맞춤 문제).
5. 지금 run의 메시지(지금과 같음)

기본값(`실험 중`): N = 6, K = 20. 상수는 한곳에 모으고 run의 설정 지문(`config_fingerprint`)에 포함한다.

읽는 범위: 노드 진입마다 DB에서 읽는 앞선 run은 최근 M = 30개로 제한한다(대화 길이에 비례해 읽기량이 늘지 않게). [이전 대화]·[참조 가능한 대상]·출처 분류 입력은 이 범위 안에서 만든다. 작업 집합 복원만은 범위와 상관없이 대화의 가장 최근 핸들 기록 한 행을 따로 읽는다(핸들 번호가 끊기지 않게). 그래서 M개보다 오래된 턴에서 사용자가 말한 주소는 출처 분류에서 `user`로 잡히지 않고 더 엄격한 쪽(`model`)으로 분류된다.

앞선 비서 응답 텍스트는 외부 콘텐츠를 요약한 내용을 담을 수 있다. 프롬프트에 그 안의 지시를 따르지 않는다고 적고, 쓰기는 지금처럼 서버의 출처 분류와 승인으로 막는다.

### 2. 작업 집합의 대화 범위 유지 (D8-1)
- 지금 run에 핸들 기록이 아직 없으면 같은 대화의 가장 최근 핸들 기록(앞선 run의 마지막 읽기 도구 결과 행)으로 작업 집합을 복원한다. 번호는 대화 전체에서 이어진다.
- 쓰기 도구의 핸들 해석, 인자 해시, 승인 흐름은 바뀌지 않는다.
- 인자 출처 분류(ADR-0012)의 입력에 같은 대화의 앞선 run의 사용자 원문과 도구 결과를 포함한다. 앞선 턴에서 사용자가 말한 주소는 `user`, 앞선 조회 결과의 주소는 `workspace_data`로 분류된다.

### 3. 대화 단위 직렬화
- 같은 대화에 종료되지 않은 run(queued·running·waiting_approval)이 있으면 `POST /api/runs`는 409 `conversation_busy`다. 맥락이 섞이는 것을 막는다. 멱등 키 재전송은 이 검사보다 먼저 기존 run을 돌려준다.
- 한계: 워커 장애로 run이 종료 상태로 가지 못하면 그 대화는 새 메시지를 받지 못한다(멈춘 작업 복구와 승인 만료가 대부분 정리한다). 사용자가 run을 취소하는 기능은 12단계 운영 범위에서 다룬다.

### 4. 대화 목록·이어서 보기 API
- `GET /api/conversations`: 최근 활동 순 목록(id, 제목 = 첫 사용자 메시지 첫 줄 40자, 만든 시각, 마지막 활동 시각, 마지막 run 상태).
- `GET /api/conversations/{id}`: 턴 목록(run_id, 상태, 사용자 원문, 비서 응답 텍스트, 대기 중인 승인 ID).
- 둘 다 `workspace_session` 안에서 조회하고, 다른 워크스페이스의 대화는 404다.

### 5. 저장 위치 (ADR-0006)
맥락은 노드에 진입할 때마다 `run_message`(RLS)에서 다시 만든다. 그래프 상태와 작업 인자에는 지금처럼 ID만 둔다. 새 테이블은 만들지 않는다.

## 보류 (평가 보류 목록에 추가)
- 오래된 턴의 LLM 요약: 비용과 요약 오류 위험이 있어, 다중 턴 평가로 필요성을 확인한 뒤 정한다.
- N·K 값 결정과 다중 턴 지표(참조 해소 정확도, 불필요한 되묻기 비율, 잘못된 대상 쓰기 시도 수): D8-4 평가 데이터가 생긴 뒤.
- 평가 경로(`assistant_v0`)는 단일 턴이라 이번 변경의 영향을 받지 않는다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 앞선 run의 메시지 전체(도구 결과 포함) | 메일 본문 등으로 입력이 빠르게 커지고, 비용·지연 상한이 없다 |
| 최근 N턴만(슬라이딩 윈도우) | 오래전에 조회한 대상을 가리키면 실패한다(D8-2) |
| run마다 작업 집합 새로 시작 | "그거"가 가리키는 핸들이 사라진다 |
