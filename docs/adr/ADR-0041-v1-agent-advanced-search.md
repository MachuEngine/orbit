# ADR-0041 — v1 Agent 색인 검색 도구에 Advanced 검색 단계 넣기

- 상태: 보류 (2026-11-24 개발자 결정). dev에서 성공률 차이를 확인하지 못했고 지연이 늘어 제품 경로에 넣지 않는다. 평가 경로 전용 변형(`--search-variant advanced`)은 재검토용으로 남긴다. 제품 경로(`runflow`의 기본 동작, 워커·API)는 바꾸지 않았다.
- 작성일: 2026-11-24
- 근거: ADR-0038(Agentic RAG + Advanced 검색, R03c), ADR-0031(v1 기준 설정: luna · react · 색인 켬), ADR-0040(최종 채점기), ADR-0010(짝 비교·봉인), ADR-0006(RLS 밖 저장소), ADR-0019(메일 색인)

## 문제

v1 기준 설정(luna · react · 색인 켬)의 dev 최종 성공률은 0.723이다(ADR-0040 채점기로 재현 확인). 실패 73건 중 `wrong_answer`가 29건으로 가장 많다.

R03c(RAG 과제)에서는 `search_indexed_mail` 안쪽을 Advanced RAG 검색 단계(질의 재작성 → Hybrid 상위 20통 → reranker 상위 5통 → 문맥 압축)로 바꾼 `A2X`가 기준 Agentic RAG보다 test 성공률이 +0.181 [0.108, 0.253] 높았다. 그런데 이 결과는 검색 도구 두 개만 쓰는 RAG 과제에서 나왔다. v1 Agent는 일정·문서·쓰기 도구를 함께 쓰고 과제 유형도 넓다.

질문: v1 Agent의 색인 검색 도구 안쪽을 `A2X` 검색 단계로 바꾸면 v1 dev 성공률이 오르는가.

`wrong_answer` 29건이 실제로 검색 실패 때문인지는 아직 나누지 않았다. 이 실험의 결과와 별개로 원인 분류는 저장된 실행 기록으로 따로 할 수 있다.

## 결정

### 1. `runflow_v0`에 평가 전용 검색 변형을 더한다

- `run`에 `--search-variant {default,advanced}`를 더한다. 기본값 `default`는 지금과 같다.
- `advanced`는 `--sut runflow_v0 --index on`에서만 쓴다. 다른 조합은 실행 전에 거부한다.
- `advanced`는 `RunDeps.tool_limits.search_override`(ADR-0038에서 만든 평가 전용 연결 지점)에 `AgenticSearch(variant="advanced")`를 넣는다. 도구 설명 끝에 `A2X_TOOL_NOTE` 한 문장을 붙인다.
- 그 밖에는 기준 설정과 같다: 도구 집합 전체(일정·문서·쓰기 도구 포함), 시스템 프롬프트, 모델, 추론 강도, 색인 지문. RAG 과제용 답 안내(`RAG_ANSWER_NOTE`)와 도구 제한(`A2_TOOLS`)·`ToolLimits` 맥락 글자 상한은 쓰지 않는다. `read_mail`이 외부 본문을 4,000자에서 자르는 규칙(`limit_external`)은 기준 설정과 같이 그대로 둔다.
- reranker(`BAAI/bge-reranker-v2-m3`, 같은 revision·max_length·device), 재작성·압축 프롬프트와 버전, 후보 수 20, 상위 수 5는 `A2X`와 같은 값을 쓴다. 새로 조정하지 않는다.
- 재작성·압축 LLM 호출은 `A2X`와 같이 SUT 모델(luna)로 하고, 에피소드 비용·step·토큰에 그대로 센다.

### 2. step 상한

`A2X`는 검색 1회에 후보 20통을 Connector로 읽어 step이 20 이상 늘어난다(ADR-0038 §3). 기준 설정의 상한 50이면 검색 2회에서 걸릴 수 있다.

- 이번 비교는 두 구성 모두 `--max-steps 150`으로 실행한다. 기존 기준 결과(`compare-v1/index-on.jsonl`, 상한 50)와 짝 비교하지 않고, 같은 상한으로 기준 설정을 새로 실행한다. 상한 외의 조건(실행 시점, 코드 버전)도 맞추기 위해서다.
- 시간 상한(120초)과 토큰 상한(200,000)은 기준 설정과 같다. reranker가 CPU에서 돌아 시간 상한에 걸리는 에피소드가 생길 수 있다. 상한을 결과를 보고 바꾸지 않고, 걸린 비율을 그대로 보고한다.

### 3. 설정 지문

- `advanced`에서는 `search_variant`, reranker `model_id`·`revision`·`max_length`·`device`, 후보 수, 상위 수, 재작성·압축 프롬프트 버전, 도구 설명 문장 버전을 지문에 넣는다.
- `default`의 지문은 바뀌면 안 된다. 기존 지문 골든 테스트가 그대로 통과해야 한다.

### 4. 데이터 경계

- 검색 경로는 `A2X`와 같다: 후보는 색인 SQL과 Connector가 `workspace_id`로 거른다(D4-1, D4-4). reranker 입력용 후보 20통은 임시 작업 집합에만 등록하고, 에이전트에게 돌려준 메일만 실제 작업 집합에 등록한다.
- 압축 본문도 메일 내용이므로 발췌와 같은 데이터 봉투·필드 상한을 적용한다(ADR-0018, D6-1).
- `rag_diag`에는 메일 ID와 숫자만 남긴다(ADR-0006). 질의문·압축 본문은 넣지 않는다.

### 5. 측정

- dev 88과제 × 3회, 시드 0. 두 구성(기준 `default`, `advanced`) 모두 `--max-steps 150`.
- 채점은 ADR-0040 최종 채점기(`.graded.jsonl`)로 한다.
- 주 지표: 성공률 짝 차이 `advanced − default`, 과제 묶음 부트스트랩 95% CI(10,000회, 시드 0).
- 보조: 실패 유형별 건수 변화, 시간 상한 도달 비율, 에피소드당 비용·지연(p50).
- dev 결과로 채택하지 않는다. dev에서 차이가 확인되면 test 실행(1회, 봉인 확인 후)과 제품 경로 반영 여부를 따로 결정한다. 제품 경로에 넣으려면 reranker 모델을 서버에서 돌리는 배포 결정이 함께 필요하다.
- 실행 전마다 비용을 추정해 개발자 승인을 받는다.

## 결과 (2026-11-24)

### dev 종단 비교

dev 88과제 × 3회, 시드 0, 두 구성 모두 `--max-steps 150`, ADR-0040 최종 채점기. 독립 묶음 73.

| 지표 | `default` (Agentic RAG, Hybrid) | `advanced` (A2X) |
| --- | --- | --- |
| 성공률 | 0.754 | 0.769 |
| `wrong_answer` | 24 | 22 |
| `unexpected_state_change` | 7 | 5 |
| 지연 p50 / p95 | 5.5초 / 12.7초 | 8.0초 / 25.1초 |
| 시간 상한(120초) 도달 | 0 | 0 |

- 성공률 짝 차이 `advanced − default`: +0.015 [−0.027, 0.060]. 차이를 확인하지 못했다.
- 색인 검색을 한 번이라도 쓴 에피소드는 264개 중 86개(호출 89회)다. 검색을 쓰지 않는 과제가 많아 검색 품질 변화가 전체 성공률에 드러나기 어렵다. 검색을 쓴 31과제만 보면 0.849 → 0.882지만 사후에 고른 부분집합이라 근거로 쓰지 않는다.
- 실행과 채점 비용은 두 구성 합쳐 약 $0.55다.
- 원본은 `eval/runs/agent-a2x-v1/`(git 제외)에 있다.

### reranker 후보 순위 비교 (오프라인)

`scripts/rag_v1_reranker_compare.py`로 R03의 A1 dev 실행에 저장된 1단계 후보 20통을 후보 reranker마다 원래 질문으로 다시 정렬했다. LLM 호출은 없다. rag-v1 dev 144행·48과제, CPU.

| 순위 | recall@5 | MRR | 20통 정렬 시간 p50 | 정답 메일 2통 이상 과제 recall@5 |
| --- | --- | --- | --- | --- |
| Hybrid 순서 그대로 | 0.730 | – | – | – |
| `BAAI/bge-reranker-v2-m3` (현재) | 0.830 | 0.927 | 5.9초 | 0.745 |
| `dragonkue/bge-reranker-v2-m3-ko` | 0.840 | 0.976 | 5.9초 | 0.759 |
| `Dongjin-kr/ko-reranker` (max_length 512) | 0.819 | 0.860 | 4.4초 | 0.728 |

- reranker는 Hybrid 순서보다 recall@5를 약 0.09~0.11 올린다. reranker끼리의 차이는 작고, 부트스트랩 CI는 계산하지 못했다(실행을 중간에 멈춰 결과 파일이 생기지 않았다). 위 숫자는 실행 로그에서 옮겼다.
- 1단계 후보 20통 안에 정답이 들어오는 비율(recall@20)이 0.917이라 reranker로 올릴 수 있는 상한이 있다.
- 정답 메일이 여러 통인 과제(이어진 메일)에서는 어느 reranker든 0.73~0.76에 머문다. reranker 교체로 이 문제가 풀리지 않는다.
- 질의는 실제 A2X처럼 LLM 재작성문이 아니라 원래 질문이다(재작성문은 저장하지 않는다, ADR-0006).
- `Qwen/Qwen3-Reranker-0.6B`는 CPU에서 1시간 넘게 끝나지 않아 중단했다. 점수 계산 코드도 검증하지 않았다.

### 결정

- 제품 경로에 A2X와 reranker를 넣지 않는다. v1 성공률 차이가 확인되지 않았고, CPU reranker가 검색 1회에 약 6초를 더하며 p95 지연이 두 배가 됐다. 제품에 넣으려면 reranker 서버 배포도 필요하다.
- 다시 볼 조건: reranker 지연을 검색 1회 1초 안팎으로 줄일 수 있을 때(GPU·API), 또는 색인 검색을 많이 쓰는 과제 비중이 커졌을 때. 그때는 test 1회 확인을 거친다.

## 대안

- **제품 경로(`mailindex`·`runflow`)에 바로 넣기**: reranker 모델 배포·지연 증가를 측정 없이 떠안는다. v1에서 효과를 확인한 뒤 결정한다. 보류.
- **기존 기준 결과(상한 50)와 짝 비교**: 실행 비용 약 $0.2를 아끼지만 step 상한과 실행 시점이 달라 차이를 검색 단계 효과로만 읽을 수 없다. 기각.
- **reranker만 넣기(`A2R` 방식)**: R03c에서 `A2R`은 기준과 차이를 확인하지 못했다(+0.017 [−0.049, 0.087]). 이번에는 효과가 확인된 `A2X`만 잰다. 기각.

## 영향

- 평가 경로에만 코드가 추가된다. `default` 실행 결과와 지문은 바뀌지 않는다.
- `advanced` 실행에는 평가 전용 의존성 그룹(`uv sync --group rag-eval`)이 필요하다.
