# 평가 계획 초안 (검토 대기, 2026-11-15)

> 개발자 검토 후 `docs/implementation-plan.md`의 "평가 보류 목록"과 필요한 ADR에 반영한다.
> 구성: 1) 평가 종류와 지표 → 2) 비교 실험(평가 종류의 지표로 설정을 비교) → 3) 기반 작업.
> 표기: **[기존]** 이미 정한 내용(출처), **[추가]** 이번에 새로 제안하는 내용.

## 공통 통계 규칙 [기존: ADR-0009 §3, ADR-0010 §2, 세부 설계 D3-3]
- 과제당 k회 반복(기본 3). 성공률은 묶음(cluster) 단위 bootstrap 95% 신뢰구간과 함께 보고한다.
- 두 설정 비교는 같은 과제에서의 짝지은(paired) 차이를 bootstrap한다.
- 신뢰성 지표 pass^k(같은 과제를 k번 모두 성공할 확률).
- test 분할은 봉인하고 실행 횟수를 기록한다.

## 1. 평가 종류와 지표

### 1-1. 과제 정확도 — 사용자가 원한 결과를 냈는가
- [기존: ADR-0010 §1] 성공률: 구조화된 답(`event_set`·`event`·`event_time`·`time_slot`)과 정답 ID 비교. 실패 유형을 `answer_format`(형식 오류)과 `wrong_answer`(오답)로 나눈다.
- [기존: D1-3, ADR-0009 §3] 쓰기 과제: 최종 상태 일치(`state_diff_match`, 비결정 필드 정규화) + 궤적 규칙(금지 도구, 승인 위반, 불필요한 쓰기)이 모두 통과해야 성공.
- [기존: ADR-0010] 보조 지표 `text_fact_recall`(답 문장에 정답 사실이 들어간 비율). 성공 판정에는 쓰지 않는다.
- [추가] 새 정답 유형: 메일 집합(`message_set`), 문서(`document`), 리마인더(`reminder`: `due_at` 순간 비교 + 문구 포함).
- [추가] 쓰기 인자 정확도: 수신자·제목·시각·참석자 필드별 일치율(필드 단위 오류 분석용, 성공 판정은 상태 일치).
- [추가] 다중 턴: 대화 단위 성공률(마지막 턴까지 모두 맞아야 성공)과 턴 단위 성공률을 함께 보고.

### 1-2. 근거성 — 답이 실제 데이터에 근거하는가
- [기존: D2-4] 요약의 완전성·근거성처럼 정형 채점이 안 되는 기준에만 LLM Judge를 쓴다. Judge는 사람 라벨 표본(60~100개)과의 일치도(Cohen's kappa, 0.6 이상 관례)를 먼저 검증하고, 평가 대상과 다른 모델 계열을 우선한다.
- [추가] 사실 근거율: 답의 주장 중 도구 결과로 뒷받침되는 비율. 날짜·시각·이름·숫자는 코드로 도구 결과와 대조, 서술형 주장만 Judge.
- [추가] 인용 정확도: 답이 가리킨 핸들(M3, E1, D2)이 정답 근거 아티팩트(`ref_*` 태그)인지 precision·recall.
- [추가] 답할 수 없는 질문: 올바른 기권률(정보 없음을 알림), 환각률(없는 정보를 지어냄), 과잉 거절률(답할 수 있는데 거절).

### 1-3. 도구 사용 — 맞는 도구를 맞게 썼는가
- [기존: ADR-0009·0010] 금지 도구 호출(`forbidden_tools`) = 실패, 승인 위반 = 실패, 궤적(도구 순서) 기록. `required_tool_calls`는 v0에서 비워 둠.
- [추가] 도구 선택 정확도: 과제별 기대 도구 집합 대비 recall(필요한 도구를 썼는가)과 잘못된 도구 비율(예: 내용 질문에 `search_mail`만, 문서 질문에 메일 도구).
- [추가] 인자 유효율: 도구 호출 중 스키마·형식 오류(잘못된 핸들, 시간대 없는 시각) 비율.
- [추가] 불필요한 호출: 과제별 최소 호출 수 대비 초과 호출 수.

### 1-4. 검색 품질 — 필요한 메일·문서를 찾았는가
- [기존: ADR-0019, 구현 계획] 비교 대상: Gmail 검색만(기준선) vs 키워드·벡터·혼합. `ts_rank`는 BM25가 아니므로 BM25 기준선은 평가에서 따로 계산. 워크스페이스 크기별 recall.
- [추가] 검색 지표: recall@k(k=5·10·20), MRR, nDCG@10. 정답 문서는 과제의 `ref_message` 태그로 코드가 정한다.
- [추가] 종단 지표: 검색 방식별 최종 과제 성공률(검색이 좋아져도 답이 좋아지는지).
- [추가] 검색 지연 p50·p95, 질의 시점의 색인 경과 시간(`indexed_as_of`).

### 1-5. 안전 — 공격과 실수로부터 사용자를 지키는가
- [기존: D6-3] 공격 서브셋 지표 세 개를 함께 본다: 공격 성공률, 공격 상황의 정상 작업 성공률, 정상 데이터에서의 오탐률. AgentDojo 방식 참고.
- [기존: D6-3, CLAUDE.md] 출시 차단 조건: 무승인 외부 발송 0건, 다른 사용자 데이터 노출 0건. 공격 성공률 기준값은 기준선 측정 후 정한다.
- [기존: 구현 계획 "추가 작업"] 실모델 인젝션 확인(지침 노출 0, 쓰기 도구 호출 0)은 동작 확인이며 측정이 아니다.
- [추가] 공격 유형별 성공률: 지시 따르기, 데이터 유출 시도, 쓰기 유도, 리마인더 생성 유도, 시스템 지침 노출.
- [추가] 방어 장치 ablation별 공격 성공률 변화(데이터 봉투, 승인 흐름).

### 1-6. 강건성 — 조건이 흔들려도 같은 품질을 내는가
- [기존: D1-4] 선언적 FaultPlan으로 같은 결함을 같은 시점에 주입해 패턴 간 복구 능력을 비교.
- [기존: D3-3] pass^k로 반복 실행 일관성.
- [추가] 결함 주입 시: 성공률, 정직 보고율(실패를 사용자에게 알린 비율), 결함 상황 환각률.
- [추가] 표현 변형: 같은 의도의 변형 묶음(존댓말·반말, 오타, 날짜 표현) 안에서 정답률 편차와 답 일치율.

### 1-7. 효율 — 얼마나 싸고 빠른가
- [기존: ADR-0009 §3, D3-4, D10-2·3] 에피소드별 LLM 호출 수, 입력·출력 토큰, `cost_usd`, `latency_ms`. 에피소드 예산(단계·토큰·시간) 초과는 실패. 실험 누적 비용 상한과 사전 비용 추정.
- [추가] 성공 1건당 비용, 지연 p50·p95, 첫 토큰까지 시간(화면 스트리밍), 과제당 도구 호출 수.

### 1-8. 음성 — 말을 정확히 알아듣고 자연스럽게 들려주는가 (ADR-0025)
- [기존: ADR-0025 §6] STT 정확도(한국어 CER, 고유명사 정확도), 음성 종단 성공률(같은 과제를 텍스트·음성으로 냈을 때 차이), 지연(녹음 종료→전사 완료, 질문→첫 음성 p50·p95), 분당 비용.
- [추가] 숫자·날짜·시각 표현 정확도(예: "다음 주 화요일 3시 반"), 전사 후 사용자가 고친 비율(운영 단계 온라인 지표), 잡음·말 빠르기·발화 길이별 CER.
- [추가] TTS: 읽기 문장 정리 정확도(빼야 할 기호·주소·핸들이 남지 않는 비율, 코드로 채점), 청취 선호(사람 평가, 쌍 비교).

### 2-1. STT 모델 선정 실험
- 현재 상태: `gpt-transcribe`는 공식 권장 모델이라 임시로 적용했다(ADR-0025 `실험 중`). 이 실험 결과로 선정하고 ADR에 `채택`으로 기록한다.
- 후보: OpenAI `gpt-transcribe`, `gpt-4o-mini-transcribe`(저가), `gpt-4o-transcribe`(두 모델은 2027-02-26 종료 예정이므로 비교 기준선으로만), 로컬 Whisper 계열(서버 비용 0, 지연·메모리 측정 포함). 후보 목록은 실험 시점에 공식 문서로 다시 확인한다.
- 데이터: 음성 세트(4-2)의 dev 분할로 비교하고, 선정은 test 분할에서 한 번만 확인한다.
- 지표와 선정 규칙(실험 전에 고정): 1차 CER(고유명사·숫자 표현 포함), 2차 음성 종단 성공률, 제약으로 지연 p95와 분당 비용. CER 차이가 짝지은 bootstrap 신뢰구간 안에서 구분되지 않으면 더 싸고 빠른 모델을 고른다.
- 재현성: 모델 ID 고정, 설정 지문에 STT 모델 ID(이미 포함), 같은 오디오 파일·같은 언어 힌트, 반복 3회로 비결정성 확인.


## 3. 메타 평가 (측정 도구 자체가 믿을 만한가)
Orbit이 아니라 채점기·데이터·지표를 평가한다. 이 결과가 나와야 해당 지표를 비교 실험에 쓸 수 있다.
- LLM Judge 신뢰도: [기존: D2-4] 사람 라벨 표본과 Judge의 일치도(Cohen's kappa). 기준 미달 항목은 사람 채점으로 남긴다. [추가] Judge 모델·프롬프트별 kappa 비교, 같은 계열 선호 편향 확인.
- 평가 데이터 라벨 품질: [추가] 검수자 간 일치도, 검수에서 수정·제외된 비율.
- 오프라인 지표 타당성: [추가] 운영 단계에서 오프라인 점수와 실사용 피드백의 상관.

## 4. 평가 스위트 v1 구성 (제안)
목적별로 세트를 나누고 각각 따로 버전을 매긴다. 형식·갱신 주기·쓰는 실험이 달라서다.

### 4-1. 공통: Sim 세계
- Sim 세계 = 코드가 만든 가상 사용자들의 메일함·캘린더·문서 데이터(`world.json`). 평가 때 실제 Gmail 대신 Sim 커넥터가 이것을 읽고 쓴다.
- 모든 세트가 같은 Sim 세계 버전을 참조하고, 질문·정답만 세트별로 둔다. 세트는 자기가 기준으로 삼는 세계 버전을 매니페스트에 적는다.
- v1 세계: 가상 사용자 확대, 문서 데이터 추가, 메일함 크기 200·1천·5천 통 세 단계(검색 세트용).
- 분할 규칙은 모든 세트에 같게 적용한다: 근거 아티팩트 묶음 단위 dev/test 분할, 정답 지문 중복 제거, test 봉인(ADR-0010 §2). 세트가 달라도 같은 근거 아티팩트를 쓰는 문항은 같은 분할에 둔다.

### 4-2. 세트 목록
| 세트 | 규모 | 형식 | 쓰는 평가 | 갱신 |
| --- | --- | --- | --- | --- |
| 종단 과제 세트 | 약 400문항(아래) | 질문 → 구조화된 답·최종 상태·궤적 규칙 | 1-1, 1-2, 1-3, 1-6, 1-7 | 데이터 버전 단위 |
| 검색 세트 | 질의 150~200개 | 질의 → 관련 메일·문서 ID와 관련도 등급(0~2) | 1-4 | 색인 방식 실험 때 |
| 안전 세트 | 공격 문항 60~100개 + 짝을 이루는 정상 문항 | 공격 문장을 넣은 세계 조각 + 원래 과제 | 1-5 | 공격 유형이 늘 때마다(레드팀) |

### 4-3. 종단 과제 세트 구성
- 규모: 약 400문항. test 분할에 독립 묶음(cluster) 100개 이상.
  - 근거(추정): 정답률 약 80%에서 독립 묶음 100개면 95% 신뢰구간 반폭이 약 ±8%p다. 짝지은 비교는 이보다 좁아 설정 간 약 10%p 차이를 구분하는 최소 규모로 본다. v0 test는 묶음 약 5개라 불안정했다(ADR-0010 §2).

| 쓰기(초안·발송·일정 생성·변경·취소) | 40 | 1-1, 1-3 | 최종 상태 + 인자 필드 채점 |

| 리마인더 | 30 | 1-1 | 상대 시각·시간대, 요청 없을 때 미생성 |
| 메일·캘린더 불일치 | 30 | 1-1, 1-2 | |
| 답할 수 없는 질문 | 30 | 1-2 | 기권·환각·과잉 거절 |
| 커넥터 오류(파생) | 30~60 | 1-6 | 기존 문항에 FaultPlan 적용 |
| 표현 변형(파생) | 30~60 | 1-6 | 기존 문항 30개 × 변형 2~3개 |

- 파생 문항은 원래 문항과 같은 묶음에 넣어 분할이 섞이지 않게 한다.
- 유형별 30~50문항의 신뢰구간은 약 ±12~14%p로 넓다. 유형별 수치는 경향 확인용으로 쓰고, 설정 간 우열은 전체 짝지은 비교로 판단한다.
- v0처럼 정답은 코드가 계산하고, 사람은 문항 자연스러움과 정답 타당성만 검수한다.

### 4-4. 실험별로 돌리는 세트
| 실험 | 세트 |
| --- | --- |
| RAG 방식·구성 요소 | 검색 세트 + 종단 과제 세트의 메일 내용 질의 + 스모크 |
| Agent 패턴, 모델 비교 | 종단 과제 세트 전체 + 안전 세트 |
| 맥락 구성, 오래된 턴 요약 | 종단 과제 세트의 다중 턴 + 스모크 |
| 가드레일 ablation | 안전 세트 + 스모크 |
| 프롬프트·모델 변경 회귀 | 스모크(CI) |
| STT 모델 선정, 계단식 vs Realtime | 음성 세트 + 연결된 종단 과제 |

## 5. 기반 작업
1. 실사용 경로 평가: 평가 러너가 `runflow`를 직접 실행(다중 턴, 쓰기 승인, 색인 검색, 문서, 리마인더).
2. 평가 데이터 v1: 메일·캘린더 불일치, 다중 턴, 쓰기, 인젝션, 문서, 리마인더, 커넥터 오류, 답할 수 없는 질문, 표현 변형 문항. 천장 효과 해소.
3. 데이터 검수: 사람 검수, 검수자 간 일치도, test 봉인.
4. 회귀 평가 자동화: 프롬프트·모델 변경 시 CI에서 작은 평가 묶음 실행.
5. 운영 단계: 온라인 평가(사용자 피드백, 실패 사례, 오프라인 점수와의 상관).

## 6. 평가 단계 실행 계획 (평가 세션 제안, 2026-11-15, 승인 전·보류)
> 데스크톱·음성 설계를 먼저 하기로 해 보류한다. 다시 시작할 때 이 순서로 진행한다.

- 기반 작업: ① 실사용 경로 평가(ADR-0023) → ② 평가 스위트 v1·Sim 세계 v1 설계(ADR)와 생성기 → ③ 사람 검수·test 봉인 → ④ CI 스모크 회귀
- 메타 평가: Judge 검증 세트로 kappa 측정, 라벨 일치도 측정
- 비교 실험: RAG → Agent 패턴 → 모델 → 맥락 N·K·M과 오래된 턴 요약 → 가드레일 ablation

### 첫 작업(ADR-0023 실사용 경로 평가)에 정할 내용
- 평가 대상 `runflow_v0`: 에피소드마다 테스트 DB에 워크스페이스를 새로 만들고, 포크한 Sim 세계를 resolver로 주입한 뒤 고정 시계로 `advance_run`을 직접 구동한다(통합 테스트 `runflow_support.py`와 같은 방식).
- 승인: 과제에 시뮬레이션 사용자의 결정(기본 승인, 과제가 지정하면 거절)을 둔다. `approval_violations`는 DB의 승인·실행 기록에서 계산한다(지금은 0 고정).
- 다중 턴: 과제의 `turns`를 같은 대화의 연속 run으로 실행한다.
- 구조화된 답: 평가 때만 `submit_answer` 도구와 프롬프트 한 단락을 덧붙인다. 모델이 받는 도구 목록이 실사용과 달라지므로 타당성 위협으로 ADR에 적는다.
- Sim 밖 상태: 리마인더처럼 Sim에 없는 상태는 DB에서 읽어 상태 diff에 합친다. 색인 검색은 `FakeEmbedder`로 결정성만 확인하고 실제 임베딩은 검색 세트 작업에서 다룬다.
- 확인: `ScriptedLLM` 결정성 테스트, `scripts/check.sh`, v0 dev 36문항 luna(low) 1회로 기존 점수와 비교(약 0.04~0.05달러, 사전 측정 후 승인받고 실행).
