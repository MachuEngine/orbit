# ADR-0004 — 워크스페이스 격리: 앱 필터 + PostgreSQL RLS, 트랜잭션 범위 설정

- 상태: 제안 (개발자 검토 전)
- 작성일: 2026-11-10
- 근거: `docs/spikes/SPIKE-002-rls-sqlalchemy-pool.md`, 세부 설계 D4-1·D4-4 (비공개, `private-docs/`)

## 배경

다른 사용자의 데이터가 노출되면 성공률과 관계없이 출시를 막아야 한다. 세부 설계 D4-4는 앱 계층의 `workspace_id` 필터와 PostgreSQL 행 단위 보안(RLS)을 함께 쓰는 이중 격리를 후보로 두었다. 이 방식이 SQLAlchemy 연결 풀과 함께 동작하는지 SPIKE-002에서 확인했다.

## 결정

1. **사용자 데이터 테이블은 앱 필터와 RLS로 이중 격리한다.** 모든 사용자 데이터 행에 `workspace_id`를 두고, 앱 쿼리에도 조건을 넣으며, DB도 RLS 정책으로 다시 강제한다 (D4-4 유지).
2. **구현 규칙**

| # | 규칙 | 지키지 않으면 생기는 문제 (스파이크 근거) |
| --- | --- | --- |
| 1 | 워크스페이스는 트랜잭션 시작 직후 `SELECT set_config('app.workspace_id', :id, true)`(트랜잭션 범위)로만 설정한다. 세션 범위 `SET`/`set_config(..., false)`는 금지 | 세션 범위로 설정하고 커밋하면 같은 연결을 쓰는 다음 요청이 이전 사용자의 행을 본다 (R5: 10/10회 40행 노출) |
| 2 | SQLAlchemy 엔진의 `pool_reset_on_return`을 기본값(rollback)으로 둔다. 끄지 않는다 | 트랜잭션을 연 채로 연결이 반환되면 트랜잭션 범위 설정도 다음 요청에 샌다 (R4·R5 변형) |
| 3 | 정책식은 `workspace_id = NULLIF(current_setting('app.workspace_id', true), '')::uuid`로 쓰고 `USING`과 `WITH CHECK`에 모두 적용한다 | `NULLIF`가 없으면 한 번 쓰인 연결에서 설정이 빠졌을 때 `''::uuid` 변환 오류가 난다 (R8) |
| 4 | 애플리케이션 접속 역할은 테이블 소유자가 아니고 `NOBYPASSRLS`다. 마이그레이션은 별도 소유자 역할로 한다. 사용자 데이터 테이블에는 `FORCE ROW LEVEL SECURITY`를 켜고 정책 대상은 `PUBLIC`으로 둔다. 운영 중 전체 데이터에 접근해야 하는 작업은 `BYPASSRLS` 전용 역할을 명시적으로 쓴다 | 소유자는 RLS를 우회한다(R7: 5,110행 전부). FORCE + 대상 한정 정책이면 소유자는 기본 거부로 0행이 되어 관리 작업이 조용히 실패한다(R7) |
| 5 | RLS가 걸린 벡터 검색 쿼리에는 `hnsw.iterative_scan`을 트랜잭션 범위로 켠다(`relaxed_order` 또는 `strict_order`, 선택은 RAG 실험으로) | HNSW 후보 40개를 먼저 뽑고 RLS로 거르므로 작은 워크스페이스는 결과가 0건이 될 수 있다 (R9: 10/10회 0행) |

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 앱 필터만 사용 | 단순하다 | 쿼리 하나에서 필터가 빠지면 바로 노출된다. 스파이크에서 RLS가 이 누락을 막는 것을 확인했다 (R2) |
| 워크스페이스별 스키마·DB 분리 | 격리가 가장 강하다 | 개인 사용자 수만큼 스키마가 생겨 관리할 수 없다 (D4-4). 기업 테넌트 확장 시 재검토 |
| SQLAlchemy 이벤트 훅으로 매 체크아웃마다 세션 범위 `SET` | 설정을 잊을 일이 줄어든다 | 세션 범위 설정이 커밋 후 남는 문제(R5)를 그대로 가진다. 트랜잭션 범위 설정을 공통 헬퍼로 강제하는 편이 안전하다 |

## 결과

- 장점: 앱 코드에서 필터가 빠지거나 설정을 잊어도 DB가 0행으로 막는다(R2, R6 혼합 대조군). 동기·비동기 SQLAlchemy 모두 같은 방식으로 동작한다.
- 비용: DB 역할이 둘 이상 필요하고, 모든 요청이 트랜잭션 시작 시 설정 쿼리를 한 번 더 실행한다. 벡터 검색은 iterative scan 비용이 든다.

## 미결정·후속 확인

- 트랜잭션 범위 설정을 강제할 공통 헬퍼(요청 단위 세션 팩토리 등)의 형태는 백엔드 골격 단계에서 정한다.
- 워크스페이스 크기별 벡터 검색 recall·지연과 `iterative_scan` 설정값은 RAG 실험에서 측정한다.
- 운영 규모에서 RLS 정책이 쿼리 계획에 주는 영향은 측정하지 않았다.

## 재검토 트리거

- 기업 테넌트처럼 워크스페이스 하나의 데이터가 매우 커지거나 규제상 물리적 분리가 필요할 때
- RLS 때문에 검색 지연이나 recall이 목표를 넘을 때
- PostgreSQL·pgvector 업그레이드로 RLS·iterative scan 동작이 바뀔 때
