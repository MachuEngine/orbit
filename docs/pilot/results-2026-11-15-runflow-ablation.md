# 실사용 경로 원인 확인 ablation (2026-11-15)

근거: ADR-0023 §10. `runflow_v0`가 `assistant_v0`보다 낮게 나온 원인 후보(프롬프트 [사실 확인] 구역, 추론 항목 되돌리기)를 하나씩 켜서 확인했다. 합성 데이터(평가 데이터 v0)만 썼다.

## 설정
- 데이터: `orbit-eval@v0/dev` 36문항(묶음 6개), **반복 3회**(설정마다 108 에피소드), 시드 0
- 모델: `openai/gpt-6-luna`, reasoning effort `low`(ADR-0015). 다섯 실행 모두 응답 모델이 선언 모델과 같았다
- 코드: `2ffa079`. 변형은 `--runflow-variant facts`(`facts-v1`), `--runflow-variant reasoning-rt`
- 실행: 개발자 로컬, 평가 DB `orbit_eval`. 결과 원본은 `runs/ablation-1/`(git 제외)

## 해석
- 두 변형 모두 기준과의 차이가 신뢰구간 안에서 0을 포함한다. 이 데이터로는 [사실 확인] 구역과 추론 항목 되돌리기가 `runflow_v0`의 낮은 점수를 설명한다고 말할 수 없다. `assistant_v0`와의 차이(+12.0%p)는 그대로 남는다.
- 차이는 두 유형에 몰려 있고, 실패는 거의 모두 **답 종류를 잘못 고른 형식 실패**다.
  - 일정 변경: 정답 종류는 `event_time`인데 `event`를 낸다. 기준 12/21, `assistant_v0` 6/21.
  - 인물 다음 미팅: 정답 종류는 `event`인데 빈 `event_set`을 낸다. 모든 runflow 설정에서 18/18이 이 실패다. `assistant_v0`도 12/18이 같은 실패다.
- 두 경로는 읽기 도구 구현이 같다. 인물 과제에서 runflow 설정은 거의 모두 `list_calendars` → `list_events`를 한 번만 하고 답을 냈고, `assistant_v0`는 18번 중 14번 이 조회를 두 번 이상 반복했다. 조회를 더 하는 쪽이 일부 맞혔지만, 두 경로 모두 실패의 대부분은 답 종류를 고르는 단계에서 났다. `runflow_v0`의 답 종류 안내는 평가 전용 확장 `eval-answer-v1`의 한 단락(ADR-0023 §6)에 압축돼 있고, `assistant_v0`는 같은 내용을 [답하는 방법] 구역에 항목별로 둔다. **남은 차이의 상당 부분이 실사용 경로의 품질이 아니라 평가용 답 제출 안내의 형식에서 올 수 있다.** 이는 측정 타당성 문제이며, 아직 확인하지 않은 가설이다.
- 남은 다른 후보는 도구 수(14개 대 5개)와 runflow 프롬프트의 긴 [도구 사용]·[대화 맥락] 구역이다.
- luna low는 두 경로 모두 추론을 거의 하지 않는다(에피소드당 4~15토큰). 되돌릴 추론 항목이 적어 `reasoning-rt`의 효과가 작을 수밖에 없다. 비용은 `reasoning-rt`에서 캐시 적중이 늘어 절반 이하로 줄었지만, 원인은 확인하지 않았다.
- `assistant_v0`는 같은 날 반복 1회 두 번에서 83.3%, 72.2%, 반복 3회에서 70.4%였다. 반복 1회 결과로 비교하면 안 된다는 점을 다시 확인했다.

## 다음 확인
- 답 제출 안내를 `assistant_v0`의 [답하는 방법] 항목 형식으로 바꾼 `eval-answer-v2`로 같은 조건(반복 3회)을 돌려, 남은 차이가 측정 방식에서 오는지 확인한다.
- 인물 다음 미팅은 두 경로 모두 약하다. 문항 문구("다음 미팅 일정")가 목록 질문으로 읽히는지 평가 데이터 v1 설계 때 함께 검토한다.
