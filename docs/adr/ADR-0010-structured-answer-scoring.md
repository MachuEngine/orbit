# ADR-0010 — 평가 채점은 구조화된 답을 기준으로 하고, 분할은 근거 아티팩트 단위로 한다

- 상태: 채택 (2026-11-11, 개발자가 단계별 진행을 위임한 범위에서 메인 세션이 결정. 이의가 있으면 3단계 PR 리뷰 때 바꾼다)
- 작성일: 2026-11-11
- 근거: ADR-0009(평가 기반 v0) §2·§3을 고친다. 3단계-B·C 코드 리뷰 지적, 세부 설계 D1-3·D2-3·D8-1 (비공개, `private-docs/`)

## 배경

ADR-0009는 응답 텍스트에 정답 표현(`answer_facts`)이 들어 있는지로 채점하고, 금지 표현(`must_not_contain`)이 있으면 실패로 정했다. 3단계-B 데이터셋과 3단계-C 러너를 리뷰한 결과, 텍스트 부분 일치로는 다음 문제를 막을 수 없었다.

| 문제 | 예 | 영향 |
| --- | --- | --- |
| 단정과 설명을 구분하지 못한다 | 빈 시간 질문에 "9시~10시는 회의가 있어 안 되고 15시 이후 가능"이라 답하면 정답 "10시"가 들어 있어 통과 | 오답이 성공으로 집계된다. 설명이 많은 모델일수록 유리하다 |
| 부정 언급을 실패로 본다 | "취소된 X는 제외했다"가 금지어 X 때문에 실패 | 도구 결과를 충실히 설명하는 모델·패턴이 불리해진다 |
| 사실이 일정에 묶이지 않는다 | 두 일정의 시각을 바꿔 말해도 제목·시각이 모두 있으면 통과. 인접 일정의 종료 시각이 다음 일정 시작 정답을 채운다 | 일정 목록 과제가 느슨하게 채점된다 |
| 숫자 경계 | "10시"가 "10시 30분"에 일치 | 숫자 경계 규칙으로 일부만 막을 수 있다 |

또 dev와 test가 시나리오는 달라도 같은 일정을 정답 근거로 공유했고, 정답이 완전히 같은 과제가 여러 개 있었다. 이러면 dev에서 조정한 결과가 test 정답을 건드리고, 과제를 독립 표본으로 가정한 bootstrap 신뢰구간이 실제보다 좁게 나온다.

## 결정

### 1. 구조화된 답이 성공 판정의 기준이다
- 과제 정답(`gold`)에 `expected_answer`를 둔다. 값이 있으면 성공 판정은 평가 대상이 낸 구조화된 답(`EpisodeOutput.structured`)과 이것을 비교해서 한다.
- `expected_answer.kind`와 비교 규칙 (v0)

  | kind | 형식 | 일치 조건 | 쓰는 과제 유형 |
  | --- | --- | --- | --- |
  | `event_set` | `{"kind": "event_set", "events": [{"calendar_id", "event_id"}, ...]}` | 순서 무관 집합이 같다 | 하루 일정, 취소 제외, 프로젝트 주간 |
  | `event` | `{"kind": "event", "event": {"calendar_id", "event_id"}}` | 같은 일정 | 특정 인물의 다음 미팅 |
  | `event_time` | `{"kind": "event_time", "event": {...}, "start": ISO 8601}` | 같은 일정이고 시작 시각이 같은 순간 | 변경된 일정의 현재 시각 |
  | `time_slot` | `{"kind": "time_slot", "start": ISO 8601}` | 같은 순간 | 빈 시간 |

  시각은 시간대 오프셋이 있는 ISO 8601이어야 하고 순간(instant)으로 비교한다. 오프셋이 없으면 형식 오류다.
- 실패 유형을 나눈다. 구조화된 답이 없거나 형식이 틀리면 `answer_format`, 형식은 맞지만 값이 다르면 `wrong_answer`다. 형식 준수 실패와 오답을 따로 집계해 패턴 비교에서 원인을 구분한다.
- 텍스트 사실(`answer_facts`)은 보조 지표다. `expected_answer`가 있는 과제에서는 성공 판정에 쓰지 않고 `text_fact_recall`(충족한 사실 비율)로만 기록한다. `expected_answer`가 없는 과제에서만 ADR-0009의 텍스트 채점으로 판정한다.
- `must_not_contain`은 하드 실패로 남기되, 취소 일정 제외처럼 구조화된 답으로 판정할 수 있는 경우에는 쓰지 않는다. v0 데이터는 이 필드를 비워 둔다.
- 일정 식별자: 모델은 작업 집합 핸들(E1, M3)로만 일정을 가리킨다(D8-1). 핸들을 제공자 ID로 바꾸는 일은 평가 대상의 코드가 한다. 러너는 Sim의 ID로 비교한다.

### 2. 분할과 중복 제거
- 각 과제는 정답 계산에 쓴 근거 아티팩트(일정 ID, 메일 ID)를 `tags`의 `ref_event:`·`ref_message:`로 모두 기록한다. 빈 시간 과제는 그날 업무 시간 안의 모든 일정을, 취소 제외 과제는 취소 일정도 기록한다.
- dev와 test는 근거 아티팩트를 공유하지 않는다. 근거를 공유하는 과제들을 하나의 묶음(연결 요소)으로 보고 묶음 단위로 분할한다.
- 정답 지문(과제 유형과 `expected_answer`의 정규화 JSON)이 같은 과제는 하나만 남긴다.
- 생성기 테스트가 이 두 성질을 검사한다.

### 3. 기타 정정
- ADR-0009 §2의 `expected_state_diff`는 코드와 같게 `expected_changes`로 부른다. `None`은 검사하지 않음, `[]`는 변화가 없어야 함이다.
- test 분할 봉인의 한계: 공개 저장소라 `tasks.jsonl`의 test 정답을 누구나 읽을 수 있다. 봉인은 러너가 확인 플래그 없이 test를 실행하지 않는 수준이며, 실험 기록에 test 실행 횟수를 남겨 과적합 위험을 드러낸다.
- v0 과제의 `required_tool_calls`는 비운다. 메일만으로 답을 찾는 접근을 궤적 규칙으로 실패시키지 않기 위해서다. 금지 도구(`forbidden_tools`)는 유지한다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 텍스트 매칭 규칙을 더 정교하게(숫자 경계, 부정 인식) | 경계 규칙은 3단계-C에서 넣었지만, 단정과 설명을 구분하는 문제와 사실을 일정에 묶는 문제는 글자 규칙으로 풀 수 없다 |
| 질문에 출력 형식을 지시("마지막 줄에 HH:MM으로") | 자연스러운 사용자 질문이 아니게 되고, 텍스트 파싱 문제가 그대로 남는다 |
| LLM Judge | 채점이 다른 모델의 해석에 의존한다. v0에서 제외했다(D2-4). 응답 문장 품질을 따로 볼 때 다시 검토한다 |
| 일정 제목·시각을 구조화된 답으로 받기 | 제목 표기 차이 정규화가 다시 필요하다. ID 비교가 가장 엄격하고 결정적이다 |

## 결과
- 평가 대상(3단계-D)은 최종 답을 구조화된 형태로 내야 한다. 모델에 답 제출 도구를 주고, 평가 대상 코드가 핸들을 ID로 바꿔 `EpisodeOutput.structured`에 담는다.
- 응답 문장 품질은 이 채점으로 측정되지 않는다. `text_fact_recall`은 참고 지표로만 쓴다.
- 데이터셋 생성기(3단계-B)와 러너(3단계-C)를 이 결정에 맞게 고친 뒤 통합한다.
