# 하네스 공통 작업 규칙

> 이 파일은 하네스 템플릿(claude-harness-template)이 관리한다. 프로젝트에서 직접 고치지 않는다.
> 바꿀 내용이 있으면 아래 "하네스 개선 절차"를 따른다. 프로젝트 고유 규칙은 `CLAUDE.md`에 쓴다.

## 역할 분담
| 역할 | 담당 | 하는 일 |
| --- | --- | --- |
| 지휘 | 메인 세션 (`claude-opus-5-5`) | 요구사항 분석, 설계·기획, ADR 작성, 작업 명세 작성, 위임, 리뷰 결과 판단, 최종 보고 |
| 구현 | `implementer` 서브에이전트 (`claude-sonnet-5-5`) | 작업 명세대로 코드·테스트 작성, 리뷰 지적 수정 |
| 검토 | `code-reviewer` 서브에이전트 (`claude-sonnet-5-5`) | 변경을 읽기 전용으로 검토하고 지적 사항 보고 |

- 메인 세션은 제품 코드와 테스트를 직접 고치지 않는다. 직접 고치는 대상은 문서, `CLAUDE.md`, `.claude/`, `scripts/`, `.github/` 같은 문서·하네스 파일뿐이다.
- 서브에이전트는 다른 서브에이전트를 부르지 않는다. 위임은 메인 세션만 한다.

## 작업 순서
1. **메인**: 요구사항과 관련 설계 문서·ADR을 읽는다.
2. **메인**: 수정 범위, 대안, 예상 영향, 검증 방법을 제안하고 개발자 승인을 받는다. 구조에 영향을 주면 ADR을 먼저 쓴다.
3. **메인**: 아래 작업 명세를 작성해 `implementer`에 위임한다.
   - 작업 목적 / 범위(변경 가능·금지) / 완료 조건 / 설계 근거(ADR 등) / 검증 명령
4. **implementer**: 구현하고 `scripts/check.sh`를 실행한 뒤 보고한다. 설계 변경이 필요하면 멈추고 메인에 돌려준다.
5. **메인**: 작업 명세와 implementer 보고서를 `code-reviewer`에 넘긴다.
6. **메인**: 지적 사항을 판단한다. 수정할 항목만 골라 `implementer`에 다시 위임하고, 수정 후 다시 검토받는다. 수정·재검토는 최대 2회까지 하고, 그래도 남으면 개발자에게 판단을 요청한다.
7. **메인**: `git diff`와 `scripts/check.sh` 결과를 직접 확인한 뒤 결과, 미검증 항목, 위험, 새로 필요한 결정을 보고한다.

## 결정 상태
- 기술 선택은 `채택` / `실험 중` / `보류` / `기각` 중 하나로 표시한다. 검증하지 않은 기술을 채택된 것처럼 쓰지 않는다.
- 구조에 영향을 주는 선택은 ADR로 남긴다.

## 공통 금지·주의
- 비밀키, 토큰, 실제 사용자 데이터를 코드·로그·테스트 픽스처에 남기지 않는다.
- 측정하지 않은 개선 효과를 사실처럼 쓰지 않는다.
- 테스트를 지우거나 검사 규칙을 약하게 바꿔서 실패를 숨기지 않는다.
- 강제 푸시, 대량 삭제, 프로덕션 배포, 실제 외부 발송은 따로 승인을 받는다.
- `private-docs/`는 git에서 제외한 비공개 문서다. 내용을 공개 문서·커밋 메시지·PR에 그대로 옮기지 않는다.

## 완료 보고
변경 사항 / 선택 이유 / 실행한 검사와 결과 / 실패·미검증 사항 / ADR 필요 여부

## 하네스 파일 소유 구분
| 구분 | 파일 | 수정 위치 |
| --- | --- | --- |
| 템플릿 소유 | `.claude/harness/`, `.claude/agents/`, `.claude/hooks/`, `scripts/harness-check.sh`, `tests/harness/`, `.github/pull_request_template.md` (정확한 목록: `.claude/harness/owned-files.txt`) | 하네스 템플릿 저장소에서만 고친다 |
| 병합 | `.claude/settings.json`, `.gitignore`, `.github/workflows/ci.yml` | 프로젝트에서 고쳐도 된다. `copier update`가 템플릿 변경과 병합한다 |
| 프로젝트 소유 | `CLAUDE.md`, `scripts/check.sh`, `.env.example` | 프로젝트에서 고친다. 템플릿이 다시 덮어쓰지 않는다 |
| 관리 파일 | `.copier-answers.yml` | 직접 고치지 않는다 |

## 하네스 개선 절차
하네스 개선은 실제 문제가 재현된 뒤에 한다. 같은 유형의 문제가 2회 이상 반복되거나, 보안·데이터 손상 위험이 1회라도 발견되면 검토한다.

1. 문제가 **이 프로젝트에만 해당**하면 프로젝트 소유 파일(`CLAUDE.md`, `scripts/check.sh`)이나 병합 파일에서 해결한다.
2. **다른 프로젝트에도 해당**하면 템플릿 소유 파일의 문제로 본다. 프로젝트 안의 복사본을 고치지 말고 메인 세션이 개발자에게 다음을 제안한다.
   - 하네스 템플릿 저장소에서 수정하고 템플릿 테스트를 실행한다.
   - 템플릿 저장소의 `docs/hir/`에 HIR(하네스 개선 기록)을 남기고 `CHANGELOG.md`를 갱신한 뒤 버전 태그를 붙인다.
   - 각 프로젝트에서 작업 트리를 커밋한 뒤 `copier update`를 실행하고 `scripts/check.sh`로 확인한다.
3. 급해서 프로젝트 복사본을 먼저 고쳤다면 같은 작업 안에서 템플릿 저장소에도 반영한다. 반영하지 않으면 다음 `copier update`에서 충돌이 쌓이고 다른 프로젝트가 개선을 받지 못한다.

### 템플릿 반영 알림
템플릿 소유 파일을 프로젝트에서 고치면 두 곳에서 알린다.
- **수정 직후**: Claude가 Edit·Write로 고치면 `template_drift_notice.py` 훅이 사용자에게 알림을 띄우고, 메인 세션에 템플릿 반영을 제안하라고 전달한다. 같은 세션에서 같은 파일은 한 번만 알린다.
- **검사 실행 시**: `scripts/check.sh`가 마지막 커밋 이후 바뀐 템플릿 소유 파일을 경고로 보여 준다. 에디터나 Bash로 직접 고친 경우도 잡는다. `copier update`로 바뀐 경우(`.copier-answers.yml`도 함께 바뀐 경우)는 경고하지 않는다.

알림을 받으면 메인 세션은 그 변경이 범용인지 프로젝트 전용인지 판단해 개발자에게 위 절차 중 하나를 제안한다.
