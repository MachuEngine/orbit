# ADR-0037 — GraphRAG local 메일 순위에 reranker 적용 (R03b)

- 상태: 채택 (2026-11-22). dev·test 실행을 마쳤다. 결과는 [rag-architecture-v1](../eval/rag-architecture-v1.md)의 R03b 절에 있다. 평가 경로 전용 구성이며 제품 기준 설정은 바꾸지 않는다.
- 작성일: 2026-11-22
- 근거: ADR-0036(RAG 아키텍처 비교, R03), ADR-0010(짝 비교·봉인), ADR-0006(RLS 밖 저장소), ADR-0019(메일 색인)

## 문제

R03에서 GraphRAG(`A4`)는 test 성공률 0.368로 Agentic RAG(기준, `A2`)보다 낮은 쪽으로 기울었다(−0.115 [−0.233, 0.0]). context recall은 0.374였고, 문맥 상한 6,000자에 닿은 episode가 97%였다.

dev 진단(읽기 전용 스크립트, 유료 LLM 호출 없음)에서 원인이 검색 범위보다 **메일 순위**에 있다는 것을 확인했다.

- local 경로는 시드 개체에서 2홉까지 관계를 따라간다. 이렇게 닿는 메일은 계정 메일 약 400통 중 382~392통이다. 그래프가 후보를 거의 거르지 못한다.
- 현재 순위는 (가장 가까운 홉, 그 홉의 관계 수 내림차순, 제공자 ID)다. 질문과 메일이 얼마나 관련 있는지는 순위에 쓰지 않는다.
- 상위 12통(`LOCAL_MAX_MAILS`)을 고른 뒤 6,000자 상한까지 채우면 실제로 4~10통이 들어간다. 정답 근거 메일이 순위 뒤쪽에 있으면 잘린다.

dev 정답 근거 메일 99통(답할 수 없음 제외 48문항)의 순위 비교:

| 순위 방식 | 상위 5 | 상위 12 | 중앙 순위(0부터) | 근거가 모두 상위 12에 든 문항 |
| --- | --- | --- | --- | --- |
| 현재(홉 → 관계 수) | 34 | 60 | 8 | 22/48 |
| 질문-청크 임베딩 거리 | 51 | 71 | 4 | 23/48 |
| 홉 먼저, 같은 홉 안에서 임베딩 거리 | 61 | 76 | 3 | 27/48 |
| Hybrid 검색 점수(RRF) | 53 | 70 | 4 | 26/48 |
| 임베딩 상위 40통 → reranker | **79** | **86** | **1** | **35/48** |
| 참고: 그래프 없이 전체 메일 임베딩 거리 | 51 | 71 | 4 | 23/48 |

- 유형별로 보면 다중 홉은 근거가 모두 상위 12에 든 문항이 1/16에서 7/16으로, 집계는 9/16에서 12/16으로 늘었다.
- 집계 유형에서는 "홉 먼저 + 임베딩 거리"가 14/16으로 reranker(12/16)보다 높았다. 전체 기준으로는 reranker가 가장 높다.
- 이 표는 **순위만** 잰 결과다. 답 성공률이 오르는지는 재지 않았다.
- 임베딩 거리만 쓴 순위는 그래프가 있을 때와 없을 때 결과가 같았다. 이 결과만으로는 그래프가 순위에 기여하는지 알 수 없다.

## 결정

### 1. 새 구성 두 개를 추가한다. R03 구성과 결과는 바꾸지 않는다

| 설정 ID | 사용자용 이름 | 흐름 |
| --- | --- | --- |
| `A4R` | GraphRAG + reranker | `A4`와 같다. local 경로의 메일 순위만 아래 2단계 순위로 바꾼다 |
| `A4RN` | reranker 대조군(그래프 없음) | 경로 선택 없음. 계정 전체 메일을 후보로 아래 2단계 순위 → 상위 12통 원문 → 답 생성. 관계 줄 없음 |

- `A4RN`은 그래프가 후보 선택과 관계 줄로 기여하는 몫을 떼어 보려고 둔다. `A4R`과 `A4RN`은 그래프 후보, 관계 줄, 경로 선택(global 포함)이 다르다. 그래서 둘의 차이를 그래프 하나의 효과로 단정하지 않는다.
- `A4`, R03 결과 파일, 설정 지문은 그대로 둔다. `A4`의 지문 골든 테스트는 바뀌면 안 된다.

### 2. local 메일 순위 (A4R, A4RN 공통)

1. **후보**: `A4R`은 `plan_local`이 2홉 안에서 닿은 모든 메일이다(현재 상위 12통 자르기 전 목록). `A4RN`은 그 계정에서 색인된 모든 메일이다.
2. **1단계(임베딩 거리)**: 메일마다 질문 임베딩과 그 메일 청크 임베딩 사이의 최소 코사인 거리를 구한다. 거리가 작은 순으로 상위 `GRAPH_RERANK_CANDIDATES = 40`통을 남긴다. 같은 거리면 제공자 ID 순이다. 청크가 없는 메일은 맨 뒤로 보낸다.
   - SQL은 `chunk`와 `source_item`을 조인하고 두 테이블 모두 같은 SQL 안에서 `workspace_id`로 거른다(D4-1, D4-4).
3. **2단계(reranker)**: 40통을 Advanced RAG(`A1`)와 같은 고정 reranker(`BAAI/bge-reranker-v2-m3`, revision·max_length 768·device cpu 동일)로 다시 정렬한다. passage는 `A1`과 같은 `rerank_passage`(제목 + 본문)를 쓴다. 점수가 같으면 1단계 순서를 따른다.
4. **자르기**: 상위 `LOCAL_MAX_MAILS = 12`통을 이 순서대로 넘긴다. 문맥 상한 6,000자와 채우는 방식은 `A4`와 같다.
5. **관계 줄(A4R만)**: `relation_lines`는 새 메일 순서를 따른다. 관계 줄이 상한의 글자를 먼저 차지하는 방식도 `A4`와 같다.

경로 선택 프롬프트, 시드 개체 찾기, `HOPS = 2`, global 경로, 답 프롬프트, 문맥 상한은 `A4`와 같다. `A4R`이 global을 고르면 `A4`와 똑같이 동작한다.

### 3. 값 선택과 누설 관리

- `GRAPH_RERANK_CANDIDATES = 40`은 dev 순위 진단 한 번으로 정했다. test를 보고 고치지 않는다.
- reranker를 고른 근거도 dev 진단이다. test는 봉인된 상태로 한 번만 실행한다(ADR-0010).
- 봉인 세트 `eval/datasets/orbit-eval/rag-v1/`는 바꾸지 않는다.

### 4. 설정 지문

`A4R`, `A4RN`의 지문에는 다음을 넣는다.

- `A4`와 같은 그래프 항목(`A4RN`은 그래프를 쓰지 않으므로 그래프 항목 대신 `graph: none`).
- `local_rank_version`(새 버전 상수), `graph_rerank_candidates`, `local_max_mails`.
- reranker의 `model_id`, `revision`, `max_length`, `device`.
- `A4R`의 프롬프트 버전 문자열에는 순위 버전을 붙여 `A4` 결과와 섞이지 않게 한다.

### 5. step 상한

- 2단계 reranker 입력은 후보 40통을 Connector로 읽는다. `step_definition`(`llm_calls+connector_calls/v1`)에 따라 이 읽기도 step으로 센다. Advanced RAG(`A1`)가 후보 20통을 읽을 때와 같은 방식이다.
- 이렇게 세면 `A4R` local 경로는 경로 선택 1 + 후보 읽기 40 + 문맥 메일 읽기 최대 12 + 답 생성 1로, 최대 54 step을 쓴다. R03의 상한 `max_steps = 50`을 넘는다.
- 그래서 R03b의 두 구성은 `--max-steps 100`으로 실행한다. 두 구성은 호출 수가 고정된 흐름이라 이 상한은 실패 여부만 바꾸고, 모델이 무엇을 할지는 바꾸지 않는다. 값은 설정 지문의 `budget.max_steps`에 들어간다.
- step 정의와 시간 상한(120초), 토큰 상한은 R03과 같다.

### 6. 실행 기록

episode마다 다음을 남긴다. 모두 ID와 숫자만 남기고 본문은 남기지 않는다(ADR-0006).

- 1단계 후보 수, 2단계 입력 수, 최종 후보 메일 ID 목록(`candidate_message_ids`).
- reranker 처리 시간(ms).
- `A4R`은 기존 `A4` 진단 항목(시드 수, 경로, 빈 문맥 이유)을 그대로 남긴다.

## 지표와 통계

R03(ADR-0036)과 같은 지표, 같은 계산을 쓴다.

- **주 지표**: task success. 짝 차이 두 개를 cluster bootstrap 95% CI(10,000회, seed 0)로 낸다.
  - `A4R − A2`(Agentic RAG 기준)
  - `A4R − A4`(원래 GraphRAG 대비 순위 변경 효과)
  - 참고로 `A4RN − A2`, `A4R − A4RN`도 낸다.
- 유형별 성공률과 짝 차이(탐색 결과로 표시), pass³.
- **진단 지표**: context recall(넣은 메일의 출처로 역추적), 근거 인용 정밀도·재현율, groundedness Judge(repeat 0), 경로 분포(`A4R`), 효율(LLM 호출 수, 토큰, 비용, 지연 p50·p95), reranker 처리 시간.
- **정답 비교 Judge**: R03과 같은 Judge·같은 프롬프트로 구성마다 표본 100건을 채점해 코드 채점 일치율을 낸다.
- CI가 0을 포함하면 차이를 확정하지 않는다고 쓴다.

## 예상 비용

R03 실측을 구성 하나 단위로 나눠 추정했다(생성 `openai/gpt-6-luna`, Judge `google/gemini-3.6-flash`).

| 항목 | 구성 하나 | 두 구성 |
| --- | --- | --- |
| dev 실행(64문항 × 3) | 약 0.10 | 약 0.20 |
| dev groundedness Judge(repeat 0) | 약 0.37 | 약 0.74 |
| test 실행(96문항 × 3) | 약 0.13 | 약 0.26 |
| test groundedness Judge(repeat 0) | 약 0.56 | 약 1.12 |
| 정답 비교 Judge(표본 100건) | 약 0.12 | 약 0.24 |
| reranker | API 비용 없음(CPU 시간만) | |
| **합계** | | **약 2.6** |

- **비용 상한 3달러(제안)**. ADR-0036 누적 약 8.38달러와 합치면 약 11.4달러이고, 프로젝트 총예산(약 35달러) 안이다.
- dev 실행과 test 실행 전에 각각 다시 추정해 보고하고 승인받는다. 누적 비용이 상한을 넘으면 멈춘다. 후보와 지표는 줄이지 않는다.

## 대안

- **홉 먼저 + 임베딩 거리**: reranker 없이 구현이 간단하다. dev 순위 진단에서 집계 유형은 가장 좋았지만 전체로는 reranker보다 낮았다(상위 5에 든 근거 61 대 79). 채택하지 않는다.
- **Hybrid 검색 점수로 정렬**: 상위 5에 든 근거 53으로 reranker보다 낮았다.
- **HOPS를 1로 줄이기**: 후보를 줄이지만 다중 홉 근거를 놓칠 수 있고, 순위 문제는 그대로 남는다.
- **추출 프롬프트 개선(관계 recall 향상)**: 원인 후보지만 그래프를 다시 구축해야 하고 test 누설 관리가 어렵다. 이번 범위에서 다루지 않는다.

## 결과와 위험

- 결과 문서에는 R03b로 따로 적고, R03 표의 `A4` 값은 바꾸지 않는다.
- `A4R`이 오르더라도 그 효과는 "GraphRAG local에 reranker를 붙인 것"이다. GraphRAG 일반의 성능으로 일반화하지 않는다.
- reranker가 CPU에서 질문마다 40통을 처리하므로 지연이 늘어난다. 실측해서 보고한다.
- `A4RN`이 `A4R`과 비슷하거나 높으면, 이 평가에서 그래프가 순위 단계에 주는 이득이 작다는 근거가 된다. 이 경우도 그대로 보고한다.
