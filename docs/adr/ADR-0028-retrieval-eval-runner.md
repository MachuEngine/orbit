# ADR-0028 — 검색 평가 실행기와 평가용 색인 재사용

- 상태: 채택 (2026-11-16 개발자 결정: 메일만 색인, 문서 정답 질의는 메일 검색 지표에서 제외)
- 작성일: 2026-11-16
- 근거: ADR-0019(메일 색인·검색), ADR-0020(문서 읽기, 문서 색인 보류), ADR-0026 §3·§6(검색용 메일함·검색 세트), ADR-0010(분할·봉인), 평가 계획 §1-4

## 문제
검색 세트(질의 133개, test 78개 봉인)와 지표 함수는 있지만, 질의를 실제 검색 방식에 넣어 순위를 얻는 실행기가 없다. RAG 비교(평가 보류 목록 첫 번째)를 하려면 다음을 정해야 한다.
- 200·1,000·5,000통 메일함을 어떻게 색인하고, 실험마다 다시 임베딩하지 않으려면 무엇을 재사용하는가.
- 평가용 색인이 운영 색인과 같은 동작을 대표하게 하려면 어떤 조건이 필요한가.
- 문서가 정답인 질의를 어떻게 다루는가. 검색 세트의 등급 2 정답 180개 중 60개가 문서인데, 운영은 문서를 색인하지 않는다(ADR-0020 보류).

## 결정

### 1. 운영 색인 코드를 그대로 쓴다
- 평가용 색인은 운영과 같은 경로로 만든다: Sim 메일 커넥터 → `mailindex.sync`(청크·Kiwi 토큰화·임베딩·저장) → `mailindex.search`. 평가 전용 색인 코드를 따로 만들지 않는다.
- 다른 점은 설정값뿐이다. 운영의 첫 동기화 상한(`FIRST_SYNC_MAX_MAILS` 2,000통)은 5,000통 메일함을 다 담지 못하므로 평가 실행기는 상한을 인자로 덮어쓴다. 상한 값은 결과 메타데이터에 남긴다.
- 메일함 세 개는 각각 별도 계정·연결로 색인한다(계정마다 ID가 다르다). 부분집합 관계는 이미 세계에 있으므로 따로 만들지 않는다.

### 2. 재사용 단위: 색인 지문
- 색인 지문 = 세계 `world.json` sha256 + 계정 + 청크 설정(크기·겹침·청크 상한) + 토큰화 설정(Kiwi 버전·품사 규칙) + 임베딩 모델 ID + `mailindex` 색인 코드 버전 상수.
- 평가 전용 DB(`orbit_eval`, 운영·개발 DB와 분리)에 지문별 워크스페이스로 색인을 둔다. 실행기는 지문이 같은 색인이 있으면 재사용하고, 없으면 만든다. 지문이 다른 색인은 지우지 않는다(비교 실험에서 두 설정을 오가므로).
- 임베딩 캐시: `(임베딩 모델 ID, 청크 텍스트 sha256) → 벡터`를 git에서 제외한 로컬 파일(`runs/embed-cache/`)에 둔다. DB를 비우거나 청크·토큰 설정만 바꿀 때 같은 청크는 다시 임베딩하지 않는다. 캐시 적중·미적중 수를 결과에 남긴다.
- 운영 색인은 지금처럼 동기화 작업이 증분으로 만든다. 이 결정은 운영 동작을 바꾸지 않는다.

### 3. 비교 대상(방식)
같은 질의·같은 메일함에서 메일 단위 순위(상위 20)를 얻는다.
| 이름 | 방식 |
| --- | --- |
| `gmail_search` (기준선) | 커넥터 `search_messages`에 질의 문장을 그대로 넣는다(지금 실사용 경로가 쓰는 Gmail 검색) |
| `keyword` | 운영 SQL의 키워드 쪽만(Kiwi 토큰 + `ts_rank`) |
| `vector` | 운영 SQL의 벡터 쪽만 |
| `hybrid` | 운영 SQL 그대로(RRF k=60) |
| `bm25` | 같은 Kiwi 토큰으로 실행기 안에서 BM25 계산(ADR-0019: `ts_rank`는 BM25가 아니다). 메일함마다 따로 계산한다 |
- 운영 SQL의 한쪽만 쓰는 방식은 `mailindex.search`에 이미 있는 분기(질의 토큰 없음·벡터 없음)를 인자로 고르게 하는 작은 확장으로 만든다.
- 지표: recall@5·10·20(등급 2, 등급 1 이상), MRR, nDCG@10. 질의 형태별(키워드·바꿔 쓴 질문·사람/시점)과 메일함 크기별로 나눠 보고한다. 방식 간 차이는 같은 질의 짝 비교로, 신뢰구간은 주제 묶음 단위 bootstrap으로 낸다.

### 4. 문서 정답 질의
- 이번 실행기는 메일 색인만 평가한다. 등급 2 정답이 문서인 질의는 메일 검색 지표에서 빼고, 빠진 수를 결과에 적는다. 문서 색인은 ADR-0020 보류 항목으로 남긴다.
- 문서를 찾는 능력은 종단 과제의 문서 질의(문서 검색 도구)로 잰다.
- 이유: 문서 색인을 같이 만들면 운영에 없는 기능을 평가하게 되고, 범위가 커진다. 문서 색인을 도입할 때 같은 실행기에 `kind=document`를 더한다.

### 5. 분할과 봉인
- 방식·설정 선택은 dev 질의로만 한다. test 질의는 러너와 같은 확인 플래그 없이는 실행하지 않고, test 실행 횟수를 결과에 남긴다(ADR-0010).
- 결과 파일은 `runs/`(git 제외)에 두고, 설정 지문·색인 지문·코드 SHA를 함께 기록한다.

### 6. 비용
- 메일 6,200통(200+1,000+5,000), 평균 본문 약 370자로 청크는 대략 메일당 1개다. `text-embedding-3-small` 기준 첫 색인 약 2M 토큰, 약 $0.04로 추정한다. 질의 임베딩은 무시할 만하다. 실행 전 dry-run으로 다시 계산하고, 누적 상한 인자를 둔다.
- 임베딩 호출은 OpenAI 직접 경로(남은 크레딧)를 쓴다.

## 영향
- `mailindex.search`에 방식 선택 인자, 동기화에 첫 동기화 상한 인자가 추가된다(기본값은 지금 동작과 같다).
- 새 모듈: 검색 평가 실행기(CLI), BM25 계산, 임베딩 캐시.
- 문서 정답 질의가 빠지므로 메일 검색 지표의 질의는 dev 37·test 51개, 주제 묶음은 dev 13·test 19개다(검수 제외 반영). 신뢰구간이 넓어지므로 방식 간 차이는 짝 비교로만 해석한다.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 평가 전용 색인·검색 코드 | 측정 결과가 운영 동작을 대표하지 못한다 |
| 실험마다 새로 색인 | 비용은 작지만 시간이 들고, 같은 설정의 반복 측정이 임베딩 응답 변동에 흔들릴 수 있다 |
| 5,000통 색인 하나로 작은 메일함을 필터 | 계정·ID가 달라 대응표가 필요하고, BM25 같은 말뭉치 의존 점수가 달라진다 |
| 문서도 지금 색인 | 운영에 없는 기능을 평가하게 된다(ADR-0020 보류) |
