# ADR-0003 — LangGraph로 승인 대기 Run 실행, 중복 실행 방지는 Orbit이 담당

- 상태: 채택 (2026-11-10, 개발자 승인)
- 작성일: 2026-11-10
- 근거: `docs/spikes/SPIKE-001-langgraph-interrupt-resume.md`, 세부 설계 D5-2·D5-3·D5-4·D5-5 (비공개, `private-docs/`)

## 배경

세부 설계 D5-3은 Agent 패턴을 LangGraph로 구현하고, 승인 대기는 `interrupt`로 멈췄다가 재개하는 방식을 후보로 두었다. 이 방식은 워커가 재시작돼도 이어서 실행할 수 있어야 쓸 수 있다. SPIKE-001에서 LangGraph 1.2.20과 PostgreSQL checkpointer로 이를 측정했다.

## 결정

1. **Run 실행에 LangGraph `interrupt` + `PostgresSaver`를 쓴다.** 그래프 내부 상태만 LangGraph checkpointer에 두고, 제품 상태(`run`, `approval`, `execution`)의 원본은 Orbit 테이블로 둔다 (D5-3 유지).
2. **외부 쓰기의 중복 실행 방지는 Orbit이 책임진다.** LangGraph에 맡기지 않는다. 구현 시 다음 네 조건을 지킨다.

| # | 조건 | 막는 문제 (스파이크 근거) |
| --- | --- | --- |
| 1 | 외부 쓰기 전에 `execution` 행을 `approval_id` 유일 제약으로 먼저 커밋한다. 행이 이미 있으면 외부 호출을 하지 않고 기존 결과나 대조 절차(D5-4)로 넘어간다 | 쓰기 직후 워커가 죽으면 노드가 다시 실행되어 쓰기가 중복된다 (S4: 10/10회 2건) |
| 2 | 승인 결정은 `approval` 행을 `status = 'PENDING'`일 때만 바꾸는 조건부 갱신으로 처리하고, 갱신에 성공한 요청만 그래프를 재개한다 | 같은 Run에 동시에 재개하면 둘 다 실행된다 (S7: 10/10회 2건) |
| 3 | interrupt가 있는 노드에서는 interrupt 앞에 부수 효과를 두지 않는다. 승인 요청 기록처럼 필요한 쓰기는 멱등하게(같은 키로 다시 써도 결과가 같게) 만든다 | 재개할 때 노드를 처음부터 다시 실행해 interrupt 앞 코드가 두 번 실행된다 (S6: 10/10회 2건) |
| 4 | 재개할 수 있는지는 Orbit의 `approval`·`run` 상태로 판단한다. LangGraph가 중복 재개를 오류로 알려 줄 것이라고 기대하지 않는다 | 완료된 Run에 재개를 다시 보내면 오류 없이 무시된다 (S5) |

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| LangGraph에 중복 방지를 맡김 | 구현량이 적다 | 스파이크에서 LangGraph가 동시 재개와 실행 중 장애 후 재실행을 막지 않았다 (S4, S7) |
| 자체 상태 기계로 Agent 실행 | 실행 시점을 완전히 통제 | 재개 자체는 LangGraph로 충분히 동작했다. 패턴 여섯 가지를 직접 구현하는 비용(D5-3)을 정당화할 문제가 나오지 않았다 |
| Temporal 등 durable execution 엔진 | 재시도·재개를 엔진이 보장 | 별도 클러스터 운영이 1인 개발에 크다. 위 조건 1·2로 해결 가능한 문제였다 |

## 결과

- 장점: D5-3의 구조를 유지한다. API 서버는 그래프를 실행하지 않고 `get_state`로 대기 중인 승인 요청을 읽어 `approval` 행을 만들 수 있다.
- 비용: `execution`·`approval` 테이블의 조건부 갱신과 유일 제약이 필수가 된다. 외부 쓰기 도구마다 결과 대조 방법(D5-4)이 필요하다.

## 미결정·후속 확인

- **메일 발송의 결과 대조 방법**: D5-4의 "앱이 넣은 고유 값으로 보낸편지함 검색"은 SPIKE-004에서 불성립했다(Message-ID는 Gmail이 덮어쓰고, 사용자 정의 헤더는 보존되지만 검색되지 않음). SPIKE-005에서 **초안 생성 → 초안 발송** 방식이 성립했다(발송된 초안은 즉시 404, 같은 초안 재발송은 404로 거절, 초안 스레드 ID로 보낸 메일을 찾을 수 있음). 이 방식을 메일 발송의 대조 방법으로 제안한다. 절차는 `docs/spikes/SPIKE-005-gmail-draft-send-reconcile.md` "제안하는 메일 발송 절차"를 따른다. `gmail.compose` 권한이 필요하다.
- 외부 쓰기가 있는 Run에 `durability="sync"`를 쓸지 여부. 스파이크는 기본값 `async`로만 측정했다.
- 장시간 대기 후 재개, LangGraph 버전 업그레이드 후 기존 체크포인트 재개.
- 조건 1·2를 구현한 뒤 S4·S7 시나리오를 통합 테스트로 만들어 외부 쓰기 1건을 보장하는지 확인한다.

## 재검토 트리거

- LangGraph의 interrupt·checkpointer 동작이 버전 업그레이드로 바뀔 때
- 조건 1·2를 지켜도 중복 실행이 재현될 때
- 장시간 대기 Run이 늘어 체크포인트 저장소 크기나 재개 지연이 문제가 될 때
