# 메일 RAG 아키텍처 비교 v1

설계: [ADR-0036](../adr/ADR-0036-rag-architecture-comparison.md). 같은 생성 모델(`openai/gpt-6-luna`, 추론 강도 `none`)과 같은 메일 색인에서 RAG 구조만 바꿔 메일 질의응답 성능을 비교했다. 승인·쓰기를 뺀 메일 QA 전용 평가 경로에서만 실행했고 제품 기준 설정은 바꾸지 않았다.

검색 정책 비교(R02, [rag-patterns-v1](rag-patterns-v1.md))와는 다른 실험이다. R02는 ReAct 안에서 검색 시점과 질의 재작성만 바꿨고, 이 문서는 RAG 구조 자체를 바꾼다.

## 결론

- **Advanced RAG(A1)만 test에서 기준 Agentic RAG(A2)보다 성공률이 높았다.** 성공률 0.601, A2 대비 짝 차이 +0.118 [0.052, 0.184]. dev(+0.167 [0.042, 0.292])와 방향이 같다.
- Naive RAG(A0)와 Adaptive RAG(A3)는 A2와 차이를 확인하지 못했다(CI가 0을 포함).
- GraphRAG(A4)는 A2보다 낮은 쪽으로 기울었지만 test CI 상한이 0.0이라 차이를 확정하지 못했다(−0.115 [−0.233, 0.0]).
- 다중 홉 질문은 A2만 일부 풀었다(test 0.417). 검색을 한 번만 하는 구성(A0·A1·A3·A4)은 0~0.21이다. dev 분석에서 한 번 검색으로는 두 근거 메일이 함께 맥락에 들어가는 경우가 거의 없었다(아래 "다중 홉 실패 원인").
- 구조별로 잘하는 유형이 달랐다. A1은 전체 집계, A0·A3는 단일 조회와 답할 수 없음, A2는 다중 홉에서 가장 높았다. 하나의 구조가 모든 유형에서 앞서지는 않았다.
- **R03b(후속)**: GraphRAG local 메일 순위에 reranker를 붙인 A4R은 test 성공률 0.625로 A4보다 +0.257 [0.132, 0.389], A2보다 +0.142 [0.063, 0.219] 높았다. A1과는 차이를 확인하지 못했고(+0.024 [−0.052, 0.108]), 그래프 없는 대조군과도 차이를 확인하지 못했다(+0.035 [−0.010, 0.080]). 아래 "R03b" 절.
- **R03c(후속)**: Agentic RAG 검색 도구 안에 Advanced RAG 검색 단계(재작성·reranker·압축)를 넣은 A2X는 test 성공률 0.663으로 A2보다 +0.181 [0.108, 0.253], A1보다 +0.062 [0.007, 0.118] 높았다. reranker만 넣은 A2R은 A2와 차이를 확인하지 못했다(+0.017 [−0.049, 0.087]). A4R과는 차이를 확인하지 못했다(+0.038 [−0.024, 0.101]). 지연은 p50 15.0초로 늘었다. 아래 "R03c" 절.
- 개선 효과는 이 질문 세트(합성 코퍼스, 160문항)와 이 모델에서 측정한 값이다. 제품 기준 설정 변경은 이 결과만으로 결정하지 않는다.

## 비교 설정

| 설정 | 이름 | 흐름 |
| --- | --- | --- |
| A0 | Naive RAG | 질문 원문으로 Hybrid 검색 1회 → 상위 5통 원문 → 답 생성 |
| A1 | Advanced RAG | 질의 재작성 → Hybrid 상위 20통 → `BAAI/bge-reranker-v2-m3` 상위 5통 → LLM 문맥 압축 → 답 생성 |
| A2 | Agentic RAG (기준) | 현재 제품 ReAct. 도구는 `search_indexed_mail`, `read_mail`, 답 제출만 허용 |
| A3 | Adaptive RAG | 라우터 LLM 1회가 {검색 없음, A1, A2} 중 하나를 고른 뒤 그 흐름 실행 |
| A4 | GraphRAG | 메일에서 개체·관계 추출 → Postgres 그래프 → 질문마다 local(개체 이웃 + 원본 메일) 또는 global(커뮤니티 요약) |

공통 조건(ADR-0036 공통 조건 1~8):

- 생성 모델·색인(Hybrid: `text-embedding-3-small` + Kiwi/`ts_rank`, RRF k=60, 800자 청크·100자 겹침)·답 형식이 같다.
- 검색 문맥 상한은 모든 구성에서 6,000자다. 결과를 보기 전에 dev 근거 길이로 정했다.
- A0·A1·A4-local은 메일 원문과 머리글을 넣어 A2의 `read_mail`과 정보량을 맞췄다. A4-global만 커뮤니티 요약을 넣는다.
- 모든 구성의 답 생성 프롬프트 끝에 같은 답 제출 안내(`rag-answer-note-v1`)를 붙였다(아래 "dev 1차 실행 폐기").

## 질문 세트와 사전 규칙

- 질문 세트 rag-v1: 새 합성 코퍼스(계정 4개 × 약 400통, 1,600통)에서 코드로 정답을 만든 160문항이다. 유형은 단일 조회·다중 홉·전체 집계·답할 수 없음이 각 40문항이다. 정답 근거 메일의 39%가 800자를 넘는다.
- 분할: dev 64문항, test 96문항(24 cluster). 사람 표본 검수(40문항) 뒤 test를 봉인했고, test 실행 직전 `verify-seal`로 봉인이 그대로인지 확인했다.
- 반복: dev·test 모두 구성마다 3회. 구성당 dev 192, test 288 episodes.
- 성공: 근거 메일 집합 정확 일치(`structured_answer`)와 답 사실 일치(`answer_facts`)를 모두 통과해야 한다.
- 통계: A2와의 같은 task/repeat 짝 차이, cluster bootstrap 95% CI(10,000회, seed 0), pass³. 유형별 CI는 표본이 작아 탐색 결과로 본다.
- 선택은 dev에서 했고 test는 한 번만 실행했다.

### Advanced RAG(A1) 세부

- 질의 재작성 fallback 0%.
- 압축 결과가 원문 문장과 맞지 않아 원문으로 되돌린 메일 196통(288 episodes 합계), 압축 비율 0.14.
- 압축 뒤 본문이 빈 메일은 episode당 평균 3.5통이다. 머리글은 남기므로 근거 메일 도달로 센다(ADR-0036 A1 구현 경계).

### GraphRAG(A4) 색인

- 그래프 구축: 4계정, LLM 비용 $0.2459. 계정마다 개체 377~394개, 관계 1,320~1,379개.
- 추출 품질(Sim 정답 그래프 대비): 개체 recall 0.58~0.64, 관계 recall(엄격 일치) 0.13~0.22. test 누설을 막으려고 추출 프롬프트를 튜닝하지 않았다.
- 낮은 관계 recall이 A4의 낮은 context recall과 다중 홉 0의 원인 후보다. 원인으로 확정하려면 추출 품질만 바꾼 비교가 필요하다.

### dev 1차 실행 폐기

dev 1차 실행에서는 ORACLE을 포함한 모든 구성의 다중 홉 성공률이 0이었다. 원인은 답 제출 안내의 빈틈이었다.

- 답 문장은 맞는데 `submit_answer`를 `abstain`으로 냈다.
- 다중 홉에서 대상을 확인한 중간 메일을 빼고 답 메일 1통만 냈다.

공용 답 안내의 `message_set` 설명이 "조건에 맞는 메일 전부"뿐이라 메일 내용을 묻는 질문에서 무엇을 낼지 알려주지 않았다. 채점은 바꾸지 않고 모든 구성의 답 생성 프롬프트에 같은 안내(`rag-answer-note-v1`)를 붙였다. 1차 결과는 `eval/runs/rag-arch-v1/dev-attempt1/`에 남겼고 비교에 쓰지 않는다. 이 수정은 ADR-0036 단계 7에서 허용한 dev 단계 프롬프트 수정이며, 모든 구성에 같이 적용했다.

## 코드 채점 검증 (정답 비교 Judge)

`answer_facts` 코드 채점이 바꿔 쓴 답을 제대로 판정하는지 확인하려고 표본 500건(구성마다 100건, dev·test에서 답할 수 있는 유형만, seed 20261121)을 `google/gemini-3.6-flash` Judge(`correctness-v2`)로 다시 판정했다. 근거 메일 집합 채점(`structured_answer`)은 코드로만 하고 이 비교에 넣지 않는다.

| 범위 | n | 일치율 | Cohen's kappa | 코드 통과 | Judge 정답 |

| 전체 | 500 | 0.942 | 0.883 | 210 | 231 |
| A0 | 100 | 0.94 | 0.876 | 37 | 43 |
| A1 | 100 | 0.90 | 0.795 | 56 | 60 |
| A2 | 100 | 0.98 | 0.960 | 50 | 52 |

- 판정이 다른 29건 중 25건은 코드 실패·Judge 정답이다. 24건이 단일 조회의 결정 문장 질문이고, 답이 "외주 디자인 범위 축소"를 "범위를 줄이기로" 같이 바꿔 썼다. 코드 채점은 바꿔 쓴 결정 문장에서 정답을 놓친다.
- 그래서 **단일 조회 성공률은 실제보다 낮게 잡혔을 수 있다**. 표본에서 코드 통과 103건, Judge 정답 126건이다. 다중 홉·전체 집계는 거의 그대로다.

## R03b: GraphRAG local 순위에 reranker 적용

설계: [ADR-0037](../adr/ADR-0037-graphrag-reranker.md). R03 GraphRAG(A4)는 2홉 안에서 계정 메일 대부분(약 400통 중 382~392통)에 닿았지만, 메일 순위에 질문 관련도를 쓰지 않아 근거 메일이 상한 6,000자 밖으로 밀렸다. R03b는 local 메일 순위만 "임베딩 거리 상위 40통 → reranker(A1과 같은 `BAAI/bge-reranker-v2-m3`) → 상위 12통"으로 바꿨다. R03의 구성·결과·설정 지문은 바꾸지 않았다.

## R03c: Agentic RAG 검색 도구에 Advanced RAG 검색 단계 넣기

설계: [ADR-0038](../adr/ADR-0038-agentic-advanced-search.md). R03에서 Advanced RAG(A1)는 단일 조회·전체 집계에, Agentic RAG(A2)는 다중 홉에 강했다. R03c는 A2의 ReAct 흐름과 도구는 그대로 두고 `search_indexed_mail` 안쪽만 A1의 검색 단계로 바꿨다. R03·R03b의 구성·결과·설정 지문은 바꾸지 않았다.

| 설정 ID | 이름 | `search_indexed_mail`이 하는 일 |
| --- | --- | --- |
| A2R | Agentic RAG + reranker | Hybrid 상위 20통 → reranker → 상위 `max_results`통. 결과 형식은 A2와 같다 |
| A2X | Agentic RAG + Advanced 검색 | 질의 재작성 → Hybrid 상위 20통 → reranker 상위 5통 → 문맥 압축. 발췌 대신 압축 본문을 돌려준다 |

- reranker, 재작성·압축 프롬프트, 후보 수 20은 A1과 같은 값을 썼다. 새로 조정하지 않았다.
- 후보 20통 읽기도 step으로 세므로 두 구성은 `--max-steps 150`으로 실행했다(ADR-0038 §3). step·시간 상한으로 실패한 episode는 dev·test 모두 없었다. 실패는 모두 `wrong_answer`다.
- test는 `verify-seal`로 봉인을 확인한 뒤 구성마다 한 번만 실행했다.

### 결론 (R03c)

- **A2X는 기준 A2보다 성공률이 높았다.** test A2X − A2 = +0.181 [0.108, 0.253]. dev(+0.188 [0.052, 0.312])와 방향이 같다.
- **A2X는 A1보다도 조금 높았다.** +0.062 [0.007, 0.118]. CI 하한이 0에 가까워 차이가 작다. 단일 조회·전체 집계는 A1과 차이를 확인하지 못했고, 다중 홉은 A1보다 높았다(+0.347 [0.181, 0.514], 탐색 결과).
- **reranker만 넣은 A2R은 A2와 차이를 확인하지 못했다.** +0.017 [−0.049, 0.087]. context recall은 0.860에서 0.904로 올랐지만 성공률은 거의 그대로였다.
- **A2X − A2R = +0.163 [0.090, 0.240].** 이 차이에는 질의 재작성, 발췌 대신 압축 본문, 결과 수 5통 고정이 함께 들어 있다. 어느 요소의 효과인지는 이 실험으로 나누지 못한다.
- **다중 홉**: A2X 0.514로 A2(0.417)보다 높은 쪽이지만 차이를 확인하지 못했다(+0.097 [−0.069, 0.278]). A2의 다중 홉 성능을 잃지 않으면서 단일 조회·전체 집계를 A1 수준으로 올린 결과다.
- **GraphRAG + reranker(A4R)와는 차이를 확인하지 못했다.** A2X − A4R = +0.038 [−0.024, 0.101].
- **비용과 지연이 늘었다.** A2X는 A2보다 LLM 호출이 3.7회에서 6.8회로, episode당 비용이 $0.00077에서 $0.00099로, p50 지연이 5.2초에서 15.0초로 늘었다(p95 8.1초 → 28.5초).
- 정답 비교 Judge 불일치 21건을 원문과 대조한 결과 19건은 Judge가 맞았다. 코드 채점은 A2X 단일 조회 성공을 더 많이 놓쳤다(아래).

### R03c 한계

- **요소 분리 불가**: A2X는 A2R과 질의 재작성, 압축 본문, 결과 5통 고정이 함께 다르다. 이득을 한 요소의 효과로 해석하지 않는다. 도구 결과 잘림 비율이 A2X에서 크게 줄어든 것(0.590 → 0.017)이 원인 후보지만 검증하지 않았다.
- **빈 압축**: A2X가 돌려준 메일의 72%(dev 888/1,235, test 1,305/1,805)는 압축 결과가 비어 머리글만 들어갔다. A1도 비슷하다. 이런 메일도 context recall에서는 닿은 것으로 센다(A1과 같은 규칙).
- **지연**: 검색마다 CPU reranker가 돌아 p95가 28.5초다. 다른 장치에서는 달라진다.
- **에이전트 query 봉투**: A2X의 재작성 입력에 에이전트 query를 봉투 없이 넣는다. 평가 경로 전용이고 합성 데이터만 쓴다(ADR-0038 §2).
- **trace 본문**: `rag_diag`에는 ID와 숫자만 남기지만 `trace`(ADR-0029)에는 다른 R03 구성처럼 도구 인자와 본문이 남는다. 합성 데이터이고 결과 파일은 커밋하지 않는다.
- **R03 한계 승계**: 아래 "알려진 한계"의 채점·Judge·설정 지문 항목이 R03c에도 그대로 적용된다.

## 정답 판정 보조 실험: Jev (ADR-0039)

자유 서술 답의 정답 판정에 결정 전용 모델 Jev(`typesafe-ai/jev-1.14.0`)를 쓸 수 있는지 Judge 라벨 900건으로 검증했다. 주 지표와 위 수치는 바꾸지 않았다.

- test에서 Judge와 kappa 0.977, 3회 반복에서 판정 뒤집힘 0건으로 두 조건을 채웠다.
- 대조 검토 67건에서 검토 결과와 맞은 건수는 Jev 62, Judge 63, 코드 채점 4다. Jev가 Judge 이상이어야 한다는 조건을 채우지 못해 기각했다. 처음에는 검토 라벨을 옮기는 스크립트 오류로 63/66으로 계산했고, 고친 뒤에도 판정은 같다.
- Judge와 갈린 8건(dev 2, test 6)은 모두 Jev가 정답 쪽이었다. 근거 메일과 대조하니 Judge 쪽이 5건, Jev 쪽이 3건이었다(`eval/runs/rag-arch-v1/jev/disagreements-review.md`). Jev는 기준 사실이 답에 있으면 다른 프로젝트 내용이 섞여도 정답으로 보는 경향을 보였다.
- Judge 프롬프트의 일반 판정 기준을 Jev 질문에 옮긴 v2(`jev-correctness-v2`)도 실행했다. 섞인 답의 확률은 내려갔지만 dev에서 고른 임계값 0.4에서 대조 검토 62건으로 v1과 같아 기각했다. 0.5에서는 64건이지만 사전 규칙상 채택 근거로 쓰지 않는다. 세부는 ADR-0039에 있다.
- dev에서만 설정을 고르고(v2, 임계값 0.60) 채점한 적 없는 test 1,413건에 한 번 실행해 다시 검증했다. Judge와 kappa 0.970, 반복 뒤집힘 2.0%였지만, 둘이 갈린 21건의 눈가림 검토에서 Jev 2건, Judge 19건이 맞아 기각했다. 두 채점기가 같은 판정을 낸 표본 60건에서 함께 틀린 문항은 없었다. 비용은 약 1.77달러다. 자유 서술 답의 주 정답 판정은 Judge(`correctness-v2`)로 유지한다.
- 기각 뒤 사용 방식을 점검하려고 dev에서만 세 문구를 더 시험했다. 영어 지시문(v3)은 정답 확률을 0.8 이상으로 모았고, 영어 지시문에 섞임 질문을 더한 v4는 임계값 0.20~0.35 구간에서 dev 검토 27건 중 26건으로 Judge와 같았다. 기준 사실을 input에 넣은 v5는 효과가 없었다. dev 결과라 채택 근거로 쓰지 않으며, 세부는 ADR-0039에 있다.
- 지출 0.0231달러. 결과는 `eval/runs/rag-arch-v1/jev/`에 있다. 자세한 수치와 해석은 ADR-0039 "실행 결과"를 본다.

## 알려진 한계

- **답 사실 채점의 부분 문자열 판정**: `answer_facts`는 정규화 뒤 부분 문자열로 비교한다. 답 문장에 여러 값을 나열하면 통과할 수 있고, 결정 문장을 바꿔 쓰면 놓친다. 정답 비교 Judge 표본에서 단일 조회 일치율이 0.838이었다.
- **정답 비교 Judge 코드**: 재시도 지시문(`RETRY_NOTE`)이 판정 지문에 들어가지 않는다. 동시 실행 상한 단위 테스트는 배치 사전 계산만 검사한다. 이번 판정 결과에는 영향이 없다.
- **기간 표현**: "11월 24일까지"처럼 범위를 말한 답이 날짜 사실을 통과한다.
- **A3 라우터**: 다중 홉을 모두 A1으로 보냈다. A3 결과는 이 라우터 프롬프트의 결과이며 Adaptive RAG 구조 일반의 상한이 아니다.
- **A3 "검색 없음" 경로**: A0 답 프롬프트를 재사용한다. 이번 실행에서 이 경로를 고른 적은 없다.
- **GraphRAG 구현 범위**: 라이브러리 없이 직접 만든 최소 구현이다. 추출 관계 recall이 낮고 프롬프트 튜닝을 하지 않았다. 다른 GraphRAG 구현의 성능으로 일반화하지 않는다.
- **dev 1차 폐기**: 답 제출 안내를 고친 뒤 dev를 다시 실행했다. 고친 안내는 모든 구성에 같이 적용했다.
- **"repeat 0"**: ADR의 "repeat 0만 Judge"는 실행 기록의 첫 반복(repeat 값 1)으로 해석했다.
- **A2와 v1 기준선**: A2는 도구를 두 개로 제한했으므로 v1 기준선 점수와 직접 비교하지 않는다(ADR-0036).
- **생성 계열 편향**: 질문 생성 모델 계열별 결과 분리(ADR-0026)는 이번 문서에서 하지 않았다.
- **설정 지문**: TEMPERATURE가 설정 지문에 들어가지 않는다. 모든 구성이 같은 값을 쓰지만 지문만으로는 확인할 수 없다.
- **실행 코드 상태**: 비교 코드가 아직 커밋되지 않은 작업 트리에서 실행했다. 실행 기록의 `config_fingerprint`로 구성을 구분한다.
- **test 실행 승인**: ADR 단계 8의 test 실행 승인은 개발자의 "질문 없이 쭉 진행" 지시로 갈음했다. test 비용은 dev 실측으로 다시 추정했고 상한 안이었다.
