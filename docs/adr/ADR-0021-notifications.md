# ADR-0021 — 예약 알림 (웹 안 + 브라우저 알림)

- 상태: 채택(구조). 알림 시점 기본값(10분 전)과 일정 조회 주기는 `실험 중` 기본값.
- 작성일: 2026-11-12
- 근거: ADR-0004(RLS), ADR-0005(작업 큐), ADR-0006(RLS 밖 저장소), ADR-0011(읽기 비서), ADR-0012(쓰기 경로), ADR-0016(연결), ADR-0018(데이터 봉투), ADR-0019(주기 작업·`SECURITY DEFINER` 선별 패턴), D6-1(외부 콘텐츠)

## 문제
비서는 사용자가 말을 걸 때만 동작한다. 곧 시작하는 일정이나 사용자가 부탁한 일("내일 3시에 보고서 제출 알려줘")을 정해진 시각에 먼저 알려 주지 못한다.

## 결정

### 1. 알림 종류
| 종류 | 만드는 쪽 | 내용 |
| --- | --- | --- |
| `event_reminder` | 서버 주기 작업 | 연결된 계정의 기본 캘린더 일정 시작 N분 전. 종일 일정과 내가 거절한 일정은 제외 |
| `reminder` | 대화(비서 도구) | 사용자가 요청한 시각에 사용자가 요청한 문구 |

### 2. 발송 채널
- Orbit 화면 안 알림 목록(헤더 알림 버튼, 읽지 않은 수)과, 탭이 열려 있고 사용자가 허용했을 때의 브라우저 시스템 알림(Notification API).
- 브라우저 알림 권한은 사용자가 "브라우저 알림 켜기"를 누를 때만 요청한다. 알림 `tag`를 알림 ID로 써서 탭이 여러 개여도 같은 알림이 한 번만 보이게 한다.
- 메일·Web Push 같은 외부 발송은 하지 않는다(별도 결정). 탭이 모두 닫혀 있으면 다음에 열 때 목록에서 본다.

### 3. 저장 (마이그레이션 0010, RLS ENABLE + FORCE)
- `notification`: id, workspace_id, kind, title(200자), due_at, status(`scheduled`·`cancelled`), read_at, created_at. `event_reminder`는 connection_id·calendar_id·event_id·event_start를 함께 두고 `(workspace_id, connection_id, calendar_id, event_id)`로 유일. `reminder`는 만든 run_id를 둔다.
- `notification_setting`: workspace_id(PK), 일정 알림 사용 여부(기본 켬), 알림 시점(5·10·15·30·60분 전, 기본 10분).
- "도착"은 따로 저장하지 않는다. `status=scheduled AND due_at <= now`인 알림이 도착한 알림이다. 발송 작업이 없으므로 워커가 잠시 멈춰도 알림이 사라지지 않는다.
- 일정 제목은 외부 문자열이다. RLS 테이블에만 두고 화면에서 텍스트로만 그린다(링크·HTML 해석 없음).

### 4. 일정 알림 만들기
- 주기 작업 `schedule_event_reminders`(5분마다, 별도 큐 `notify`)가 일정 알림을 켠 워크스페이스의 활성 연결을 `SECURITY DEFINER` 함수(ID만 반환)로 고르고, 워크스페이스마다 작업 `sync_event_reminders(workspace_id, connection_id)`를 등록한다.
- 작업은 기본 캘린더에서 지금부터 2시간 안에 시작하는 일정을 조회해 알림을 만들거나 고친다(시작 시각이 바뀌면 `due_at` 갱신, 취소·거절·삭제되면 `cancelled`). 이미 시작한 일정의 알림은 새로 만들지 않는다. 알림 시점 설정을 바꾸면 아직 도착하지 않은 일정 알림의 `due_at`을 다시 계산한다.
- 커넥터 오류는 개수·종류만 기록하고 다음 주기에 다시 시도한다. 권한 철회는 ADR-0019와 같은 방식으로 건너뛴다.

### 5. 대화 리마인더
- 실사용 경로(`runflow`)에 쓰기 도구 `create_reminder(text, due_at)`를 추가한다. `due_at`은 시간대가 있는 ISO 시각이고 지금 이후 1년 이내, `text`는 200자 이하.
- 외부에 아무것도 보내지 않고 Orbit 안에만 남으므로 승인 흐름(ADR-0012)을 거치지 않는다. 대신 프롬프트는 사용자가 직접 요청했을 때만 만들라고 하고, 도구 결과를 데이터 봉투로 돌려준다. 사용자는 알림 목록에서 예정된 리마인더를 보고 취소할 수 있다. 남는 위험: 모델이 데이터 속 지시로 리마인더를 만들면 그 문구가 알림 목록과 브라우저 알림 제목에 그대로 뜬다(링크·HTML 해석은 없고 예정 리마인더는 100개 상한).
- 평가 경로(`assistant_v0`)에는 추가하지 않는다. 프롬프트 `runflow-v0.7`.

### 6. API·화면
- `GET /api/notifications`(도착한 알림, 최근순, 읽음 여부), `GET /api/notifications/upcoming`(예정된 리마인더·일정 알림), `POST /api/notifications/{id}/read`, `POST /api/notifications/read-all`, `DELETE /api/notifications/{id}`(예정 알림 취소), `GET·PUT /api/notification-settings`. 모두 `workspace_session` 안, 다른 워크스페이스는 404.
- 화면은 로그인 동안 30초마다 도착한 알림을 가져온다(탭이 숨겨지면 멈췄다가 다시 보일 때 바로 가져온다). 새로 도착한 읽지 않은 알림(도착 10분 이내)만 브라우저 알림으로 띄운다.

### 7. 삭제 전파
연결 해제·교체 시 그 연결의 `event_reminder`를 같은 트랜잭션에서 지운다(D7-4). 대화 리마인더는 연결과 무관해 남는다.
- 보존: 일정 알림은 일정 시작 후 7일이 지나면 동기화 작업이 지운다. 대화 리마인더는 도착 후 30일이 지나면 지운다(같은 작업이 워크스페이스 단위로 정리). 예정된 대화 리마인더는 워크스페이스당 100개까지(데이터 속 지시로 남발되는 것을 막는 서버 상한).

## 보류
- 외부 발송(메일·Web Push), 탭이 닫혀 있을 때의 알림.
- 기본 캘린더 밖 캘린더, 반복 리마인더, 리마인더 수정 도구.
- 알림 시점 기본값 평가.

## 검토한 대안
| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 알림마다 예약 작업(`schedule_at`)으로 발송 | 취소·시각 변경 때 작업도 같이 고쳐야 한다. 웹 안 알림은 시각 비교만으로 충분하다 |
| SSE로 알림 밀어 주기 | 연결 수가 늘고, 30초 지연이면 충분하다 |
| 리마인더도 승인 받기 | 외부 영향이 없는데 매번 확인을 요구하면 쓸 이유가 줄어든다 |
| 일정을 미리 전부 저장 | 일정은 실시간 조회 원칙(D7-1). 2시간 창만 본다 |
