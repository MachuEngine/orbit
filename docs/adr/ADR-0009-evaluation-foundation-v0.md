# ADR-0009 — 평가 기반 v0 구조: LLM 인터페이스, 평가 데이터, 평가 러너

- 상태: 채택 (2026-11-11, 개발자가 단계별 진행을 위임한 범위에서 메인 세션이 결정. 이의가 있으면 3단계 PR 리뷰 때 바꾼다). §2 분할과 §3 채점 일부는 ADR-0010이 고친다
- 작성일: 2026-11-11
- 근거: 세부 설계 D2(평가 데이터), D3(평가 러너), D9(LLM 제공자·모델 고정), D10(실험 범위·예산) (비공개, `private-docs/`), ADR-0008(Connector 계약·Sim)

## 배경

3단계는 "측정할 수 있는 상태"를 만드는 단계다. 이후 모든 기능(일정 조회, RAG, Agent 패턴)의 효과를 같은 데이터·같은 러너로 비교하려면, 세 구성 요소의 경계를 먼저 고정해야 한다. 세 요소를 병렬로 개발하기 위해서도 인터페이스가 먼저 필요하다.

## 결정

### 1. LLM 인터페이스 (`orbit.llm`) — D9-2·D9-3·D9-4
- 모든 모델 호출은 Orbit 내부 인터페이스 하나를 거친다. 메서드는 `complete(request) -> response` 하나로 시작한다(비동기).
  - `request`: 메시지 목록, 도구 정의(JSON Schema), `tool_choice`, `max_output_tokens`, `temperature`, 메타데이터(`purpose`: `system_under_test` | `data_generation` | `judge`).
  - `response`: 텍스트, 도구 호출 목록(이름·인자 JSON), 종료 사유, 사용량(입력·출력·캐시 토큰), 비용(알 수 없으면 `None`), 지연, 실제 응답한 모델 ID·제공자.
- **모델 ID는 설정에서만 오고 고정 ID여야 한다.** 별칭(`latest` 등)이나 빈 값이면 시작 시 실패한다(D9-3).
- 구현체
  - `OpenRouterLLM`: OpenAI 호환 API. 요청마다 제공자 라우팅(`order`, `allow_fallbacks=false`, `require_parameters=true`, `data_collection=deny`)을 붙인다(D9-4). 응답의 실제 모델·제공자를 기록해 설정과 다르면 오류로 처리한다.
  - `ScriptedLLM`: 테스트·러너 개발용. 미리 정한 응답 목록을 순서대로 돌려준다. 네트워크 없음.
- 호출 기록: 각 호출의 사용량·비용·지연을 러너가 수집할 수 있게 콜백 또는 기록기로 노출한다. 프롬프트·응답 원문은 기록기에 남기지 않는다(ADR-0006 취지, 디버그 모드에서만 로컬 파일로).
- 재시도 정책은 인터페이스가 소유한다: 일시 오류만 재시도, 재시도 횟수는 사용량에 포함.

### 2. 평가 데이터 (`orbit.evaldata`) — D2
- **시나리오 우선 생성**(D2-1): 세계 모델(YAML: 가상 사용자, 인물, 프로젝트, 반복 일정) → 시드 고정 사건 타임라인(코드) → 아티팩트(Sim 스냅샷 v1의 메일·일정) → 질문과 정답(Gold).
- **정답은 코드가 계산한다.** 날짜·ID·기대 상태 변화·기대 도구 호출은 구조 데이터에서 나온다. 본문 문장만 LLM이 다듬을 수 있고, v0은 LLM 없이 템플릿 문장으로도 생성할 수 있어야 한다(LLM 렌더링은 선택 단계, 사실 보존 검사 포함).
- **산출물 형식**: 데이터셋 디렉터리 하나 = `manifest.json`(이름, 버전, 생성 시드, 생성 코드 git SHA, 분할 비율), `world.json`(Sim 스냅샷 v1), `tasks.jsonl`(과제당 한 줄). 과제는 `task_id`, `scenario_id`, `split`(`dev`/`test`), `as_of_time`, `account_id`, `turns`(사용자 발화 목록), `gold`(정답 유형별: `answer_facts`, `expected_state_diff`, `forbidden_tools`, `required_tool_calls` 중 필요한 것), `difficulty`(시나리오 파라미터), `tags`.
- **분할**(D2-3): 시나리오 단위로 dev/test를 나누고, 같은 시나리오의 과제는 같은 쪽에 둔다. test는 봉인한다(러너가 `--split test`를 받으면 명시 확인 플래그 없이는 실행하지 않는다).
- **규모**(D2-2 v0): 가상 사용자 2명, 메일 200건, 일정 60건, 질문 60개. 문서는 문서 Connector가 생기는 7단계까지 제외한다. 1차 과제 유형은 **일정 조회**(읽기 전용)다.
- **사람 검수**: v0은 전수 검수. 검수 결과(승인·수정·제외, 사유)를 `review.jsonl`로 남기고 데이터셋 버전에 포함한다.

### 3. 평가 러너 (`orbit.evalrunner`) — D3
- **평가 대상 인터페이스** `SystemUnderTest`: `async run(episode) -> EpisodeOutput`. `episode`는 Sim 커넥터(포크된 월드), 고정 시계, FaultPlan, 예산, LLM 인터페이스, 과제를 담는다. `EpisodeOutput`은 최종 응답 텍스트와 구조화된 답(있다면)이다. 궤적은 Sim 호출 기록에서, 상태 변화는 `diff`에서 러너가 직접 가져온다(평가 대상이 보고하는 값을 믿지 않는다).
- **에피소드 절차**: 월드 포크(시드 = 과제·반복 번호로 결정) → 시계를 `as_of_time`으로 고정 → FaultPlan 적용 → 평가 대상 실행(예산 상한 감시) → 상태 diff·궤적·응답 수집 → 채점 → 결과 한 줄 기록.
- **채점**(D1-3): 정형 정답은 코드로 채점한다 — 최종 상태 비교(정규화 후 `expected_state_diff`와 일치), 궤적 규칙(금지 도구 호출, 승인 위반, 불필요한 쓰기), 응답 사실 포함 여부(`answer_facts`: 날짜·시각·제목 등 정규화 비교). LLM Judge는 v0에 넣지 않는다(D2-4).
- **결과 스키마**(D3-2): 에피소드당 JSONL 한 줄. `experiment_id`, `config`(git SHA, 데이터셋 이름@버전/분할, 평가 대상 이름·버전, 모델 ID, 프롬프트 버전, 예산, FaultPlan 이름), `task_id`, `repeat`, `outcome`(`success`, `failure_type`), `state_diff_match`, `approval_violations`, `trajectory`(도구 이름 순서), `usage`(LLM 호출 수, 입력·출력 토큰, `cost_usd`), `latency_ms`. 설정 지문(`config`의 정렬된 JSON 해시)을 함께 저장한다.
- **반복과 통계**(D3-3): 과제당 k회(기본 3) 반복. 성공률과 과제 단위 bootstrap 95% 신뢰구간, 두 설정의 짝지은(paired) 차이 bootstrap, pass^k. 통계 함수는 결과 JSONL만 입력으로 받는다(러너와 분리).
- **예산**(D3-4, D10-3): 에피소드별 최대 단계·토큰·시간을 넘으면 실패로 기록하고 비용은 합산한다. 실험 단위 누적 비용 상한을 넘으면 러너가 중단한다. 실행 전 사전 측정 모드(과제 5개)로 전체 비용을 추정해 출력한다.
- **결정성 확인**: `ScriptedLLM`과 같은 데이터셋·시드로 두 번 실행하면 결과 JSONL(시각·지연 제외)이 같아야 한다. 이것을 러너의 회귀 테스트로 둔다.

### 4. 3단계 작업 분할
| 작업 | 의존 | 병렬 |
| --- | --- | --- |
| 3a LLM 인터페이스 + `ScriptedLLM` + `OpenRouterLLM`(HTTP는 모의 테스트) | 없음 | 가능 |
| 3b 평가 데이터 생성기 v0(템플릿 렌더링) + 검수 도구 | ADR-0008 Sim 스냅샷 | 가능 |
| 3c 평가 러너 v0 + 통계 + `ScriptedLLM` 기반 결정성 테스트 | 3a·3b의 인터페이스(이 ADR) | 가능(인터페이스는 이 ADR 기준으로 맞춘다) |
| 3d 읽기 전용 일정 조회 경로(평가 대상 첫 구현) | 3a, 3c | 3a·3c 뒤 |
| 3e 모델 파일럿 → 고정 모델 ADR | 3a~3d, **OpenRouter API 키(개발자)**, **데이터 60문항 검수(개발자)** | 마지막 |

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 평가 프레임워크(Inspect AI, LangSmith) 사용 | Orbit 파이프라인 전체(Sim 포크, 고정 시계, FaultPlan, 상태 diff)를 어차피 직접 구현해야 한다(D3-1). 결과 스키마를 직접 소유하면 나중에 내보내기 쉽다 |
| 정답을 LLM이 생성 | 생성 텍스트 해석에 정답이 의존하고 다문서 모순을 잡을 수 없다(D2-1) |
| 평가 대상이 궤적·상태를 스스로 보고 | 평가 대상의 버그가 채점 결과를 오염시킨다. 러너가 Sim에서 직접 수집한다 |
| LiteLLM 등 다중 제공자 계층 | 계층이 늘고 제공자 고유 기능이 빠질 수 있다(D9-2). OpenRouter 하나로 파일럿까지 충분하다 |

## 결과

- 3a·3b·3c를 세 implementer가 병렬로 진행할 수 있다.
- 개발자 개입이 필요한 지점은 두 곳뿐이다: OpenRouter 계정·API 키 설정(ZDR, 데이터 수집 거부), 평가 데이터 60문항 검수.
