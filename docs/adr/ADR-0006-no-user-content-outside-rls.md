# ADR-0006 — RLS 밖 저장소에 사용자 본문을 두지 않는다

- 상태: 채택 (2026-11-11, 구현 계획 v0.1 승인에 포함)
- 작성일: 2026-11-11
- 근거: `docs/implementation-plan.md` §1, ADR-0003, ADR-0004, ADR-0005, 세부 설계 D4-4·D7-4 (비공개, `private-docs/`)

## 배경

ADR-0004는 사용자 데이터를 `workspace_id` + RLS로 이중 격리하기로 했다. 그런데 라이브러리가 소유한 두 저장소는 이 구조 밖에 있다.

| 저장소 | 테이블 | 저장 형태 | `workspace_id` |
| --- | --- | --- | --- |
| LangGraph checkpointer (ADR-0003) | `checkpoints`, `checkpoint_blobs`, `checkpoint_writes` | 그래프 상태 전체를 JSON/바이너리로 저장 | 없음 |
| Procrastinate (ADR-0005) | `procrastinate_jobs` | 작업 인자 `args`를 JSON으로 저장 | 없음 |

메일 본문이나 주소가 그래프 상태나 작업 인자에 들어가면, RLS가 적용되지 않는 곳에 사용자 데이터가 쌓이고 연결 해제 시 삭제 전파(D7-4)에서도 빠진다.

## 결정

1. **그래프 상태에는 식별자와 짧은 제어 값만 둔다.** `run_id`, 작업 집합 핸들(E1, M3), Orbit 테이블의 ID, 단계 상태 플래그는 허용한다. 메일·문서·일정 본문, 메일 주소, 사람 이름, 모델에 넘긴 프롬프트·응답 원문은 넣지 않는다. 필요하면 Orbit 테이블(RLS 적용)에 저장하고 ID로 참조한다.
2. **작업 인자에는 ID만 둔다.** 예: `execute_run(run_id)`. 작업 처리기는 시작할 때 트랜잭션 범위로 워크스페이스를 설정하고(ADR-0004), ID로 Orbit 테이블에서 필요한 데이터를 읽는다.
3. **체크포인트는 `run`과 생명주기를 같이 한다.** `run` 삭제, 워크스페이스·연결 삭제 시 해당 `thread_id`의 체크포인트 행을 같은 작업에서 지운다. 삭제 후 남은 행 0을 자동 테스트로 확인한다(D7-4와 같은 방식).
4. **강제 방법**
   - 그래프 상태 타입을 Orbit이 정의한 좁은 스키마로 제한한다. 문자열 필드의 길이 상한 같은 단순 검사를 둔다.
   - code-reviewer 프로젝트 검토 관점에 "그래프 상태·작업 인자에 사용자 본문이 들어가는가"를 추가한다.

## 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| 체크포인트 테이블에 `workspace_id` 열과 RLS 추가 | DB가 강제한다 | 라이브러리 소유 테이블이라 스키마를 바꾸면 업그레이드마다 충돌하고, checkpointer가 쓰는 연결에 워크스페이스 설정을 끼워 넣기 어렵다 |
| 체크포인트를 별도 DB·스키마에 두고 접근 제한 | 격리 범위가 분명하다 | 본문이 여전히 저장되어 삭제 전파 문제가 남는다. 저장 자체를 없애는 편이 단순하다 |
| 그래프 상태 암호화 | 유출 시 피해 감소 | 키 관리가 늘고 삭제 전파 문제는 그대로다 |

## 결과

- 장점: 사용자 본문은 모두 RLS가 적용된 Orbit 테이블에만 존재한다. 삭제 전파 대상이 Orbit 테이블과 체크포인트 `thread_id`로 한정된다.
- 비용: 그래프 노드가 본문이 필요할 때마다 Orbit 테이블에서 읽어야 한다. 대화 맥락(D8-2)은 Orbit의 `message` 테이블에서 조합한다.

## 재검토 트리거

- LangGraph가 상태 외부 저장(참조 기반 상태)을 공식 지원해 이 규칙을 라이브러리 차원에서 강제할 수 있을 때
- 그래프 노드의 반복 조회가 지연 목표를 넘을 때
