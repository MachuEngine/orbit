# ADR-0034 — 평가 에피소드의 준비·실행·관찰과 정리에 시간 상한을 둔다

- 상태: 채택 (2026-11-17 사용자 지시 범위의 방어 수정. 실제 정지 원인은 미확정)
- 작성일: 2026-11-17
- 근거: ADR-0023(평가 DB 수명), ADR-0030(평가 전용 패턴), ADR-0031(fixed_workflow 채택 보류), 평가 계획 §1-7

## 문제와 조사 범위

`fixed_workflow` test 평가가 4~9개 에피소드 뒤 멈췄다. 부분 JSONL에는 완료된 에피소드만 있어 멈춘 호출의 스택이나 대기 위치를 확정할 수 없다. dev 264건이 완료됐다는 사실도 test에서만 생기는 논리 오류나 네트워크 정지를 입증하지 않는다.

코드에서는 다음을 확인했다.

- 범주 밖 도구는 `tool_not_allowed`로 거절하고 act 단계는 증가한다. 범주별 단계 상한, 전체 단계 예산, 그래프·승인 왕복 상한이 있다. 반복 호출만으로 무한 루프가 된다는 증거는 없다.
- OpenAI·OpenRouter 어댑터는 HTTP 타임아웃과 비동기 재시도 대기를 쓴다. HTTP의 개별 입출력 타임아웃은 에피소드 전체의 벽시계 상한과 다르다.
- `Budget.max_seconds`의 `asyncio.timeout`은 SUT 실행만 감싼다. 평가 DB 준비·관찰·정리, 실패 시 잠금 해제·연결 종료는 이 상한 밖이다. 이 누락은 실제 정지 원인과 별개로 고친다.
- 이벤트 루프를 막는 동기 호출, 절전 뒤 네트워크·드라이버 대기는 후보로 남긴다. 실제 정지 시점의 스택 없이 하나를 원인으로 단정하지 않는다.

## 결정

1. 평가 러너에서 준비 → SUT 실행(분류·LLM·도구·승인 재개 포함) → 결과 관찰에 하나의 에피소드 시간 예산을 적용한다. 단계마다 예산을 다시 시작하지 않는다. 시간 초과는 `budget_exceeded / time`으로 기록한다.
2. 시간 초과 뒤에도 자원 정리를 시도한다. 정리에는 별도의 짧은 유한 유예 시간을 둔다. 따라서 총 경과 시간에는 에피소드 예산에 정리 유예 시간이 더해질 수 있다. 관찰이 끝나지 않으면 성공으로 채점하지 않는다.
3. 취소 처리 중 실행하는 잠금 해제·연결 닫기와 실험 종료의 환경 닫기에도 유한 상한을 둔다. 정리 실패는 표시하고, 안전한 정리를 보장하지 못하면 다음 에피소드를 계속 실행하지 않는다. 외부 취소는 삼키지 않는다. 예외·로그에는 ID와 오류 종류만 남긴다.
4. 실사용 runflow, 범주·프롬프트·도구 정의·LLM 어댑터는 바꾸지 않는다. 정상 react 요청과 runflow 설정 지문은 유지한다. 평가 결과의 코드 SHA로 수정 전후를 구분한다. 시간 초과 경계의 실패 결과는 달라질 수 있다.
5. 이번에는 스크립트 LLM·비동기 대기 대역·실제 테스트 DB만으로 검증한다. 실제 LLM·임베딩·평가 DB를 쓰는 재실행은 후속 사용자 확인 때 한다.

### 구현 상한과 결과 해석

- 에피소드 본 예산은 기존 `Budget.max_seconds`(기본 120초)다. 준비·실행·관찰이 이를 공유한다. 정상 경로의 `latency_ms`는 기존 SUT 실행 구간 의미를 유지하며, 전체 자원 수명 상한과 다른 값이다.
- 에피소드 정리는 5초 유예, advisory unlock은 1초, 연결 닫기는 1초다. 정리의 5초가 끝나 취소돼도 finally의 unlock·close를 시도하므로 최대 2초의 해제 시간이 더 들 수 있다.
- 실험 종료에서 환경 닫기에도 5초를 적용하고 DB dispose는 1초로 제한한다. 취소 뒤 실행하는 연결 닫기·dispose의 자체 유예도 더해질 수 있다. 이 값들을 포함한 실경과 시간이 에피소드 본 예산과 같다고 주장하지 않는다.
- 정리 실패는 `cleanup_failed`, 실험 중단 이유는 `database_cleanup_failed`로 남긴다. 시간 초과로 관찰하지 못했으면 `turns`·`reminders_created`는 `None`이고 승인 check를 넣지 않는다. 이때 `approval_violations=0`은 미관찰 기본값이며 위반 없음의 확인 결과가 아니다.
- 같은 환경의 중복 준비·연결 시도는 새 연결 전에 `EpisodeInUse`로 거절한다. 잠금 소유 연결과 연결 중 예약을 구분해 기존 연결 참조를 덮지 않는다.

## 검증과 한계

- 스크립트 LLM으로 범주 밖 도구 반복이 단계 상한에서 끝나는지 확인한다.
- 분류·act 호출, DB 준비·관찰·정리, 취소 후 해제·환경 닫기의 대기와 준비 중 취소를 회귀 테스트로 다룬다. 기존 취소 호출 비용 미상 처리와 승인·쓰기 격리 테스트를 유지한다.
- 기존 실사용·react 요청 및 지문 테스트와 DB를 포함한 `scripts/check.sh`를 통과시킨다.
- `asyncio`의 시간 상한은 이벤트 루프가 실행되고 await가 취소에 협조할 때 동작한다. 이벤트 루프 자체를 막거나 취소를 무시하는 라이브러리를 프로세스 밖에서 강제 중지하는 장치는 이번 범위에 넣지 않는다. 그런 정지가 확인되면 스택을 확보하고 별도 프로세스 watchdog을 검토한다. 이 변경만으로 모든 형태의 정지가 해결됐다고 주장하지 않는다.

## 대안

| 대안 | 판단 |
| --- | --- |
| 범주·프롬프트·도구 집합 변경 | 정지 원인 근거가 없고 패턴 비교 조건을 바꾸므로 제외 |
| HTTP 타임아웃만 줄이기 | DB 준비·관찰·정리 대기는 막지 못하고 실사용에도 영향을 줌 |
| 평가마다 별도 자식 프로세스와 강제 종료 | 비협조적 대기도 막지만 프로세스·자원 전달 구조가 커짐. 실제 스택 확인 뒤 검토 |
| 시간 초과 뒤 성공 결과로 계속 진행 | 채점·격리 신뢰성을 해치므로 제외 |
