# ADR-0036 — 메일 질의응답 RAG 아키텍처 비교 (A0~A4)

- 상태: 채택 (2026-11-21 개발자 승인. 새 코퍼스 생성과 R02 문서 이름 정리 포함)
- 작성일: 2026-11-21
- 근거: ADR-0010(짝 비교·봉인), ADR-0006(RLS 밖 저장소), ADR-0019(메일 색인), ADR-0026(평가 세트 v1 생성 방식), ADR-0028(색인 재사용·임베딩 캐시), ADR-0029(기록·지표), ADR-0031(기준 설정), ADR-0034(시간 상한), ADR-0035(검색 정책 비교)

## 문제

ADR-0035(R02)는 현재 도구 호출형 RAG에서 **검색 시점과 질의 재작성**만 바꾼 검색 정책 비교였다. 메일 읽기·도구 흐름은 ReAct로 그대로 두었으므로 RAG 아키텍처 사이의 차이는 측정하지 않았다. 또 v1 평가 세트는 단일 메일 사실 조회 위주라서 여러 메일을 이어야 하는 질문(다중 홉)이나 메일함 전체를 모아야 하는 질문(전역 집계)이 거의 없다. 근거 메일이 800자를 넘는 사실 과제도 e2e 계정 1,800통 중 18통뿐이다.

이 ADR은 같은 생성 모델에서 RAG 구조만 바꾼 5개 구성을, 이 비교를 위해 새로 만든 질문 세트로 종단 비교하는 계획을 정한다.

## R02 이름 정리

R02의 문서 표기를 "메일 RAG 패턴 비교"에서 **"메일 RAG 검색 정책 비교"**로 바꾼다. 이번 비교의 이름과 혼동하지 않기 위해서다.

- 바꾸는 곳: `docs/eval/rag-patterns-v1.md` 제목·표의 "RAG 패턴" 열 이름, `docs/eval/README.md`의 R02 절 제목·링크 문구, ADR-0035 상단에 ADR-0036 참조 한 줄.
- 바꾸지 않는 곳: 코드 식별자(`--rag-pattern`, `RAG_PATTERNS`, `RAG_VERSION`), 지문 payload의 `pattern` 키, 파일·디렉터리 이름(`rag-patterns-v1`, `scripts/eval-rag-patterns.*`), 기록된 해시. 이름을 바꾸면 R02 설정 지문과 보관본 해시를 재현할 수 없다.
- `scripts/summarize-rag-patterns.py`가 만드는 표 머리글은 재집계 결과가 보관본과 달라지지 않도록 그대로 둔다.

## 비교할 구성

모든 구성은 같은 생성 모델(`openai/gpt-6-luna`, 추론 강도 `none`), 같은 메일 색인(Hybrid: `text-embedding-3-small` + Kiwi/`ts_rank`, RRF k=60, 800자 청크·100자 겹침), 같은 최종 답 형식을 쓴다.

| 설정 | 이름 | 흐름 | 검색 호출 |
| --- | --- | --- | --- |
| A0 | Naive | 질문 원문으로 Hybrid 검색 1회 → 상위 k통 원문을 그대로 넣고 답 생성 1회 | 1 |
| A1 | Advanced | 질의 재작성 → Hybrid 검색(후보 확대) → reranker로 재정렬 → 문맥 압축 → 답 생성 | 1 |
| A2 | Agentic (기준) | 현재 제품 ReAct. 도구는 `search_indexed_mail`, `read_mail`, 답 제출만 허용 | 모델이 결정 |
| A3 | Adaptive | 라우터 LLM 1회가 질문마다 {검색 없음, A1, A2} 중 하나를 고른 뒤 그 흐름 실행 | 경로에 따름 |
| A4 | GraphRAG | 메일에서 개체·관계를 추출해 Postgres 그래프로 저장. 질문마다 local(개체 이웃 + 원본 메일) 또는 global(커뮤니티 요약) 검색 후 답 생성 | 1 |

### 공통 조건

1. **정보 동등성**: A0, A1, A4-local은 고른 메일의 원문 전체와 머리글(보낸 사람, 받는 사람, 참조, 날짜, 제목, 첨부 유무)을 넣는다. A1의 압축은 머리글을 남기고 본문만 줄인다. A4-global만 원문 대신 커뮤니티 요약을 넣는 예외다. A2는 `read_mail` 결과로 같은 정보를 얻는다.
2. **문맥 상한**: 모든 구성의 답 생성 입력 중 검색 문맥 부분은 같은 글자 수 상한을 둔다(값은 단계 1에서 dev 근거 메일 길이 분포로 정해 지문에 넣는다). A2는 한 episode 동안 도구 결과로 받은 글자 수 합에 같은 상한을 적용한다.
   - **확정값 6,000자 (2026-11-21, 결과를 보기 전에 고정)**: 규칙은 "dev 문항별 정답 근거 본문 글자 수 합의 최댓값의 2배를 1,000 단위로 올림"이다. rag-v1 dev 실측은 단일 조회 최대 1,167자, 다중 홉 최대 1,367자(근거 2통), 전역 집계 최대 2,863자(근거 최대 5통)다. 2,863 × 2 = 5,726이므로 6,000자로 정했다. 이 값이면 모든 dev 문항의 정답 근거가 상한 안에 들어가고, 같은 양의 오답 후보를 함께 넣을 여유가 남는다. 전체 메일 본문 길이는 p50 307자, p90 831자, 최대 1,457자다. 상한을 dev 결과에 맞춰 다시 고치지 않는다.
3. **고정 프롬프트**: 각 단계 프롬프트(재작성, 압축, 라우터, 추출, 요약, 답 생성)는 버전 상수로 고정하고 설정 지문에 넣는다. 구성별로 dev 결과를 보고 프롬프트를 고치면 버전을 올리고 이전 결과와 섞지 않는다.
4. **답 형식**: 최종 출력은 {답 문장, 답/답할 수 없음, 근거 메일 핸들 목록}이다. 모델은 제공자 ID를 보지 않고 핸들(M 핸들)로만 메일을 가리킨다(D8-1).
5. **데이터 격리**: 검색·그래프 조회는 모두 `workspace_id` 필터를 같은 SQL 안에 둔다. 그래프 테이블에도 `workspace_id`와 RLS를 건다.
6. **저장 제한**: LangGraph 상태·작업 인자·로그에 메일 본문, 주소, 이름, 프롬프트 원문을 넣지 않는다(ADR-0006). 그래프 개체 이름·요약은 메일 원문에서 나온 데이터이므로 RLS가 걸린 테이블에만 둔다.
7. **읽기 전용 평가 경로**: 이번 비교는 메일 질의응답 전용 평가 경로에서만 실행한다. 승인·쓰기·일정·문서 도구는 노출하지 않는다. 제품 워커·API에서 A0·A1·A3·A4를 켜는 경로는 만들지 않는다.
8. **답 문장 확보**: 답 생성 호출이 `submit_answer`만 내고 답 문장을 비워 두면, 도구 결과를 붙여 같은 대화로 한 번 더 호출해 답 문장을 받는다(도구는 끈다). A2는 ReAct 루프가 도구 결과 뒤에 같은 방식으로 답 문장을 쓰므로, 단일 호출 구성(A0, A1, A4)에도 같은 기회를 준다. 2026-11-21 스모크에서 A0·A1은 근거 메일을 맞게 골랐지만 답 문장이 비어 `answer_facts` 채점에서 모두 실패했다. 추가 호출 여부를 진단에 기록하고 비용·지연에 포함한다. 첫 호출에 답 문장이 있으면 추가 호출하지 않는다.

### 구성별 구현 경계

- **A0**: 검색 top-k는 메일 단위 대표 청크 기준 k=5로 고정한다. 원문을 상한까지 잘라 넣고 잘린 여부를 기록한다.
- **A1**: 재작성은 R02의 `RagPolicy` 재작성 프롬프트를 재사용하지 않고 A1 전용 버전으로 둔다(질문 유형이 다르다). 후보는 Hybrid 상위 20통, 로컬 `BAAI/bge-reranker-v2-m3`로 재정렬한 상위 5통(모델 리비전 해시를 지문에 넣는다). 압축은 LLM 1회로 각 메일 본문에서 질문과 관련된 문장만 남긴다. 압축 결과에 원문에 없는 문장이 들어가면 그 메일은 원문으로 되돌리고 횟수를 기록한다. 압축 항목은 원문 문장 하나와 통째로 같아야 한다(공백 정규화 뒤 비교, 문장 일부만 고르면 부정어가 잘릴 수 있어 허용하지 않는다). 압축 뒤 본문이 비어도 머리글은 남긴다(보낸 사람·받는 사람처럼 근거가 머리글에만 있는 집계 질문이 있다. 2026-11-21 스모크에서 본문만 보고 압축한 결과 근거 메일 3통이 머리글째 빠졌다). 이런 메일은 머리글이 맥락에 들어갔으므로 도달로 세고, 본문이 빈 메일 수를 따로 기록한다. reranker는 CPU로 고정하고, 입력 길이 상한은 코퍼스 메일 전체가 잘리지 않는 값으로 정해 지문에 넣는다(긴 메일 뒤쪽 근거가 점수에서 빠지지 않게). 원문으로 되돌리는 것은 형식 실패(JSON 오류, 원문에 없는 문장, 출력 잘림)일 때만이다. 제공자 오류는 다른 구성과 같이 에피소드 실패로 센다.
- **A2**: `runflow_v0` ReAct를 그대로 쓰고 `PatternMemory.allowed_tools`로 도구를 두 개로 제한한다. 제한은 모델에 보이는 도구 목록과 실행 코드 양쪽에서 강제한다. 기존 기준 설정(ADR-0031)과 도구 목록이 다르므로 이번 A2 점수를 v1 기준선과 직접 비교하지 않는다.
- **A3**: 라우터는 질문 문장과 과거 대화만 본다. gold·태그·질문 유형을 넘기지 않는다. 라우터가 고른 경로와 각 경로 실행 결과를 모두 기록한다.
- **A4**: 라이브러리 없이 직접 구현한다.
  - 색인: 메일마다 LLM 1회로 개체(사람, 회사, 프로젝트, 문서, 장소, 결정)와 관계(삼중항)를 추출한다. 각 개체·관계에 출처 메일 ID를 남긴다. 같은 이름 개체는 정규화 규칙(공백·호칭 제거)으로 합친다.
  - 커뮤니티: 관계 그래프에서 고정 시드로 커뮤니티를 나누고 커뮤니티마다 LLM 1회로 요약한다. 요약에도 출처 메일 ID 목록을 붙인다.
  - local: 질문에서 개체를 찾고(이름 일치 + 개체 임베딩 유사도) 1~2홉 이웃 관계와 출처 메일 원문을 넣는다.
  - global: 질문과 관련된 커뮤니티 요약을 골라 넣는다.
  - 저장: 새 마이그레이션으로 `mail_graph_entity`, `mail_graph_relation`, `mail_graph_community`(이름은 구현 때 정한다)를 만든다. 모든 행에 `workspace_id`와 출처 메일 ID가 있고 RLS를 건다.
  - local/global 선택: 고정 프롬프트 LLM 라우팅 1회. 라우터는 질문 문장만 본다.
  - 커뮤니티 탐지: `networkx` Louvain, 고정 시드.

## 질문 세트 (rag-v1)

### 코퍼스

v1 world를 그대로 쓰면 다중 홉·전역 집계 질문의 근거가 부족하고 800자를 넘는 근거 메일도 거의 없다. ADR-0026 방식(구조는 코드, 본문은 LLM이 한 번 생성, 3개 계열 교차)으로 **RAG 전용 코퍼스를 새로 만든다**.

- 구조: 계정 4개, 계정당 메일 약 400통. 사람·회사·프로젝트·결정 사이 관계를 코드로 먼저 정하고, 다중 홉 사슬(예: 프로젝트 → 담당자 → 그 담당자가 보낸 견적의 금액)과 집계 대상(예: 한 프로젝트에서 나온 모든 마감일)을 구조에 심는다. 관계와 무관한 방해 메일(뉴스레터, 공지, 다른 프로젝트의 비슷한 사실)을 섞는다.
- 길이: 근거 메일의 30% 이상을 800자 초과(긴 등급)로 만든다. 사실이 본문 뒷부분에 오도록 위치도 구조 단계에서 정한다.
- 생성 비용: v1 world 8,000통 생성 실비가 1.75달러였으므로 1,600통은 약 0.4~0.6달러로 추정한다(긴 메일 비율이 높아 v1 평균보다 길다).
- 검수: v1과 같은 자동 검수와 사람 표본 검수를 거친다. 실제 메일·문서 원문은 쓰지 않는다.

### 질문 유형과 gold

| 유형 | 예 | gold 계산 |
| --- | --- | --- |
| 단일 조회 | 한 메일에 있는 금액·마감일·장소 | 구조의 사실 값과 근거 메일 1통 |
| 다중 홉 | 두 통 이상을 이어야 답이 나오는 질문 | 관계 사슬을 코드로 따라가 값과 근거 메일 집합 계산 |
| 전역 집계 | 한 프로젝트의 모든 결정, 특정 거래처와 오간 건수 | 구조에서 조건에 맞는 사실을 모두 모아 집합·개수 계산 |
| 답할 수 없음 | 코퍼스에 없는 사실, 비슷하지만 다른 프로젝트의 사실 | 구조에 해당 사실이 없음을 코드로 확인 |

- 질문 문장은 LLM이 한 번 생성하고, gold 값·근거 메일 집합은 코드가 계산한다. 질문 문장에 gold 값이 새지 않는지 코드로 검사한다.
- 사람이 전수 또는 표본 검수한 뒤 봉인한다. 확정(2026-11-21): 질문 유형마다 10개씩 40개를 계정별로 돌아가며 뽑는 표본 검수, 시드 20261121(`scripts/rag_v1_review_sample.py` → `review-sample.md`, 근거 메일 본문 전체 포함). 표본에서 생성 규칙 문제가 나오면 같은 규칙으로 만든 문항 전체를 다시 확인한다.
- 검수 결과와 봉인(2026-11-21): 표본에서 세 가지 생성 규칙 문제가 나왔다. 뜻이 둘로 읽히는 결정 문구가 있었고, 마감이 없어야 할 메일에 마감 표현이 남았고, 결정 메일 하나에 결정이 여러 개 나열됐다. 결정 문구 "회의록은 당일 공유"를 "외부 공유 자료는 PDF로만 배포"로 바꿨다. 같은 자리에 넣어 다른 묶음의 배정은 그대로다. 마감·다중 결정 금지 규칙(정규식)을 더한 뒤 위반한 본문만 다시 생성했다. 그 결과 정답이 바뀐 문항은 3개다. 같은 규칙의 메일 전체를 대조 검사해 위반 0건을 확인했다. 본문 생성 누적 비용은 $0.4515다. `python -m orbit.evaldata.rag_v1 seal`로 봉인했다(test 96문항·24묶음, `manifest.json`의 `seal`). `verify-seal`로 봉인 뒤 변경 여부를 확인한다.
- 묶음(cluster)은 같은 관계 사슬·같은 집계 대상을 공유하는 질문끼리 묶고, 묶음 단위로 dev/test를 나눈다.
- 채점: 성공은 근거 메일 판정과 답 문장 판정을 모두 통과해야 한다. 집계 질문은 원소별 사실을 모두 맞춰야 성공이다. 답할 수 없음 질문은 abstain이 정답이다.
  - 근거 메일: 구조화된 답(`submit_answer`의 메일 핸들)을 gold 근거 메일과 코드로 비교한다.
  - 답 문장: 모든 episode를 코드로 채점한다. 기존 `answer_facts`(any_of 문자열, 공백 무시)에 금액·날짜·개수 표기 정규화를 더한다(예: "세 통"→3, "오백삼십칠만 원"→5,370,000, "2026-11-24"→11월 24일). 정규화 규칙은 dev 결과를 보기 전에 고정한다.
  - 코드 채점 검증(2026-11-21 개발자 결정, 표본 200건에서 500건으로 늘림): 답할 수 있는 질문의 episode(5구성 × 120문항 × 3 = 1,800건) 중 500건을 뽑아 LLM Judge로 정답과 뜻이 같은지 판정하고, 코드 채점과의 일치율을 구성별·유형별로 보고한다. 표본은 구성마다 100건, 그 안에서 질문 유형과 repeat를 고르게 나누고 고정 시드로 뽑는다. Judge는 답하는 모델(luna)과 다른 계열인 `google/gemini-3.6-flash`(근거성 Judge와 같은 모델)로 고정하고, 프롬프트 버전과 모델 ID를 설정 지문에 넣는다. 둘이 다른 건은 사람이 확인해 어느 쪽이 맞는지 기록한다.
  - 기록(2026-11-21): 처음에는 v1의 문자열 일치 채점을 그대로 쓰기로 했다. 스모크에서 뜻은 맞지만 표현이 다른 답("세 통", 결정 문장 바꿔 말하기)이 오답 처리되는 것을 발견해 위처럼 바꿨다. 이 일로 낭비된 유료 호출은 약 0.01달러다.
  - 기록(2026-11-22, dev 1차 실행 뒤): 다중 홉 성공률이 모든 구성에서 0이었다. gold 메일을 직접 넣은 oracle도 마찬가지였다. oracle 다중 홉 48건을 보면 답 문장은 맞는데 `submit_answer`를 `abstain`으로 낸 경우가 20건, 대상을 확인한 중간 메일을 빼고 답 메일 1통만 낸 경우가 28건이었다. 공용 답 제출 안내의 `message_set`은 "조건에 맞는 메일 전부"만 설명하고, 메일 내용을 묻는 질문에 무엇을 제출할지는 알려주지 않는다. 채점 규칙은 바꾸지 않았다. 모든 구성의 답 생성 프롬프트에 같은 안내 단락(`RAG_ANSWER_NOTE`, `rag-answer-note-v1`)을 더했다. 내용은 세 가지다. 메일 내용을 묻는 질문에 답했다면 근거 메일을 `message_set`으로 낸다. 중간 메일도 넣는다. 답을 찾지 못했을 때만 `abstain`을 낸다. dev 전 구성을 다시 실행한다. 1차 dev 결과(LLM 약 0.49달러)는 비교에 쓰지 않고 이 결정의 근거로만 남긴다. test 분할은 이 수정 전에 실행하지 않았다.

## 지표와 통계

### 주 지표

- task success. 각 구성과 A2의 같은 task/repeat 짝 차이, cluster bootstrap 95% CI(10,000회, seed 0), pass³.
- 유형별(단일·다중 홉·집계·답할 수 없음) 성공률과 짝 차이를 함께 보고한다. 유형별 CI는 표본이 작으므로 탐색 결과로 표시한다.
- 선택은 dev에서 하고 test는 봉인한 뒤 한 번 확인한다(ADR-0010).

### 진단 지표

1. **검색 재현율(recall@K)**: gold 근거 메일 중 검색 상위 K개에 든 비율. 표준 이름으로 보고한다(2026-11-21 개발자 결정).
   - A0는 검색 순위, A1은 reranker 순위로 recall@1·@3·@5·@10을 낸다. 답 생성 입력에 넣는 수가 5개이므로 recall@5가 실제로 LLM에 넘어간 비율이다. 검색 결과 순위를 실행 기록에 남긴다.
   - A2·A4는 고정 K가 없어 recall@K로 부르지 않는다. A2는 episode 전체 도구 결과의 합집합 recall, A4는 넣은 관계·요약의 출처 메일 ID로 역추적한 recall로 따로 표시한다.
   - A3는 고른 경로의 방식을 따른다.
2. **근거 인용 정밀도·재현율**: 답에 붙인 핸들과 gold 근거 메일 비교.
3. **groundedness Judge**: 답 문장이 넣은 문맥에 근거하는지(J04 채택 Judge). 모든 구성·문항의 repeat 0에 적용한다.
8. **코드 채점 일치율**: 표본 500건에서 코드 채점과 정답 비교 Judge가 일치한 비율(구성별·유형별), 다른 건의 사람 확인 결과. 일치율이 낮은 구성·유형의 성공률은 결과 문서에 함께 표시한다.
4. **효율**: episode당 LLM 호출 수, 입력·출력 토큰, 비용, 지연 p50·p95, 검색 호출 수.
5. **색인 비용**: A4 추출·커뮤니티 요약의 1회 구축 비용과 시간, 메일 1통 추가 시 갱신 비용(재추출 + 영향받은 커뮤니티 재요약). A1 reranker 처리 시간.
6. **A3 라우팅**: 질문 유형별 경로 분포. "검색 없음"을 고른 질문 중 실제로 검색이 필요했던 비율. 라우팅 정확도는 사전에 정한 유형→경로 기대표와 비교한다(기대표는 단계 1에서 결과를 보기 전에 정한다).
7. **A4 추출 품질**: 코퍼스 구조의 gold 관계 그래프와 비교한 개체·관계 추출 재현율과 정밀도.

**비용 상한 11달러(2026-11-21 개발자 결정, 처음 10달러에서 올림)**: 처음 추정 합계는 약 17달러였고 그중 Judge가 약 11.5달러였다. 개발자 결정으로 Judge는 모든 구성·문항의 repeat 0만 채점해 합계를 약 9.4달러로 맞췄다. 이후 정답 비교 Judge(표본 500건, 약 1.3달러)를 더해 합계는 약 10.7달러가 되어 처음 상한 10달러를 넘었고, 개발자 결정으로 상한을 11달러로 올렸다. 주 지표(성공률·짝 차이·pass³)는 3회 반복 전체로 계산한다. 상한까지 여유가 약 0.3달러뿐이므로 각 단계 실행 전에 dry-run으로 다시 추정해 보고하고, 실행 중 누적 비용이 단계 상한을 넘으면 멈춘다. 후보와 지표는 줄이지 않는다.

## 단계 계획

1. **R02 이름 정리**: 문서만 고친다(메인 세션).
2. **코퍼스·질문 세트 rag-v1**: 구조 생성 → 본문 생성(비용 승인) → 질문 생성 → gold 계산 → 자동 검수 → 사람 검수 → 봉인.
3. **공통 평가 경로**: 메일 QA 전용 러너, 답 형식, 문맥 상한, context recall 기록, 진단 지표 집계. A2(도구 제한)와 A0를 먼저 붙여 스모크로 확인한다.
4. **A1**: reranker·재작성·압축.
5. **A4**: 마이그레이션·추출·커뮤니티·local/global 검색, 추출 품질 지표.
6. **A3**: 라우터. A1·A2가 있어야 한다.
7. **dev 실행**: 비용 재추정·승인 → 5구성 × dev × 3, oracle 문맥 실행, dev Judge(repeat 0) → 결과와 실측 비용 보고. 프롬프트 수정이 필요하면 이 단계에서만 한다.
8. **test 실행 승인**: dev 실측 비용으로 test 비용을 다시 추정해 상한 안인지 확인하고 승인받는다.
9. **test 실행**: 봉인 해제 → 확인 실행 → 결과 문서(`docs/eval/rag-architecture-v1.md`)와 README 갱신.

각 단계는 implementer에 위임하고 code-reviewer 검토를 거친다. 2·5·7·9단계는 유료 호출 전에 예상 비용을 보고하고 승인을 받는다.

## 결과와 위험

- RAG 구조 차이를 같은 모델·같은 질문에서 비교한 기록이 생긴다. 측정 전에는 어느 구조가 낫다고 쓰지 않는다.
- A2 점수는 도구 제한 때문에 v1 기준선과 다르다. 기준 설정 변경은 결과를 보고 따로 결정한다.
- A4는 새 테이블과 추출 파이프라인이 생긴다. 평가 전용이며 제품 경로에 연결하지 않는다.
- 질문 생성에 쓴 계열과 평가 모델(luna)이 같은 계열이면 자기 계열 편향이 생길 수 있다. 생성 계열별 결과를 나눠 본다(ADR-0026).
