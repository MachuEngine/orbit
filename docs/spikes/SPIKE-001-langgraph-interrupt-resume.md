# SPIKE-001 — LangGraph 승인 대기 → 워커 재시작 → 재개

- 상태: 완료 (2026-11-10) — 가정 성립, 조건 4개 (ADR-0003 제안)
- 관련 결정: 세부 설계 D5-3(LangGraph의 역할), D5-2(백그라운드 워커), D5-4(멱등성), ADR-0002(Python)
- 기간: 1~2일
- 코드: `spikes/001-langgraph-resume/` (스파이크용 코드이며 제품 코드로 쓰지 않는다)

## 확인할 질문

LangGraph의 `interrupt` + PostgreSQL checkpointer로 다음이 가능한가?

1. Agent 실행이 승인 요청 지점에서 멈추고, 그 상태가 PostgreSQL에 저장된다.
2. 실행하던 워커 프로세스가 종료되거나 강제 종료되어도, **다른 프로세스**가 같은 `thread_id`로 실행을 이어 갈 수 있다.
3. 그래프를 실행하지 않는 프로세스(API 서버 역할)가 대기 중인 승인 요청의 내용을 읽을 수 있다. Orbit은 이 내용으로 `approval` 행을 만든다.

그리고 재개할 때 **어떤 코드가 다시 실행되는지** 측정한다. 외부 쓰기가 두 번 실행될 수 있는 지점을 알아야 D5-4의 멱등성 설계를 확정할 수 있다.

## 실험 그래프

```text
START → plan → approval → (승인) execute → END
                        → (거부) rejected → END
```

- `plan`: 계획 단계를 흉내 낸다. 설정에 따라 지정한 시간만큼 멈춘다(강제 종료 시점을 만들기 위해).
- `approval`: `interrupt()` 호출 전에 "interrupt 앞 코드 실행" 기록을 1건 남긴다. 그다음 승인 요청 내용(`tool`, `args`, `args_hash`)을 담아 `interrupt()`를 호출하고, 재개 값으로 승인·거부를 받는다.
- `execute`: 외부 쓰기를 흉내 낸다. 부수 효과 테이블에 "외부 쓰기" 1건을 기록한다. 설정에 따라 기록 전후로 멈춘다.
- `rejected`: 거부 상태로 끝낸다.

부수 효과는 PostgreSQL의 별도 테이블에 `thread_id`별로 기록해 실행 횟수를 센다.

## 시나리오와 판정 기준

검증 시나리오는 기대 결과와 다르면 실패로 본다. 관찰 시나리오는 실제 동작을 기록만 하고 실패로 보지 않는다.

| ID | 구분 | 절차 | 기대 결과 |
| --- | --- | --- | --- |
| S1 | 검증 | 프로세스 A가 시작해 interrupt에서 멈추고 종료 → 프로세스 B가 대기 중인 승인 요청을 읽음 → 프로세스 C가 승인으로 재개 | B가 `tool`·`args`·`args_hash`를 읽는다. C에서 완료된다. 외부 쓰기 1건 |
| S2 | 검증 | S1과 같지만 거부로 재개 | 완료 상태가 거부. 외부 쓰기 0건 |
| S3 | 검증 | `plan` 실행 중에 프로세스를 SIGKILL → 새 프로세스가 같은 `thread_id`로 이어서 실행 | interrupt 지점에 도달한다. 이후 승인하면 완료되고 외부 쓰기 1건 |
| S4 | 관찰 | 승인으로 재개 후 `execute`가 외부 쓰기를 기록한 **직후** SIGKILL → 새 프로세스가 이어서 실행 | 외부 쓰기 횟수를 기록한다 (1건이면 재실행 없음, 2건이면 노드 재실행) |
| S5 | 검증 | S1 완료 후 같은 `thread_id`에 승인 재개를 한 번 더 보냄 | 외부 쓰기가 늘지 않는다. 오류인지 무시인지 기록한다 |
| S6 | 관찰 | S1에서 "interrupt 앞 코드 실행" 기록 횟수 | 문서상 2회가 예상된다(재개 시 노드를 처음부터 다시 실행) |
| S7 | 관찰 | interrupt 대기 중인 같은 `thread_id`에 두 프로세스가 동시에 승인 재개 | 외부 쓰기 횟수와 각 프로세스의 결과를 기록한다 |

**가정이 성립했다고 보는 조건:** S1, S2, S3, S5가 기대대로 동작하고, S4·S6·S7의 동작을 설명할 수 있다.

## 결과

실행: `uv run python run_scenarios.py --repeat 10` (2026-11-10, 로컬 Docker). 체크포인트 저장 방식은 LangGraph 기본값 `durability="async"`를 그대로 썼다.

| ID | 구분 | 10회 결과 | 외부 쓰기 | interrupt 앞 코드 실행 | 해석 |
| --- | --- | --- | --- | --- | --- |
| S1 | 검증 | PASS 10/10 | 1 (10회) | 2 (10회) | 다른 프로세스에서 재개 가능. 그래프를 실행하지 않는 프로세스가 `get_state(...).tasks[].interrupts[].value`로 승인 요청 내용을 읽었다 |
| S2 | 검증 | PASS 10/10 | 0 (10회) | 2 (10회) | 거부 경로 정상 |
| S3 | 검증 | PASS 10/10 | 1 (10회) | 2 (10회) | `plan` 실행 중 SIGKILL 후 새 프로세스가 `invoke(None)`으로 이어 가 interrupt에 도달. `plan`은 처음부터 다시 실행됐다 |
| S4 | 관찰 | 유효 10/10 | **2 (10회)** | 2 (10회) | 외부 쓰기 커밋 직후 SIGKILL하면, 복구 시 `execute` 노드가 처음부터 다시 실행되어 외부 쓰기가 **중복**된다 |

| S6 | 관찰 | — | — | **2 (10회)** | 재개 시 interrupt가 있는 노드를 처음부터 다시 실행해 interrupt 앞 코드가 두 번 실행된다 (문서와 일치) |
| S7 | 관찰 | — | **2 (10회)** | 3 (10회) | 대기 중인 같은 스레드에 두 프로세스가 동시에 승인하면 **둘 다 실행**되어 외부 쓰기가 중복된다. 두 프로세스의 interrupt 앞 코드 기록 시각 차이는 약 0.01ms, 외부 쓰기 시각 차이도 0.01ms 수준이었다 |

### 판정 근거와 전제
- S5 "무시"의 근거: 두 번째 재개의 종료 코드 0, RESULT에 오류 없음, 두 번째 재개 전후로 `pre_interrupt`·`external_write` 횟수 불변.
- S4는 매 회차 전제(시작 성공, MARKER 확인, 종료 코드 -9)를 확인했고 10회 모두 유효했다.
- S7의 동시성 근거: `pre_interrupt` 3건(시작 1 + 재개 2)과 두 프로세스의 기록 시각. 한쪽이 끝난 뒤 다른 쪽이 시작했다면 S5처럼 무시됐을 것이다.
- S3은 SIGKILL 시점에 입력 체크포인트가 이미 저장되어 있어야 성립한다. 10회 모두 성립했다.

### 하지 않은 것
- `durability="sync"`, `"exit"` 설정에서의 동작은 측정하지 않았다.
- 승인 대기 상태로 오래(분·시간 단위) 둔 뒤의 재개, LangGraph 버전 업그레이드 후 기존 체크포인트 재개는 확인하지 않았다.
- 동시 재개를 막는 방법(행 잠금, advisory lock 등)의 효과는 측정하지 않았다.

## 결론과 Orbit 설계에 주는 영향

**가정은 성립한다.** LangGraph `interrupt` + PostgreSQL checkpointer로 승인 대기 → 워커 종료·강제 종료 → 다른 프로세스 재개가 된다. API 서버는 그래프를 실행하지 않고도 대기 중인 승인 요청을 읽을 수 있다. 따라서 D5-3(LangGraph는 그래프 내부 상태만 담당)을 유지한다.

다만 **LangGraph는 외부 쓰기의 중복 실행을 막아 주지 않는다.** S4·S6·S7에서 같은 외부 쓰기나 interrupt 앞 코드가 두 번 실행됐다. 이는 세부 설계 D5-4("기록 먼저, 호출 나중", 승인 ID를 멱등 키로 사용)가 선택이 아니라 필수라는 근거다. 구현할 때 지킬 조건은 ADR-0003에 정리했다.

1. 외부 쓰기 전에 `execution` 행을 멱등 키(`approval_id`)와 유일 제약으로 먼저 커밋하고, 이미 있으면 호출하지 않는다 (S4, S7).
2. 승인 결정은 Orbit의 `approval` 행 상태 전이(`PENDING` → `APPROVED`)를 조건부 갱신으로 한 번만 성공시키고, 성공한 쪽만 그래프를 재개한다 (S7).
3. interrupt가 있는 노드에서는 interrupt 앞에 부수 효과를 두지 않는다. 승인 요청 기록처럼 꼭 필요한 쓰기는 멱등하게 만든다 (S6).
4. 중복 재개를 LangGraph가 오류로 알려 줄 것이라고 기대하지 않는다. 재개 가능 여부는 Orbit의 `approval`·`run` 상태로 판단한다 (S5).

### 후속 확인 (백엔드 골격 단계)
- 외부 쓰기가 있는 Run에 `durability="sync"`를 쓸지 정하고, S4를 그 설정으로 다시 측정한다.
- 위 조건 1·2를 구현한 뒤 S4·S7과 같은 시나리오를 통합 테스트로 만들어 외부 쓰기 1건을 보장하는지 확인한다.
